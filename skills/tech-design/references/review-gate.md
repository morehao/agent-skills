# 评审 gate（review-gate）

**定位**：把「写完自检」升级为「作者自检 **+** 独立评审」。自检是作者视角，会顺着自己的叙述讲过去；**独立上下文才是这套东西成立的前提**——fresh reviewer 找的是作者讲过去的那部分。所以 gate 只做自检做不了的事，不替代自检。

## 何时跑

| 档位 | 是否跑 | 说明 |
|------|--------|------|
| 完整 | **必跑** | 跨系统、不可逆变更、需要委员会评审的，一个 lens 都不许省 |
| 标准 | 建议跑 | 出现跨团队评审、SLA 承诺、动契约或表结构时升级为必跑 |
| 轻量 | 跳过 | 一次评审能过的小改动，跑 gate 的收益低于成本 |

落点 C（改既有模块）与场景 S3/S4（重构、迁移）即使标准档也按「必跑」对待——这两类最容易漏影响面。

## 评审模式（评审既有文档）

用户拿一份别人的文档来评审时，**不按档位裁剪**：

- **第 1 段门禁 + 第 2 段 rubric 必跑**，轻量档也不例外——作者不是你，作者的自检结果你看不到。
- **门禁不通过是常态，不是止步条件**：`## 三段` 的「非 0 不进第 2 段」只适用于作者自评；评审他人文档时，把 error/warn 原文收进 findings，继续 rubric 与 lens。
- **lens 选 1–2 个**，按文档实际出现的信号选（有表结构 → 数据与迁移；改契约/行为 → 调用方兼容；涉敏感数据 → 安全）；没有信号的 lens 不硬凑。
- **只出 findings，不改文档**：每条给「严重度 + 位置 + 问题 + 改法」；`autofix` 只在用户明确要求时执行。
- **文档缺状态块 / 备选 / 追溯表**：记为 findings，不替作者补。
- **报告**：先 `VERDICT`，再 findings 表；不写「整体不错，建议完善」这类没有位置与动作的结论。

评审模式与编写模式的差别只有「写不写」；判定标准、lens 追问、严重度分级完全一致。

## 三段

### 第 1 段：确定性（先跑，省评审者注意力）

```bash
node <本skill目录>/scripts/check-design-doc.mjs <文档> --tier <light|standard|full> [--upstream <PRD>...] [--strict]
```

- `error` 必须先改完再进第 2 段——机械错误不该占用评审者的判断力。
- `warn` 逐条裁决：改掉，或在文档里显式豁免并写理由（不允许无声跳过）。
- `note` 必须读一遍（`[待核实]`/`[待澄清]`/`[假设]` 是否都收口到开放问题）。
- 退出码非 0 时不进第 2 段。

### 第 2 段：rubric walker（清单判定）

按档位从 `quality-bar.md` 的「评审检查清单」取子集（**那是唯一真源，本节不复述**），逐条判 `pass / gap`，`gap` 必须给位置与改法。

### 第 3 段：并行 lens（独立上下文）

按**场景与专题**选 2–4 个风险 lens（下表前四行），完整档再固定加一个实施者视角 lens；每个一个独立 subagent：

| lens | 何时选 | 追问 |
|------|--------|------|
| 安全与合规 | 专题含安全、涉敏感数据、需合规审查 | 越权与鉴权边界、密钥管理、日志脱敏、审计留痕 |
| 数据与迁移 | 动表结构、换存储、迁移场景 | 每条索引回指查询？DDL 与正文逐项一致？对账方式？回退窗口？ |
| 运维与可观测 | 完整档、上线形态有变化 | 上线步骤可执行？回滚阈值可观测？容量推导能否复算？ |
| 调用方兼容 | 落点 B/C、改契约或行为 | 谁在调（带证据）？行为变化清单？回归范围与等价性验证？ |
| **实施者视角**（builder check） | **完整档必跑**；标准档若由多人排期也跑 | 一个没参与讨论、也联系不上作者的人，能否照着排期？他在哪里必须猜，猜错会怎样？ |

前四个 lens 问的是「有没有坑」，实施者视角问的是「能不能照着干」——它不评判方案好坏，只暴露「必须猜而且猜错会改变做法」的地方。两者不能互相替代：坑填完了，文档照样可能排不出期。

**subagent 契约**（每个 lens 相同）：

- **输入**：文档路径 + 该 lens 的追问清单 + `quality-bar.md` 相关条目 + （可选）上游 PRD / 代码路径。
- **不看作者的中间推理**：只读交付文档与证据，避免被作者叙述带走。
- **输出**：完整评审写到 `<文档目录>/reviews/review-<lens>.md`（子目录，不污染交付目录）。
- **只回摘要**：`VERDICT:` + top 3 findings（严重度 / 位置 / 改法）+ 文件路径。**不把全文塞回父上下文。**
- subagent 不可用时退化为顺序执行：先写文件，再从上下文里冲掉。

### 实施者视角（builder check）

派一个独立 subagent，用下面这段提示词（`<文档路径>` 替换成绝对路径，`<领域>` 换成对口角色）：

```
你是一位资深<领域>工程师。你被交付一份技术方案，需要据此排期实施。
你联系不上作者，也不能假设还能问人。

读 <文档路径>。只报告一件事：在你能够排期之前，仍然必须问清的问题——
即「你必须猜、而猜错会改变做法」的地方。

每条给：问题 + 为什么答案会改变计划（影响哪个阶段、哪个组件、哪条验收）。

跳过三样：文档明确写明留给实施者决定的内容；你自己能合理决定的小事；措辞与排版意见。

如果确实没有重要缺口，只输出：nothing important left
```

产出不是评审结论，而是一串**问题**。父代理按三堆处置，**只问用户一轮**：

| 堆 | 判定 | 处置 |
|---|---|---|
| 文档里其实答过 | 正文/假设/上游文档已有 | 把它写进文档对应位置（不是回问用户） |
| 小事 | 合理工程师能自定，且不影响做法 | 自己定，在文档里标成「实施者判断」并给默认值 |
| 只有拍板人能定 | 答案会改变方案或排期 | 汇总进开放问题，一次问完，标默认倾向与拍板人 |

三堆都处置完才算通过：**问题不许悬空**——没归属的 builder 问题等价于一个未定项。

**停止条件（实测过，别指望跑到 0）**：同一份文档连跑四轮，条数是 8 → 5 → 6 → 7，**不降反升**。原因有两层：一是修法自己会制造新矛盾（补了批次表 → 冻结没记到批次；加了 LEGACY 批次 → 与「3.2 亿行要补批次」打架）；二是越往后越深，从「文档自相矛盾」变成「设计真错了」。

所以停法不是看条数，是看**这轮的问题属于哪一类**：

| 问题性质 | 说明 | 动作 |
|---|---|---|
| 文档内部打架、判据不能同真 | 作者自己能改 | 改，别问人 |
| 只有拍板人能定（口径、范围、优先级） | 方案已写到边界 | 进「待确认与开放问题」+ 默认倾向，停 |
| 要新增一个子系统或跨团队改造才能回答 | **超出本方案范围** | 进「已知未覆盖」，写清为什么现在不解决、谁在什么条件下解决 |
| 上一轮修法引入的新矛盾 | 正常现象 | 改掉，并在文档里记一句为什么这么选 |

判据一句话：**当新问题开始需要「设计一个新东西」才能回答时，builder check 就该停**——那已经是设计工作，不是评审工作。剩下的缺口写进文档的「已知未覆盖」，让评审者带着看，比假装想全了有用。

### 收口：单一裁决

父代理把三段汇总成一张表，并给**一个**裁决：

```
VERDICT: approve | revise
```

| ID | 严重度 | 位置 | 问题 | 改法 | 处置 |
|----|--------|------|------|------|------|
| G1 | high | 详细设计/数据模型 | 索引未回指查询 | 补「服务的查询」列 | autofix |

处置四选一：`autofix`（直接改）/ `discuss`（需人拍板，进开放问题）/ `defer`（收进开放问题并写触发条件）/ `ignore`（写理由）。

`revise` 的每条发现必须**一次能改完**（位置 + 改法齐全）。approve 后可附非阻断建议。

## 硬规则

- **gate 不替代自检**：交付前自检照跑，顺序是「自检 → 门禁 → gate」。
- **lens 是地板不是菜单**：由场景与专题决定，不能因为「这次应该没安全问题」裁掉安全 lens。
- **报 tier 不报流水账**：先一句裁决，再 critical/high；medium/low 收进「另有 N 条见 reviews/…」。
- **不可执行的建议不进 findings**：`建议优化`、`可读性欠佳` 这类没有位置与动作的，写出来只是噪音。
- **评审者不改文档**：除 `autofix` 由父代理执行外，lens 只读。

## 反模式

| 反模式 | 症状 | 改法 |
|--------|------|------|
| 自己评自己 | 作者跑 gate 并自我 approve | 换独立上下文（subagent），作者只做裁决与 autofix |
| lens 被裁掉 | 「这次没安全问题」跳过安全 lens | lens 由场景/专题决定，不由作者心情决定 |
| 全文回流 | 4 份评审全文拼进父上下文 | 只回 verdict + top3 + 路径 |
| 意见不可执行 | 「建议再完善一下」 | 指出失败条件、位置、改法 |
| 没有裁决 | 报一堆问题不说 approve/revise | 必须给单一裁决，否则评审者无法收尾 |
| 用 gate 当自检 | 跳过交付前自检直接跑 gate | 自检先跑；gate 只补独立视角 |
| 用风险 lens 代替 builder check | 「四个 lens 都说没问题，那就能实施了」 | 风险 lens 不问「能不能照着干」；完整档必须单独跑实施者视角 |
| builder 问题悬空 | 收了一堆「他可能要问」，最后没人管 | 三堆处置：补文档 / 自决并标注 / 一次性上问 |
