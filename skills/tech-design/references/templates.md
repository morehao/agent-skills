# 模板档位（templates）

三档骨架决定**篇幅与评审范围**。三个维度各管一段，冲突时按右列：

| 维度 | 作用域 | 冲突时 |
|------|--------|--------|
| **档位（本文）** | 篇幅、评审范围、读者 | — |
| 场景（`scenarios.md`） | 落点（第 0 问）+ 变更性质；过程义务、按场景增删章节 | 过程内容与章节增删听场景 |
| 专题（`focus-areas.md`） | 技术领域加固点 | 技术内容听专题 |

骨架综合了主流方案/设计文档实践：Google Design Doc 的「目标/非目标 + 备选方案 + 横切关切」、arc42 的「约束 → 上下文 → 解决策略 → 构建块 → 运行时 → 部署」顺序与「风险与技术债」、Rust RFC 的「开放问题分类收口」、ADR 的决策记录、ISO/IEC/IEEE 42010 的「关切—视图」与可追溯性，以及国内评审的「验收标准 / 发布回滚 / 业务与技术目标二分」惯例（对照见文末）。

## 叙事链：先推理，再成文

下面的骨架是**成文顺序**；决定方案质量的是它背后那条**推理链**。动笔前先把 9 问答清楚——答不出的地方就是还没想清楚，不要用章节名把空白盖住。

| # | 问题 | 落到骨架 |
|---|------|----------|
| 0 | **为什么现在做？** 不做的代价是什么？ | 背景与目标（动因与收益） |
| 1 | **有什么？** 从需求梳理**领域实体**、关系、生命周期与状态 | 数据模型（先于表结构） |
| 2 | **要解决什么问题？** 痛点在哪个场景、多频繁、证据是什么 | 现状与痛点 |
| 3 | **有哪些约束？** 硬约束（技术栈/部署/合规/预算）+ 量化质量目标与可用性预算 + 宿主约束 | 约束与非功能需求 |
| 4 | **整体怎么设计？** 上下文与边界 → 解决策略 → 备选与取舍 | 总体架构 + 方案与选型对比 |
| 5 | **怎么拆？** 构建块、职责与数据所有权、接口契约的冻结点 | 模块划分与职责、接口设计 |
| 6 | **怎么流转？** 关键运行时场景、数据流转、失败路径、部署形态 | 核心流程、数据流转、部署与资源拓扑 |
| 7 | **怎么证明它对？** 验证手段、最脆弱假设与证伪实验、验收阈值 | 验证与验收 |
| 8 | **为什么这么设计、怎么落地？** 决策理由、里程碑与切流、成本、风险与技术债、开放问题 | 选型理由、实施计划、上线与回滚、风险 |

**顺序依赖（不可随意换）**：

- 约束先于策略：没有硬约束就没有方案空间；先画架构再补容量目标是倒推。
- 上下文与边界先于分解：边界错了，模块怎么拆都错。
- 实体与生命周期先于表结构。
- **决策理由必须回指目标或约束**（给定事实与目标，证明为什么这个方案最好地满足了它们），不是泛泛比优劣。
- 验收必须回指目标：**目标/约束 → 决策 → 验证手段 → 验收阈值**四者要对得上。

**发现顺序 ≠ 成文顺序**：真实设计是拿 2–3 个关键场景走一遍 → 发现边界该切在哪 → 回头改分解。发现阶段**允许回溯**，成文阶段才是线性的；不要把成文顺序当成思考顺序。

档位只裁剪**展开深度**，不裁剪第 3 问（约束）与第 8 问（理由）——这两问答不出来，方案不值得评审。

## 通用约定（读骨架前先读这段）

1. **骨架是覆盖清单，不是填空卷**。不适用的章节**删掉**，不要留 "N/A" 或一句话占位——占位章节比缺章节更伤可信度。
2. **骨架里的括号只允许是结构标记**（`（可选）`/`（如适用）`/`（按需）`），不写内容指令；内容的必答项在下方的「各节必答项」表里，**不要**把表里的说明抄进正文。
3. **章节增删优先听场景**：`scenarios.md` 的「章节增删」高于本文骨架。例：S1 新建要删自身现状章节；S3 结构重构必须加「行为基线与等价性验证」。
4. **章节名是语义示例**，随主题替换；不加「1. 2.」数字前缀（用户明确要求编号时可在成稿时补，但不写进模板）。
5. **非目标用「超出范畴的用例」表述**，比否定句可评审：
   - 弱：「不做权限管理」。
   - 强：「超出范畴的用例：本期不覆盖跨租户数据共享、不提供字段级权限；原因是这两项需要独立的权限模型，计划在二期立项（见开放问题）」。
6. **验收标准必须可验证**：谁验、怎么验、阈值多少。凡涉及性能/容量/可用性的阈值，按 `quantification.md` 给推导与口径。
7. **不确定项集中收口**：评审需拍板的、实现中才能定的、范围外后续做的——分三类落在「开放问题」，不要散在正文里含糊。
8. **关切承载**：每个关切（安全、合规、运维、调用方、成本、可维护性）至少有一个章节或视图承载；先按读者列表反查（见「档位速览」），缺谁就补谁的关切。
9. **目标与收益**：目标分**业务目标**（底线）与**技术目标**（可衡量，如 QPS/RT/容量/成本）；同时给**收益口径**（省成本/省人力/提升转化/降风险），收益要能在上线后被验证。
10. **选型与备选**：备选必须包含**「不做 / 维持现状」**这一对照项并写不做的代价；先定评估维度与 **must-have 门槛**（不满足硬约束的直接淘汰），再比偏好。**备选必须来自不同的约束视角**（最小改动 / 最大扩展 / 最常见调用方最省事 / 最小运维），每个视角独立推演；若两个备选的差异只体现在参数或命名上，视为没做备选（`quality-bar.md` 反模式）。
11. **文档状态与决策留痕**：文档头部给状态块（状态、作者、评审人、拍板人、最后更新）；决策按 ADR 记「结论 + 备选 + 理由 + 状态（Proposed/Accepted/Superseded）+ 置信度」。不确定的决策就标低置信度，比假装确定好。**标准档及以上必须落成「决策与需求对照表」**（决策 ID / 决策 / 承接需求 / 备选含不做 / 验证手段 / 状态 / 置信度），把目标/约束 → 决策 → 验证手段 → 验收阈值一行一行对齐；只有散文叙述视为未完成。
12. **图按职责选工具**：结构/映射/对比/回边状态机 → SVG（走 `svg-maker` 产出）；时序/线性小图 → Mermaid；节点 ≥12 或含分层/泳道/边界即改用 SVG。同一张图只留一种形式，图前有导读段、图后有落着（`quality-bar.md` 图规范）。
13. **数据库设计三件套**：正文用**表**承载设计（实体清单 / 字段 / 索引与查询匹配），给一张**简版 ER 图**（只含实体、主键与关系基数），**DDL 收进附录**「数据模型 DDL」——正文不贴 `CREATE TABLE`；附录 DDL 是唯一可执行真源，落盘前与正文表格逐项核对一致。细则（三张表的列、ER 图选型、按场景的 DDL 形态）见 `data-model.md`。

14. **文档随实施演进，交付不是终点**：设计变更且**未上线**→ 直接改原文并更新「最后更新」；**已上线**→ 文末追加「修订记录」（日期 + 改了什么 + 为什么），旧结论保留可追溯；被推翻的决策把状态改成 Superseded 并指向新决策，**不删旧记录**。跨版本大改拆出子方案互链，别把原文改到没有考古价值。

### 写作前的两份工作产物（不进交付文档）

**取证台账**——第 5 步取证时边查边记，成文只用结论：

| 事实 | 证据锚点 | 采信时间 | 影响章节 | 状态 |
|------|----------|----------|----------|------|
| 下单 P99 = 180ms | APM 面板 `order-submit`，2026-09 月度 p99 | 2026-10-26 | 约束与非功能需求 | 已确认 |
| 库存服务峰值 8000 QPS | 无面板，按秒杀峰值推算 | — | 容量设计 | `[待核实]` |

**备选视角清单**——第 9 步撰写前，先按四个视角各想一遍，再决定哪 2–3 个进正文：

| 视角 | 产物 | 通常被选中的情形 |
|------|------|------------------|
| 最小改动 | 不引入新组件的最短路径 | 存量系统、发布窗口紧 |
| 最大扩展 | 为未来 3 倍规模留余地 | 规划期长、增长确定 |
| 最常见调用方最省事 | 主路径零额外成本 | 调用方多、改造成本敏感 |
| 最小运维 | 少一个组件就少一份故障 | 运维人力薄 |

## 档位速览

| 档位 | 目标篇幅 | 典型读者（及其关切） | 定位 | 篇幅上浮/下沉信号 |
|------|----------|----------------------|------|-------------------|
| 轻量 | 1-2 屏 | 本模块开发者 / 一次评审（正确性、可维护性） | 说清做什么、怎么实现、取舍与风险 | 出现跨团队评审、SLA 承诺、不可逆变更 → 上浮到标准档 |
| 标准 | 2-5 屏 | 团队评审 + 上下游调用方（兼容与影响面、验收） | 完整方案 + 详细设计 + 计划 + 验收 | 出现多系统联动、成本敏感、合规审查 → 上浮到完整档 |
| 完整 | 长文（分章节阅读） | 架构评审委员会 / 跨团队 + 运维/安全/合规（部署、容量、安全、成本、回滚） | 全链路评估，含容量/安全/成本/回滚 | 只有单模块改动、无跨系统影响 → 下沉，避免过度设计 |

> 读者决定**哪些关切必须有承载**（见「通用约定」第 8 条）；拿不准时按最严格的读者补。
>
> 场景与档位的常配关系（如 S3 结构重构常配标准/完整档）见 `scenarios.md` 速览表，不要从篇幅反推场景。

## 轻量档

适用：单个功能模块、小型优化、简单集成。只回答「背景、思路、取舍、怎么落、有什么风险」，默认**不写**成本/容灾/压测/可观测等企业级章节。

```markdown
# [主题]技术方案

> 状态：草案待评 ｜ 作者：… ｜ 评审人：… ｜ 拍板人：… ｜ 最后更新：YYYY-MM-DD

## 背景与目标
### 现状与问题
### 目标与非目标
### 假设与约束（有未确认项时）
### 验收标准

## 核心设计
### 设计思路
### 备选与取舍
### 技术选型
### 数据模型（如适用）
### 实现要点
### 验证与回归

## 实施计划
### 实施步骤
### 时间估算

## 风险与应对
### 主要风险
### 应对措施

## 待确认问题（有 `[待澄清]` 时必须写）

## 已知未覆盖

## 附录（如适用）
### 数据模型 DDL
```

**各节必答项**（✗ 标常见不合格写法）：

| 章节 | 必须回答 |
|------|----------|
| 现状与问题 | 当前怎么做、痛点具体在哪（**带证据锚点**）。**按落点**：A 整节改为「外部环境与集成点」，B 改为「宿主约束与遵从/偏离」，C 保留本节（见 `scenarios.md` 落点义务增量）｜✗「现状有待优化」 |
| 目标与非目标 | 业务目标 + 技术目标 + 收益口径（见「通用约定」9）；非目标 ≥1 条并给原因；**反目标 ≥1 条**：技术上全部达标但业务上仍算失败的情形（如客诉翻倍、成本反升、运营反而更不敢改规则）｜✗ 只写目标；✗ 把反目标写成非目标的同义词 |
| 假设与约束 | 硬约束（技术栈/部署/合规/排期）+ 我替你定的默认值（`[假设]`）+ 取不到的事实（`[待核实]`），一行一条并写不成立时的后果｜✗ 把假设埋在正文里不声明 |
| 验收标准 | 上线后如何衡量 + **怎么验**（谁验、方法、阈值）；有指标影响时必须给指标与口径｜✗「提升用户体验」；✗ 有指标影响却只写「评审通过即可」 |
| 待确认问题 | 需人拍板的 `[待澄清]` 各给默认倾向 + 拍板人｜✗ 只列问题不给倾向 |
| 已知未覆盖 | **明确知道、但本期不解**的缺口：每条给「为什么现在不解决 + 谁在什么条件下解决 + 被撞上会怎样」。真没有就写「无」｜✗ 只有待确认问题、没有已知缺口（假装想全了）|
| 设计思路 | 一句话能复述的核心做法｜✗ 只堆技术名词 |
| 备选与取舍 | ≥2 种做法（含「不做/维持现状」）+ 为何不选更重/更轻的那个；差异只在参数或命名上视为未做备选｜✗ 单一方案 |
| 技术选型 | 评估维度与 must-have 门槛 + 1-2 句取舍理由 + 代价｜✗ 只写选了什么 |
| 数据模型（如适用） | 领域实体与生命周期；正文**三张表**（实体清单 / 字段 / 索引与查询匹配）+ **简版 ER 图**；DDL 只放附录（`data-model.md`）｜✗ 正文只贴一段 `CREATE TABLE`；✗ 只列字段不说索引服务哪条查询 |
| 实现要点 | 核心步骤或最小示例（代码原则见 `quality-bar.md`）｜✗ 贴整段实现 |
| 验证与回归 | 怎么证明它对（方法 + 阈值）＋这次改动可能破坏什么（回归范围）｜✗ 只写「验收通过」 |
| 实施步骤 / 时间估算 | 步骤可独立验证；工期给区间 + 假设｜✗ 单点工期无假设 |
| 主要风险 / 应对措施 | 触发条件 + 动作（含回滚/降级）；有遗留技术债时一并写；**方案沉默清单**：本方案没提、但上线后一定会遇到、遇到就出事的 ≤5 类输入或故障模式（如「用户注销后积分怎么算」「跨年批次算谁的」）——方案没写不代表不会来｜✗「加强监控」；✗ 只列已知风险，不列方案没覆盖的输入 |
| 附录（如适用） | 有表结构时给**数据模型 DDL**：可直接执行，字段名/类型/可空/默认值/索引与正文表格一致｜✗ 正文与附录两处字段对不上 |

适用：子系统、中型业务模块。在轻量档基础上补「现状痛点、约束与验收、总体方案、详细设计、验证与验收、里程碑、备选方案否决记录」。

**各节必答项**：

| 章节 | 必须回答 |
|------|----------|
| 系统上下文与边界 | 外部系统/依赖方/上下游与数据流向（一张 context 图或 3–5 行表）+ **边界外明确不负责什么**；落点 A 即「外部环境与集成点」，落点 B 即「宿主与我的边界、宿主约束」｜✗ 只画架构图不说边界，评审时范围各说各话 |
| 业务背景与现状 | 现状能力与数据流（**带证据锚点**）。**按落点**：A 改为「外部环境与集成点」，B 改为「宿主约束与遵从/偏离」，C 保留本节｜✗ 复述需求 |
| 痛点分析 | 痛点落到具体场景与频次，不是形容词，并给出证据｜✗「效率低」 |
| 目标与非目标 | 业务目标（底线）+ 技术目标（可衡量）+ 收益口径；非目标写成「超出范畴的用例」并给原因；**反目标**：技术上全部达标、业务上仍算失败的判据（越过即回滚或重做） |
| 约束与非功能需求 | 性能/可用性/一致性/安全/合规的量化目标；可用性给端到端口径 + 串联预算；落点 B 另加**宿主约束**；另起一小节收 `[假设]` 与 `[待核实]`（取不到的现状），写清不成立时怎么办（`quantification.md`） |
| 验收标准 | 量化指标 + 口径 + 验证方式 + 责任方 |
| 总体思路 | 一段话讲清方案主干与关键取舍 |
| 总体架构 | 架构图（按 `quality-bar.md` 选型：结构类走 SVG，时序/线性小图用 Mermaid）+ 职责表；给部署形态（一句或一张图） |
| 核心流程 | 关键路径的时序或步骤，含异常分支；**跨方交互必须给时序图**（Mermaid `sequenceDiagram`），一段话描述多方时序视为未完成 |
| 备选方案与取舍 | 自研/改造/引入现成/分阶段/**不做**，各写代价与否决理由 |
| 技术选型与理由 | 评估维度 + must-have 门槛 + 组件级 2-3 方案：适用场景、代价、什么情况下不该选 |
| 决策与需求对照 | 一张表：决策 ID / 决策（Y-statement）/ 承接需求 / 备选（含不做）/ 验证手段 / 状态 / 置信度；每行回指需求编号，无孤儿决策、无未覆盖需求｜✗ 只有散文「我们决定…」 |
| 模块划分与职责 | 职责不重叠 + **数据所有权归属** |
| 接口设计 | 接口清单 + 错误码 + 鉴权 + 幂等（`focus-areas.md` API 专题） |
| 数据模型 | **领域实体、关系与生命周期**（有状态流转时配状态图）；正文用**三张表**承载（实体清单 / 字段 / 索引与查询匹配）+ **简版 ER 图**（只含实体、主键与关系基数）；每条索引回指一条具体查询；**DDL 只出现在附录**并与正文表格逐项一致（`data-model.md`）｜✗ 正文贴 `CREATE TABLE`；✗ 只列索引不说它服务哪条查询 |
| 关键逻辑与算法 | 按需保留；给边界条件与失败处理 |
| 验证与验收 | 验证手段按场景裁剪（单测/集成/契约测试、数据对账、灰度对比、回滚演练）；**最脆弱假设**（错了要重做的那个）+ 最便宜的证伪实验 + 不成立时的 Plan B；上线后观察指标、观察期与回滚触发阈值。压测方案归「性能与容量设计」，此处引用不重复 |
| 阶段与里程碑 | 每阶段可独立上线；**第一阶段是端到端最小闭环或去风险 spike**，不是并行搭基础设施 |
| 资源需求 / 时间估算 | 区间 + 假设（人力、依赖变化时如何调整） |
| 技术/业务风险 + 应对措施 | 触发条件 + 动作 + 验证，含降级与回滚；**技术债**另列：本次偿还什么、又留下什么；**方案沉默清单**（≤5 类）：方案未提及但一定会遇到、遇到就出事的输入/状态/故障，每条给「遇到时的默认行为 + 由谁确认」 |
| 待确认与开放问题 | 分三类收口：拍板 / 实现中 / 范围外 |
| 已知未覆盖 | 本期明确不做但已确认知道的缺口（活动元数据归属、风控接入、入口改造、回滚回写这类）；每条给「为什么现在不解决 + 谁在什么条件下解决 + 被撞上会怎样」 |
| 附录 | **数据模型 DDL**（有表结构时必给：可直接执行，是唯一可执行真源，`data-model.md`）+ 参考资料与术语；术语首现给中文释义 |

## 完整档

适用：系统架构、跨系统集成、技术重构、大型平台。在标准档基础上展开摘要、系统上下文、部署与资源拓扑、验证与验收、成本、决策记录等企业级章节。**备选与选型对比属于策略层论证，排在详细技术设计之前**（对齐 arc42 的「解决策略 → 构建块」与 Google 的「先讲设计再列备选」：策略层先论证，细节层后展开）。

**在标准档必答项之上，另加**：

| 章节 | 必须回答 |
|------|----------|
| 摘要 | 结论 + 核心取舍 + 量化目标 + 主要风险 + 需谁拍板（一页） |
| 读者与关切 | 3–5 行表：**谁**（角色）+ **关心什么**（兼容/容量/安全/成本/交付）+ **在哪一节得到回答**；与「关切承载」互相验证；单人评审的小方案删本节 |
| 痛点与动因 | 动因可追溯到业务或指标，不是「技术债」一句带过 |
| 约束与非功能需求 | 含**兼容约束**；可用性给端到端目标 + 串联预算表；另起小节收 `[假设]` 与 `[待核实]` 并写不成立时的应对 |
| 架构设计原则 | 每条原则能对应到后文的具体取舍 |
| 系统上下文与依赖 | 外部系统/依赖方/数据来源与去向，配 context 图（结构类走 SVG） |
| 系统边界与职责 | 边界外的事明确不负责；数据所有权归属 |
| 数据流转 | 关键数据从产生到消费的完整路径 |
| 部署与资源拓扑 | 环境（开发/预发/生产）、实例与副本、机房或可用区、依赖组件（DB/缓存/MQ/外部服务）的部署位置与网络通路；与容量规划对应 |
| 数据模型 | 同标准档的三张表 + 简版 ER 图 + 附录 DDL；实体 ≥12 或关系交叉多时 ER 图升 **SVG**（`data-model.md`） |
| 存储设计 | 与「数据模型」**分工**：数据模型管实体/字段/索引与 DDL（附录），存储设计管引擎与存储选型、分区/冷热分层、归档与容量水位、一致性要求（`quantification.md`） |
| 缓存设计 | 失效策略 + 穿透/雪崩防护 + 一致性代价 |
| 消息与异步 | 按需保留；投递语义、幂等、积压与重试 |
| 选型风险与回退路径 | 选错的代价与回退成本 |
| 性能目标与基线 | 按 `quantification.md` 给推导与口径 |
| 容量规划 | 规划期总量 + 扩容触发阈值 |
| 优化策略 | 每项：预期收益 + 代价 + 回退开关 |
| 压测方案 | 场景、数据量、通过判据 |
| 安全设计 | 资产与信任边界、越权防护、日志脱敏（`focus-areas.md` 安全专题） |
| 可观测性设计 | 指标 + 阈值 + 告警触达；日志脱敏；链路追踪采样；给「告警 → 处置动作」对应表，值班接手人能照做 |
| 验证与验收 | 同标准档，另加：回滚演练、故障注入范围、压测通过判据（引用「性能与容量设计」）；上线后观察期与责任人 |
| 发布计划 | 灰度/分批/开关，每步给进入与退出判据 |
| 兼容性与数据迁移 | **场景决定**：S1 删；S2 兼容期与数据兼容；S3/S4 迁移阶段 + 对账 + 回退窗口（`scenarios.md`） |
| 回滚方案 | 触发条件 + 步骤 + 回滚后验证 + 是否可逆；不可逆动作需审批 |
| 成本分析 | 单价 × 用量 + 计费口径，给区间；与收益口径对应 |
| 技术债 | 本次偿还了什么债、又留下什么债（给偿还触发条件与时间点），与风险并列 |
| 开放问题与后续工作 | 分三类收口：拍板 / 实现中 / 范围外独立做 |
| 已知未覆盖 | 本期明确不做、但已确认知道的缺口；每条给「为什么现在不解决 + 谁在什么条件下解决 + 被撞上会怎样」 |
| 决策记录（ADR） | **用追溯表承载**（决策 ID / 决策 / 承接需求 / 备选含不做 / 验证手段 / 状态 / 置信度），ADR 的「备选 + 理由 + 状态 + 置信度」是表的列而不是散文；无孤儿决策、无未覆盖需求｜✗ 一段段「我们决定…」 |
| 附录 | 参考资料与术语说明 + **数据模型 DDL**（唯一可执行真源，与正文表格逐项一致）；决策记录不放假附录，必须与开放问题同处（上一节） |

> 完整档不内嵌「评审检查清单」章节：清单为单一真源，统一在 `quality-bar.md`，收尾时按场景与档位生成。

## 对齐的主流模板（维护备注）

- **Google Design Doc**：Context and scope / Goals / Non-goals（非目标 = 本可以做但明确不做）/ The actual design / Alternatives considered（作者视其为最重要的小节之一）/ Cross-cutting concerns（安全、隐私、可观测）——本文的「超范围表述」「备选与取舍」「关切承载」取自这里。
  - **Context and scope 前置**：Google 把它放在 Goals **之前**；本文标准/完整档照此把「系统上下文与边界」排在目标与方案之前（范围内外不清，后面的取舍都无从判断）。
  - **Degree of constraint**（约束程度决定文档重心：绿地项目要快速收敛解空间，受约束系统要在既定选项里选最优）：本文**不设独立章节**，用「落点 A/B/C + 场景」这一对轴等价表达——落点已覆盖「有多少自由度」。
  - **体量甜点区**：Google 给大型项目 10–20 页、小改进 1–3 页；本文三档的「1-2 / 2-5 / 长文」即按此分档，并加「超过 ~20 屏就拆总纲 + 子方案」的红线。
  - **散文优先**：Google 强调文档是"unstructured text"，代码/伪代码只在描述新算法时出现；本文的「散文优先」「代码片段原则」取自这里。
- **arc42**：目标与质量目标 → 约束 → 上下文与范围 → 解决策略 → 构建块 → 运行时 → 部署 → 横切概念 → 架构决策 → 质量要求 → 风险与技术债 → 术语。本文的「叙事链」顺序依赖与「部署与资源拓扑」「技术债」取自这里；完整档的「读者与关切」对应 arc42 §1.3 的利益相关者表，质量要求（quality tree / quality scenarios）对应本文「量化目标 + 验收阈值」而非另设质量树。
- **ISO/IEC/IEEE 42010**：stakeholder → concern → viewpoint → view；rationale 必须记录被否决的备选；correspondences（一致性、可追溯性、依赖、约束、义务）。本文的「关切承载」「追溯链」取自这里。
- **4+1 视图**：逻辑（类图 + 状态图，即实体生命周期）→ 进程 → 开发 → 物理（部署）+ 场景串联——本文「先实体后表结构」「部署视图」的出处。
- **ADR / MADR**：「结论 + 备选 + 理由 + 状态 + 置信度」；Y-statement 句式（`quality-bar.md` 论证充分性）。MADR 明确「被考虑过的选项及其利弊至关重要」。**有意偏离**：ADR 主流做法是每决策一个独立文件，本文改为**内嵌一张追溯表**——评审要在一屏内看到「需求 ↔ 决策 ↔ 验证」的对齐，散成 N 个文件反而看不出缺口；需要长期沉淀时再把行导出为独立 ADR。
- **Rust RFC 模板**：Motivation 先行、Unresolved questions 分类收口。
- **Amazon PR/FAQ**：从期望结果倒推（先写新闻稿再写 FAQ）——对应本文的「为什么现在做」与收益口径。
- **国内方案评审惯例**：验收标准、发布/灰度/回滚、排期与资源显式化，业务目标与技术目标二分并写清收益。
