# 质量红线（quality-bar）

撰写全程遵守。分六块：图、代码、论证、反模式、评审清单、语言。

## 图规范（写图前必读）

### 先选工具，再选类型

**Mermaid 与 SVG 都是一等公民**，按图的**职责**选，不是按习惯选；**同一张图只产出一种形式**（不做双份）。

| 图的职责 | 工具 | 为什么 |
|----------|------|--------|
| 结构类：架构拓扑、分层、部署与资源拓扑、系统边界与数据所有权 | **SVG** | 位置本身即论据（谁在底层、谁在入口、边界在哪）；Mermaid 自动布局不认这类语义，且加一个节点全图重排，破坏结构图应有的稳定性 |
| 映射类：二部图、多对多映射、需靠重排两侧节点消除交叉线 | **SVG** | 同上 |
| 对比类：方案 A vs B、旧 vs 新（左右并列、需同构对齐） | **SVG** | 对齐关系本身承载语义 |
| 状态机 / 生命周期（回边多） | **SVG**（回边少可用 `stateDiagram-v2`） | 自动布局会把回边绕远、标签压在连线上 |
| 时序/交互 | **Mermaid**（`sequenceDiagram`） | Mermaid 强项，**不要**升级为 SVG |
| 真·线性小流程（≤8 节点、无交叉）、简单拓扑 | **Mermaid** | 纯文本、可 diff |

**命中任一条即改用 SVG**：节点数 **≥12**；含**分叉 / 汇合 / 回边 / 泳道 / 分区**；一张图要表达「接入—服务—领域—资源」这类**纵向层次**。

**SVG 产出走 `svg-maker` skill**（软件/基础设施拓扑用 `architecture-svg`，概念/流程/生命周期用 `clean-svg`），**不要自绘样式规范**——那会与既有图产生风格漂移。当前环境没有 `svg-maker` 时先说明，再退回自绘并守住下方约束。

### Mermaid 类型映射

| 用途 | Mermaid 类型 |
|------|--------------|
| 架构/调用链概览（简单、≤8 节点） | `flowchart TB`（或 BT/LR/RL） |
| 时序/交互 | `sequenceDiagram` |
| 数据模型/ER（**简版**：实体 + 主键 + 关系基数，不画全字段） | `erDiagram` |
| 类/领域关系 | `classDiagram` |
| 状态与流转（回边少） | `stateDiagram-v2` |

### Mermaid 语法方向（最容易写错的一条）

Mermaid 语法是 `节点ID[展示文本]`——**方括号里是展示文本，等号/定义左边才是 ID**：

```mermaid
flowchart LR
    client["客户端"] --> apiGateway["API 网关"]
    apiGateway --> userService["用户服务"]
```

规则：

- ID 用**语义化英文**（`client`、`apiGateway`、`orderDB`）；禁止无意义字母（`A`、`B`、`C`）、禁止中文 ID。
- 展示文本用中文可读，**一律用双引号包裹**（含中文标点或空格时不加引号会解析出错）。
- 首次出现完整定义 `id["展示"]`，后续引用只写 `id`（如 `client --> orderDB`）。
- **不要**用旧式反向写法 `客户端[client]`——它把中文当 ID、英文当展示文本，语义颠倒且部分预览器异常。参考旧示例时一律按本节改写。

### SVG 资产约束

- 落成**文档同目录的 `.svg` 资产**（英文语义名：`architecture.svg`、`data-flow.svg`；不加 `01-` 序号前缀），正文用相对路径引用。**不要内联进 Markdown**——边拓扑审计与预览只接受 `.svg` 文件。
- **自包含**：内联 CSS、零外部资源（无 `<image>` / 远程字体 / JS / 渐变），可离线双击打开。
- `<title>` 与 `<desc>` 齐备，且**都不带属性**（写 `<title>`，不写 `<title id="...">`——下游校验按标签名匹配，带属性会被判缺失）。
- 根元素**只写 `viewBox`**，不写 `width`/`height`；浅深色都要能读（`:root` 变量 + `prefers-color-scheme`）。
- 先画 connector 再画 node；盒内文字留 ≥24px 内边距；中文标点统一全角（`：`、`（）`）。
- **一处编号只写一次**：正文不写「图 N」，`<title>` 里也不写序号——正文一改结构编号就错位。

### 图必须被正文包裹

- **视图服务关切**：每个关切（安全/合规/运维/调用方/成本/可维护性）至少有一个视图或章节承载；反过来也不要画装饰图——说不出它支撑哪个关切的图删掉。
- 有生命周期/状态流转的实体应配状态图，与「数据模型」一节配对（实体先于表结构）。
- **ER 图是简版关系导航图**：只画实体、主键与关系基数，**不画全字段**——字段与索引由正文表格承载，精确形态由附录 DDL 承载；实体 ≥12、关系交叉多或需按模块分区时改 SVG（`data-model.md`）。
- 图能说清才放；同一文档**不超过 4-5 张**（Mermaid 与 SVG 合计），避免用图代替论证。
- **不引用远程/外链图片**（离线打不开、会失效、评审时看不见）；同目录 `.svg` 资产与内嵌 Mermaid 都可以。
- **图不被孤立**：图前有导读段（这张图是什么、为什么存在），图后有落着（该看什么、代价是什么）。
- 图必须与正文一致：图里出现的每个节点/组件，正文都要有解释；正文的关键路径必须能在图上找到。

### 校验（落盘前必过）

```bash
# 文档正文门禁：占位符/空壳章节/状态块/备选/追溯表/DDL 一致性
node <本skill目录>/scripts/check-design-doc.mjs <文档> --tier <light|standard|full> [--upstream <PRD>...]

# Mermaid：真解析（mermaid.parse）
node <本skill目录>/scripts/check-mermaid.mjs <生成文件>

# SVG：边拓扑审计——结构类图新画或重排后必跑
node <本skill目录>/scripts/audit-svg-topology.mjs [--expect 期望边清单.txt] [--strict] <图.svg>...

# SVG：目视预览（先把 var() 展平成字面色再出 PNG，避免误判「图坏了」）
node <本skill目录>/scripts/render-svg-preview.mjs [--out <dir>] [--width 1200] [--dark] <图.svg>...
```

- **文档门禁**：`error` 必须修完重跑；`warn` 逐条裁决（改掉，或在文档里显式豁免并写理由）；`note` 读一遍确认已收口。`--strict` 把 warn 也当失败（完整档建议加）。它只覆盖机械项，语义判断归 `review-gate.md`。
- 全部 `OK` → 通过；`[MERMAID-ERROR]` 或审计**退出码非 0** → **必须修复并重跑，不静默放过**；`[MERMAID-WARN]`（`<br>` 规范提示）、`[EDGE-GAP]`（6–40px 端点间隙，标签式箭头可能有意留白）为提示级。
- **边拓扑审计怎么用**：把设计里的期望连线逐条写进清单文件（每行 `起点 -> 终点`，`#` 起头为注释），用 `--expect` 断言。它逐条打印「起点节点 → 终点节点」，是**唯一能程序化发现「看着对、边连错」**的手段（缺边/多边/分支挂错节点，而标签全对、渲染不报错）。不一致就先别接进文档。
- **mermaid → SVG 转换必须等价**：节点标签、边的起止与分支标签逐一对应；转换后按上图跑审计，与原文清单对照。
- 三个脚本都是 `project-insight` 引擎的薄壳（单一真源，按自身位置相对定位）：`check-mermaid` 需 `skills/project-insight/scripts/` 已 `npm install`；审计与预览只用 node 内置模块，预览需本机有 `rsvg-convert`。
- **校验边界**：机器只校验「能否解析/渲染」「边是否贴合与齐全」，不校验 ID 语义化、引号、视图服务关切等约定——这些要人工过一遍。

## 代码片段原则

默认**不含代码**，仅在以下情况添加：用户明确要求示例；需要展示新架构模式的典型写法；API 方案需要接口定义/请求响应示例；核心算法需伪代码；**数据库 DDL——且只出现在附录的「数据模型 DDL」小节，正文一律不贴**（`data-model.md`）。

格式：标准 Markdown 代码块 + 语言标注 + 简洁中文注释。示例代表性优先，不要贴大段无关实现；**代码里的密钥、域名、内网地址一律用占位符**。

## 论证充分性

- **事实有据**：关于既有系统的论断（现状、影响面、调用方、容量水位）必须带证据锚点——`路径:行号`、监控面板与查询口径、工单/事故单号；取不到证据的标 `[待核实]` 并写成假设。不编现状。
- **量化义务**：涉及性能/容量/可用性/成本/**收益**的论断，按 `quantification.md` 给数字或区间 + 口径 + 假设来源；给不出就标为「待验证假设」并写清不成立时的应对。形容词（"高性能""海量"）不算论证。
- **取舍对偶**：每个选型给 ≥2 个方案（含**「不做/维持现状」**），并回答三问——为什么选它、代价是什么、**什么情况下不该选它**，且理由**回指它满足了哪条目标或约束**。只列优点或只给一个方案视为未完成；**两个方案的差异只体现在参数、命名或部署形态上，同样视为未完成**（换的是思路与代价，不是措辞）。
  - 句式（ADR 的 Y-statement，一句话交付取舍）：
    > 在〈场景〉下，面对〈关切〉，我们选择〈方案〉、放弃〈其它方案〉，以获得〈质量目标〉，接受〈代价〉，理由是〈依据〉。
- **因果与追溯**：**目标/约束 → 决策 → 验证手段 → 验收阈值**四者要对得上；决策理由不能与目标脱节。
- **可证伪**：关键论断要能被验证或推翻，写明验证方式（压测/灰度对比/指标观测）；**最脆弱假设**（错了要重做的那个）要有最便宜的证伪实验与不成立时的 Plan B。
- **风险与技术债**：风险应对具体到「触发条件 + 动作 + 责任方」，含降级与回滚预案，不写「加强监控」这类空话；技术债写清本次偿还什么、又留下什么（含偿还触发条件）。
- **实施计划**：给时间区间并注明假设（人力、依赖、排期变化时的调整方式）；里程碑要能独立交付，**第一阶段是端到端最小闭环或去风险 spike**。

## 反模式（出现即返工）

| 反模式 | 症状 | 改法 |
|--------|------|------|
| 形容词化 | 「高性能」「海量数据」「高可用」 | 换成量化目标 + 口径（`quantification.md`） |
| 单边选型 | 只给一个方案或只写优点 | 补 ≥2 方案（含不做）+ 代价 + 不该选的场景 |
| 备选换皮 | 三个方案差异只在参数/命名/部署形态 | 按四个约束视角（最小改动/最大扩展/最常见调用方/最小运维）各自独立推演（`templates.md`） |
| 要点堆砌 | 整节都是 bullet，找不到一句完整论证 | 论证改散文；列表只留可枚举项（见「语言与可读性」） |
| 纯文字架构 | 有架构/流程/数据模型章节，却一张图没有 | 补「系统上下文」图 + 「关键流程」时序图；结构关系用文字写，评审只能在脑内连线 |
| 追溯缺表 | 决策散在正文，说不出它承接了哪条需求 | 补「决策与需求对照表」，并把需求编号对到上游（`templates.md`） |
| 事实无据 | 「现状大概是…」没有任何证据锚点 | 补证据（`路径:行号`/监控口径/工单）或标 `[待核实]` 并写成假设 |
| 宿主无约束 | 在既有系统里插模块，却不写宿主技术栈/容量/发布/权限约束 | 补宿主约束与遵从/偏离理由（`scenarios.md` 落点 B） |
| 目标无收益 | 只有技术目标，不写业务目标与收益 | 业务目标（底线）+ 技术目标（可衡量）+ 收益口径 |
| 决策无因果 | 只比优劣，不说它满足了哪条目标/约束 | 回指目标或约束，用 Y-statement 收口 |
| 关切失守 | 安全/合规/运维/调用方关切全篇无人承载 | 按读者 × 关切反查，补章节或视图 |
| 验证缺位 | 只写验收阈值，不写怎么测、谁测、假设怎么证伪 | 补验证手段 + 最脆弱假设的证伪实验 |
| 图选型不当 | 分层/拓扑/对比硬用 Mermaid（加个节点全图重排），或同一张图 Mermaid + SVG 双份 | 按本节选型规则改用 SVG（`svg-maker`），同一张图只留一种形式 |
| 图是插图 | 只放一张图的小节，图前无导读、图后无落着 | 补导读段与落着，或并入正文论证 |
| 边连错未发现 | SVG 结构图看着对、边错（缺边/多边/挂错节点） | 写期望边清单，跑 `audit-svg-topology.mjs --expect` |
| 章节空壳 | 章节齐全但每节一句话、"N/A" 占位 | 删掉不适用章节，其余写实 |
| 图话两说 | 图里有正文没解释的组件，或正文流程图上没有 | 图与正文互相补齐 |
| 空话风控 | 「加强监控」「做好兜底」 | 触发条件 + 动作 + 回滚步骤 |
| 不可验收 | 「提升用户体验」「性能明显改善」 | 给可测指标 + 验证方式 + 责任方 |
| 逃逸不确定性 | 把待定项写成「后续再定」散在正文 | 集中到「开放问题」并标默认倾向 |
| 过度设计 | 小需求套成本/容灾/压测全套 | 下浮档位（`templates.md`） |
| 假设隐身 | 用了未申明的假设（如"假设用户都在同一机房"） | 显式写进「假设与约束」，标待确认 |
| 改动无影响面 | 改既有接口/表，却不写谁在调用、哪些行为会变 | 补影响面盘点 + 兼容策略（`scenarios.md` S2） |
| 重构无等价性验证 | 只写「结构更清晰」，没有行为基线、双跑或差异处理规则 | 补行为基线与等价性验证方案（`scenarios.md` S3） |
| 下线无消费者盘点 | 凭「搜代码没有引用」就删接口/服务/表 | 补消费者盘点 + 下线判据 + 数据处置（`scenarios.md` S5） |
| 优化无基线 | 直接给优化方案，不写现状指标与口径 | 先给基线、目标与测量方法（`scenarios.md` S6） |
| 表结构只有 DDL | 正文贴一大段 `CREATE TABLE`，没有设计论证、没有查询匹配 | 正文改为实体清单/字段/索引三张表 + 简版 ER 图，DDL 收进附录（`data-model.md`） |
| 表格与 DDL 两说 | 字段表改了、附录 DDL 没改（或反之），评审不知以哪份为准 | 声明附录 DDL 为唯一可执行真源，落盘前逐项核对字段名/类型/可空/默认值/索引 |

## 评审检查清单（单一真源）

**唯一清单来源在本节。** 模板不内嵌清单；收尾时按下表取子集，再叠加 `scenarios.md` 对应场景的过程义务与 `focus-areas.md` 对应专题的必答项，生成在文末「评审检查清单」小节或口头收口。

| 档位 | 取用方式 |
|------|----------|
| 轻量 | 先按场景挑相关类目（无关类目跳过），每类 1 条，合计 5-8 条 |
| 标准 | 按场景挑相关类目，每类 2-3 条 |
| 完整 | 全量 + 场景义务项 + 专题必答项 |

- **目标与范围**：目标可衡量（业务/技术二分）+ 收益有口径；非目标（超出范畴的用例）已显式列出并给原因；范围与档位匹配，无过度设计。
- **架构合理性**：模块划分清晰、职责与数据所有权不重叠；系统边界明确；无未说明的单点故障；**实体与生命周期有承载**；含部署形态的方案给了部署与资源拓扑。
- **数据模型**：领域实体与生命周期先于表结构；正文以**三张表**承载设计（实体清单含所有权与量级 / 字段含业务口径 / 索引含所服务的查询，每条索引能回指一条查询）；有**简版 ER 图**且与实体清单表一致；**DDL 只在附录**并与正文表格逐项一致；存储量有推导（`data-model.md`）。
- **影响面与兼容**：改动类文档已盘点调用方与受影响行为；**落点义务已落实**（宿主新模块写了宿主约束与对宿主的影响，既有模块写了影响面与回归范围）；契约与数据兼容策略明确；共存期与下线判据清晰。
- **事实与证据**：关于既有系统的现状/影响面/调用方/容量水位都有证据锚点，未取证的已标 `[待核实]`。
- **量化与容量**：性能/容量/可用性目标有推导与口径；容量规划含规划期总量与扩容阈值；缓存策略覆盖读写路径与失效。
- **回归与等价性**：改动类给了回归范围；结构重构给了行为基线、等价性验证与差异容忍度；专项优化给了回归清单。
- **验证与追溯**：**目标/约束 → 决策 → 验证手段 → 验收阈值**由「决策与需求对照表」逐行落地（无孤儿决策、无未覆盖需求，编号能对上游）；最脆弱假设有证伪实验与 Plan B；上线后有观察指标与回滚触发阈值。
- **图与工具选型**：图按职责选了工具（结构/映射/对比/回边状态机 → SVG；时序/线性小图 → Mermaid），无同图双份；图前有导读、图后有落着；SVG 跑过边拓扑审计，Mermaid 跑过解析校验。
- **安全**：认证授权机制明确；数据加密与密钥管理；越权防护；敏感数据与日志脱敏。
- **可维护与可观测**：监控/日志/链路方案到位（完整档）；接手人能独立读懂；关键决策有记录（ADR）。
- **决策与留痕**：文档带状态块与拍板人；决策记录含备选、理由、状态与置信度。
- **迁移与回滚**：数据迁移与兼容期有方案；回滚触发条件与步骤可执行；不可逆动作有审批与检查项，回退窗口已说明。
- **测试与验收**：验收标准可验证（谁验、怎么验、阈值）；关键路径有测试策略（单测/集成/压测/灰度对比）。
- **风险控制**：主要风险已识别且应对可行；技术债有偿还计划；假设与不确定性显式化。

## 语言与可读性

- 全文**简体中文**；技术术语保留英文（API、RPC、Kafka），首现给中文释义。
- 语义式标题层级；章节长度与信息量匹配；重要结论加粗。
- **散文优先**：论证必须写成完整句子——「因为约束 X，选 Y，代价是 Z」。**列表只用于可枚举集合**（依赖、组件、术语、检查项、参数表）；把取舍写成两行 bullet，等于让读者自己补推理，评审时也点不出问题在哪。
- **表格只用于对齐**：横向比较（方案 × 维度）、追溯（决策 × 需求）、清单（字段 × 类型）用表；叙述与因果用段。
- **论证顺序可复述**：读完应能按「为什么 → 问题 → 约束 → 方案 → 理由 → 落地」把文档讲一遍；做不到说明推理链断了。
- 论证充分但克制：每节回答「为什么」而不是堆砌内容；非技术人员也能读懂核心思路。
