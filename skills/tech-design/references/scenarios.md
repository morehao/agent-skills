# 变更场景（scenarios）

场景是**单选轴**，决定文档的**过程义务**：有没有现状可写、要不要兼容、怎么迁移、怎么证明没改坏、怎么回滚。

判定场景前先答**第 0 问·落点**（新系统 / 既有系统的新模块 / 既有系统的既有模块）——落点决定**取证对象与义务增量**（现状写什么、必须谁签），与变更性质正交。

三轴分工（互不打架，冲突时按最后一列）：

| 轴 | 作用域 | 冲突时 |
|----|--------|--------|
| 档位（`templates.md`） | 篇幅、评审范围、读者 | — |
| 专题（`focus-areas.md`） | 技术领域加固点（架构/API/数据/性能/安全） | 技术内容听专题 |
| **场景（本文）** | 落点（第 0 问）+ 变更性质；过程义务 + 按场景增删章节 | 过程内容与章节增删听场景 |

场景**不改变**档位，也**不放宽**量化义务、取舍对偶、事实有据、宁轻勿重（SKILL.md 顶层四条硬要求始终有效）。

## 判定

**第 0 问·落点**（决定取证对象与义务增量）：

| 落点 | 判定 | 取证对象（必须有证据锚点） |
|------|------|----------------------------|
| A 新系统 | 本系统无存量，从零设计新系统/服务/模块 | 外部邻居与上下游、可复用的既有能力、部署与运行规范 |
| B 既有系统的新模块 | 有宿主，改动以「加法」为主 | 宿主架构与运行规范、容量水位、发布节奏、依赖与共享组件版本、权限与监控接入、数据所有权边界 |
| C 既有系统的既有模块 | 改既有实现或契约 | 模块代码与数据流、调用方与调用量、契约消费方版本分布、历史事故与工单、数据规模 |

**第 1 问·变更性质**（按序回答，命中即停）：

1. 是否**移除**既有能力（接口/服务/表/字段/功能）？→ 是：**S5 下线与废弃**
2. 是否存在**在跑的存量**？→ 否：**S1 新建**
3. 有存量时，**外部可观察行为是否改变**？
   - 改变（新增或改动功能/接口/契约）→ **S2 增量改造**
   - 不变，但内部结构与部署形态变 → **S3 结构重构**
   - 载体（存储/中间件/框架/供应商）变 → **S4 替换与迁移**
   - 不变、结构也不变，只冲指标 → **S6 专项优化**

## 落点义务增量

落点与场景**正交**：落点定「现状写什么、要问谁」，场景定「变更过程要走哪些步」，义务取并集。以下增量叠加在场景义务包之上。

### A 新系统

- **现状类章节**：删「现状与问题」「痛点分析」等自身现状；但**保留外部环境盘点**——集成点、上下游、平台与运行规范。
- **义务增量**：集成点（谁调用它、它调用谁、数据从哪来）+ MVP 边界与分期 + 可复用既有能力盘点（别重复造轮子）。
- **验收增项**：自身功能与指标达标（用目标值，没有基线可比）。
- **回滚形态**：版本回退 / 功能开关 / 环境重建。
- **必须谁签**：平台或合规 owner（涉及部署环境、合规边界时）。

### B 既有系统的新模块

- **现状类章节**：**「现状与问题」换成「宿主约束与遵从/偏离」**——不是没有现状可写，而是写的是宿主的现状。
- **义务增量**：
  - **宿主约束**：技术栈与框架版本、编码与发布规范、容量水位与配额、依赖与共享组件版本、权限模型、监控/日志接入方式、数据所有权边界（谁的库、谁的表）。
  - **对宿主的影响**：资源占用（连接池/线程池/内存/带宽）、延迟与吞吐叠加、发布耦合（能否独立发布）、告警噪声。
  - **模块边界与数据所有权**：职责不重叠，谁能写、谁只能读。
  - **退出路径**：将来如何摘除（开关、入口、数据处置）。
- **验收增项**：自身达标 **+** 宿主不被拖累（延迟/容量/发布耦合/告警）。
- **回滚形态**：摘除模块与入口 + 撤数据；宿主侧改动要能单独回退。
- **必须谁签**：宿主 owner。

### C 既有系统的既有模块

- **现状类章节**：保留「现状与问题」，且**必须带证据**——当前怎么做、痛点在哪个场景、多频繁、数据流与调用方。
- **义务增量**：影响面盘点 + 兼容性策略 + 回归范围；**对外行为不变时升级为 S3 的行为基线与等价性验证**。
- **验收增项**：达标 **+** 不回归（回归清单或用例范围）。
- **回滚形态**：开关关停 / 版本回退；注意已按新格式落库的数据旧版本是否可读（不可读则回滚必须含数据修补，或改为前滚）。
- **必须谁签**：调用方 owner。

> 落点决定「必须谁签」与「现状写什么」，落进文档状态块（见 `templates.md` 通用约定）。

## 组合规则

- 主场景**单选**；同时命中多个（如「拆服务 + 换存储」= S3 + S4）时，取**风险更高、过程更长**者为主场景，另一场景的必答项作为**补充义务**并入，章节增删以主场景为准。
- 落点与场景**正交**：A + S1；B + S1/S2/S3（新模块，或把宿主里的一块拆出来）；C + S2/S3/S4/S5/S6。落点只加义务，不换场景。
- 场景与档位独立：模块级重构 = S3 + 标准档；项目级重构 = S3 + 完整档。
- 场景与专题独立：加缓存 = S6 + 性能与容量；对象存储替换 = S4 + 数据模型设计。

## 场景速览

| 场景 | 一句话判定 | 常见落点 | 常配档位 | 核心义务 |
|------|------------|----------|----------|----------|
| S1 新建 | 从零做，无存量 | A（宿主内新模块为 B） | 标准/完整 | 集成点 + MVP 边界；删自体现状章节 |
| S2 增量改造 | 改或加既有功能，行为变 | B（新增模块）/ C（改既有） | 轻量/标准 | 影响面盘点 + 兼容性 + 回归范围 |
| S3 结构重构 | 结构变，行为应不变 | C（从宿主拆出时为 B） | 标准/完整 | 行为基线 + 等价性验证 + 切流回滚 |
| S4 替换与迁移 | 换载体，数据要搬家 | C | 标准/完整 | 能力差异清单 + 对账 + 回退窗口 |
| S5 下线与废弃 | 移除既有能力 | C | 轻量/标准 | 消费者盘点 + 下线判据 + 数据处置 |
| S6 专项优化 | 结构不变，只冲指标 | C（宿主公共设施为 B） | 轻量/标准 | 指标基线 + 回归范围 + 收益代价 |

## S1 新建

- **判定**：从零设计新系统/服务/模块，当前无可运行的旧实现；含 POC/试点型（目标是验证可行性）。落点通常为 A；落在宿主内（B）时按「落点义务增量」补宿主约束。
- **必答项**：
  - 目标与非目标（非目标 = 范围收敛：本期不做哪些能力）。
  - 约束（技术栈/部署/合规/预算）与量化目标。
  - **集成点**：谁调用它、它调用谁、数据从哪来——新系统不等于没有邻居。
  - MVP 边界与后续分期，每期可独立上线。
  - **验证手段**：功能用例 + 指标实测（有指标影响时给压测或对比口径）。
- **章节增删**：删「现状与问题」「痛点分析」「兼容性与数据迁移」「迁移与切流」；落点为宿主内新模块（B）时，改为「宿主约束与遵从/偏离」（见「落点义务增量」）。
- **验收**：新能力的功能与指标**达标**（用目标值，不用改善幅度——没有基线可比）。
- **回滚**：版本回退 / 功能开关 / 环境重建，一句话即可。
- **非目标**：范围收敛（本期不做 X）。
- **常见漏项**：忘写集成点与上下游依赖；用「提升 30%」这类改善型指标却没有基线；POC 型没写「验证结论如何判定、是否推广」；落点 B 时忘写宿主约束（技术栈/容量/发布节奏/权限与监控接入）。

## S2 增量改造

- **判定**：既有系统上新增模块（落点 B），**或**修改既有功能/接口/表（落点 C）；旧实现继续存在。
- **必答项**：
  - 现状与痛点：当前怎么做、**为什么现在必须改**。
  - **影响面盘点**：谁在调用（上下游/消费者/客户端版本）、哪些数据与字段受影响、哪些既有行为会变。
  - **兼容性策略**：共存期与向后兼容、数据兼容（旧数据能否被新逻辑读、新写入能否被旧版本读）、灰度与开关。
  - **回归范围**：这次改动可能破坏哪些既有功能，怎么验证没坏。
  - **验证手段**：新增行为用功能用例/契约测试；改动既有用回归用例范围 + 新旧版本互读（兼容性）验证。
  - 非目标显式圈出**本次不动的旧行为与遗留问题**。
- **章节增删**：保留「现状与痛点」；**加「影响面与兼容性」（所有档位，轻量档可缩为 2-3 行）**；**加「回归与验证范围」**；落点 B 另加「宿主约束与遵从/偏离」。
- **验收**：新行为指标达标 **+** 既有行为不回归（给回归清单或用例范围）；落点 B 另加「宿主不被拖累」。
- **回滚**：开关关停 / 版本回退；关键是**已按新格式写入的数据旧版本是否可读**——不可读则回滚必须含数据修补，或改为前滚。
- **非目标**：范围收敛 + 本次不动的旧行为。
- **常见漏项**：只写「新增」而忽略改动带来的既有行为变化；没有调用方盘点就敢改契约；回滚没考虑数据已按新格式落库。
- **注意**：「新增模块」（落点 B）看集成点与**宿主约束**；「改动既有」（落点 C）看影响面与回归范围——两类义务侧重不同，按实际形态取用（见「落点义务增量」）。

## S3 结构重构

- **判定**：模块拆分或合并、分层调整、单体拆微服务、服务边界重划；目标是结构更好，外部行为应保持不变。落点通常为 C；把宿主里一块拆出来成为新模块时同时带 B 的义务。
- **必答项**：
  - **行为基线**：重构前的外部可观察行为（接口契约、关键流程输出、指标基线）——没有基线就无法证明没改坏。
  - **等价性验证方案**：回归范围、双跑（影子流量/双读比对）、**差异容忍度与不一致时的处理规则**（以哪边为准）。
  - **迁移阶段与切流**：新旧并存 → 双写/双读 → 校验 → 灰度切读 → 停用旧路径，每阶段的进入与退出判据（手法见 `focus-areas.md`）。
  - **不可逆动作清单**：删旧代码/删旧表/切主库，含执行前检查项与审批点。
  - 重构动因与目标指标（否则重构没有验收标准）。
- **章节增删**：保留现状与痛点；**加「行为基线与等价性验证」（标准/完整档必填）**；**「迁移与切流」独立成章（标准档起）**；完整档必填「不可逆动作与审批」。
- **验收**：**双达标**——等价性（按基线一致、差异在容忍度内）**+** 目标指标改善。
- **回滚**：按阶段回退（切读未完成 → 指回旧路径；已双写 → 需反向同步或前滚）；不可逆动作一旦执行，回滚即前滚。
- **非目标**：**本次不改变的业务行为**（对外契约不变是重构的前提，必须显式写）。
- **常见漏项**：只写「结构更清晰」而无等价性验证，评审无法验收；用「QPS 提升 X%」当作重构成功的唯一证据；双跑比对没有差异处理规则。

## S4 替换与迁移

- **判定**：换数据库/缓存/消息队列/云厂商/框架/语言；分库分表、服务合并；数据要搬家或契约要翻译。落点通常为 C。
- **必答项**：
  - **能力差异清单**：新旧载体的语义差异（事务、一致性级别、超时、查询能力、运维能力），逐条给「差异 → 影响 → 对策」。
  - **数据迁移**：全量 + 增量、迁移期双写、批次与限速、**对账口径 + 抽样比例 + 差异处理**。
  - **契约映射**：旧接口/模型 → 新接口/模型的映射表，含不可映射项的处理。
  - **用户可见语义变化清单**（最常漏，且从接口签名看不出来）：排序/相关性口径、总数（精确 total → 估算 count）、分页深度上限、字段含义与精度（如「累计销量」→「近 30 天」）、超时与截断行为、空结果文案。逐条给「旧行为 → 新行为 → 谁签收 → 是否对外告知」——**签收不是评审通过，是有人对某条可见变化负责**。
  - **切换前止血**：现状是否已在退化（容量水位/故障频次）？若是，第一阶段必须是止血/降级（限流、缓存、只读、旧路径扩容），再谈迁移——否则迁移期本身就是事故窗口。
  - **切流与回退**：读切与写切的先后、灰度维度（用户/租户/流量比例）、回退时数据能否反向同步。
  - 容量与成本对比（换载体的常见动因）。
- **章节增删**：**加「载体差异与对策」（本场景评审核心）**；**加「数据迁移与校验」独立章节**；完整档必填「切流计划 + 回退/前滚判据」。
- **验收**：功能等价（差异项均已确认可接受）**+** 数据一致（对账通过）**+** 目标收益（成本/性能）达标。
- **回滚**：读切回退（低风险）→ 写切回退（需反向同步）→ **双写期结束后不可回退**，必须写明「回退窗口何时关闭」。
- **非目标**：本次不迁移的数据范围、不切换的流量（如「本期只迁冷数据、只切 10% 读流量」）。
- **常见漏项**：缺能力差异清单，上线后才发现新载体不支持某语义；对账口径含糊（对什么、差多少算失败）；没写回退窗口关闭时点；**只签「接口契约兼容」而漏掉「结果语义变化」**（total 变估算、深分页失效、排序口径变了，接口一个字没改但用户全看得见）；现状已接近故障却把止血排到尾期。

## S5 下线与废弃

- **判定**：下线接口/服务/表/字段/功能，停用旧系统或旧链路，数据归档或删除。落点通常为 C。
- **必答项**：
  - **消费者盘点**：调用方、定时任务、报表、下游系统、客户端版本、离线作业；含**僵尸消费者排查方法**（网关日志/链路追踪/SQL 审计）。
  - **通知与过渡期**：通知谁、何时、过渡期多长、期内如何提醒与降级（告警、弃用响应头）。
  - **下线判据**：满足什么条件才允许真正关闭（如连续 N 天零调用 + 所有消费者确认迁移完成）——「大家都迁完了」不是判据。
  - **数据处置**：归档到哪里、保留多久、是否可恢复、删除的合规依据。
  - **不可逆动作与审批**：删表/删数据/回收资源前的检查项与审批。
- **章节增删**：技术选型一节改为「下线方式选择」（硬下/软下/灰度停用）；**加「消费者盘点与通知」**；**加「数据处置」**。
- **验收**：目标范围内调用量**归零确认** + 消费者迁移确认 + 数据按约定归档或删除。
- **回滚**：分阶段——停用流量（可回退：恢复路由/开关）→ 归档数据（可回退：回灌）→ 删除资源（**不可逆**，需审批）。
- **非目标**：本次**不**下线的相邻能力（最常被误以为一起下线）。
- **常见漏项**：不做消费者盘点就删（「搜代码没引用」≠ 没有调用方）；无下线判据；数据删除缺合规依据或保留期。

## S6 专项优化

- **判定**：性能优化、安全加固、可观测性补建、CI/CD 与构建改造、成本优化；不新增业务能力、不改对外契约、结构与部署形态大体不变。落点通常为 C；优化对象是宿主公共设施（连接池/缓存/网关策略）时带 B 的义务。
- **必答项**：
  - 现状**指标**基线 + 目标值 + 测量口径与方法（量化主场，见 `quantification.md`）。
  - 瓶颈或差距的假设与验证手段（压测/采样/火焰图/审计），先验证再给方案。
  - **回归范围**：功能不变意味着任何改坏都是纯损失，必须写回归清单。
  - 每项优化的「预期收益 + 代价 + 回退开关」。
- **章节增删**：现状与痛点必填且必须带指标；删「迁移与数据」；回滚 = 开关/参数回退。
- **验收**：指标达标（对基线给幅度）**+** 无功能回归。
- **回滚**：开关/配置回退；注意「看似安全」的动作也有代价（加索引 → 写放大与锁表，改缓存 → 一致性与成本）。
- **非目标**：本次不动的指标维度（如「只优化读路径，写路径留二期」）。
- **常见漏项**：没有基线就写优化；写「提升明显」而不给口径与测量方法；忽略优化自身的代价。
