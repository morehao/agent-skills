# Tech Design（技术方案 / 技术设计文档）

写一份**能被评审、能被执行**的方案文档：先澄清规模与约束 → 定篇幅档位 → 定落点与变更场景 → **定挑战点** → 选专题加固 → 取证 → 对账 → 按叙事链推理 → 量化关键论断 → 配图与撰写 → 落盘 → 自检 → 机械门禁 → 独立评审 gate → 报告。

六条贯穿全文的硬要求，第一条决定其余五条该用在哪：

1. **挑战点优先**：一份方案里只有 1–3 处真正需要设计，其余都是抄作业。先找出这几个真问题（判定见「定挑战点」），由它决定这一版做什么、取证看什么；挑战点之外的章节按标准做法一句带过或删掉。**写不出一个命中四信号的挑战点，说明这份文档不该写**——按「小需求停止规则」直接给改动清单。若文档仍必须存在（契约对齐、合规留痕、跨团队同步），写 `挑战点豁免：<具体理由>` 并在报告 ② 说明为什么仍值得写。
2. **事实有据**：凡关于既有系统的论断（现状、影响面、调用方、容量水位），必须带证据锚点——`路径:行号`、监控面板与查询口径、或工单/事故单号；取不到证据的显式标 `[待核实]` 并写成假设。**不编现状**（取证对象按落点定，见 `references/scenarios.md`）。
3. **量化义务**：凡涉及性能、容量、可用性、成本、收益、规模的论断，必须给数字或区间 + 口径 + 假设来源；给不出就显式标为「待验证假设」并写清不成立时的应对，不允许用形容词代替（见 `references/quantification.md`）。
4. **取舍对偶**：每个关键选型必须回答「为什么选它 / 代价是什么 / 什么情况下不该选它」，且理由**回指它满足了哪条目标或约束**；只讲优点、或只给一个方案的对比视为未完成（Y-statement 句式见 `references/quality-bar.md`）。
5. **宁轻勿重**：档位从低起步，出现明确信号才上浮；骨架是覆盖清单而非填空卷——**本次不涉及**的章节**删掉**，不留 "N/A" 或一句话占位；**涉及但按标准做法**的章节，一句「按团队规范 X 执行 / 复用既有组件」是合格写法。完整档必备章节确不适用时写 `章节豁免：<理由>`。
6. **图是论证**：结构、边界、流转、关系必须有图（下限见「配图下限」）；每张图都要能说出它支撑哪个关切，说不出就删。**图既不许缺席，也不许当装饰**——纯文字方案视为未完成。

## 两种模式（开工先判）

| 模式 | 什么时候进 | 做什么 |
|------|------------|--------|
| **编写**（默认） | 要产出新方案，或用户授权重写既有方案 | 走下面「工作流」1→13 |
| **评审** | 用户手上有文档，要挑错 / 判可行性 / 要个结论 | 走 `references/review-gate.md` 的「评审模式」：复核证据 → 门禁 → rubric → 1–2 个 lens → `VERDICT` + findings |

判不清时：

- **既有文档 + 要改** → 先评审定位问题，再切编写模式改；顺序不能反。
- **只有一句话需求** → 编写模式，先澄清，不要凭空评。
- **评审模式下文档缺状态块 / 备选 / 追溯表 / 挑战点** → 这本身是 findings，记下来，**不替作者补**。

评审模式**不重写、不补章节、不落新文件**；`autofix` 只在用户明确要求时才做。

## 配图下限（先定图，再写字）

**图是结构与流转的论证载体，不是排版装饰。** 档位下限：轻量 0 张起但**结构类章节不豁免**（出现「总体架构 / 核心流程 / 数据模型」→ 该节必须有图，或写 `图豁免：<理由>`）、标准 **≥2 张**、完整 **≥3 张**（含系统上下文）。

**先图后文**：第 4 步定完挑战点、第 10 步动笔前，先按 `references/templates.md`「视图清单」填「章节 → 图 → 工具 → 承载哪个关切 → 导读/落着」，填不满说明这节还没想清。工具按**职责**选：结构/映射/对比/回边状态机走 SVG（`diagram-design` 导出同目录 `.svg`），时序/线性小图/ER 走 Mermaid，同一张图只做一种形式。

每张图必须被正文包裹：图前导读、图后有落着，图里每个节点正文都有解释。完整规范（工具选型细则、SVG 资产约束）见 `references/quality-bar.md`「图规范」；校验在「交付与收尾」。

## 红牌（出现这些念头就停下）

- 「需求清楚，没什么难点，都是标准做法」
- 「先把范围定死，再找难点」
- 「挑战点列五六个，显得想得全」
- 「改动小 / 需求清楚，不用取证」
- 「老板/负责人已经口述现状，不用查」
- 「方案已经拍板，备选不用写」
- 「先写完，数字最后补」
- 「先把正文写完，图最后再补」
- 「图会拖长文档，能省就省」
- 「没有 subagent，评审 lens 先跳过」
- 「拿不准就标 `[假设]`」
- 「门禁 0 error，可以交付」
- 「lens 没问题，能实施了」
- 「评审意见照改就行」

每一条的现实与必做动作见 `references/anti-rationalization.md`（同一份表也当错题本用）。

## 与其它技能的边界

- 文档配图或**独立 SVG 图表文件** → 按图的职责选 Mermaid / SVG（结构类/映射类/对比类/回边状态机走 SVG，由 `diagram-design` 导出 `.svg`）；规范见 `references/quality-bar.md`。
- 深度解读开源项目源码 / Git 操作 → 分别走 `project-insight` / `git-kit`。

## 工作流

0. **判模式** → 编写（默认）/ 评审。评审模式不走进下面的编写流程，直接按 `references/review-gate.md` 的「评审模式」跑。
1. **澄清** → 先读后问 + 写一段回声（≤200 字），再按下表优先级最多问 5 个问题，其余落成 `[假设]`。
2. **定档** → 三档篇幅/评审范围（`references/templates.md`）；用途（构建契约 / 对齐材料）与档位正交，一并确定，顺手记下这档的时间盒。**档位与场景在这里只是初值**（决定写多细、走哪些过程义务）；本期范围由第 4 步挑战点收口，冲突时回改 2/3，不许删挑战点保范围。
3. **定落点与场景** → 先答落点（新系统 / 既有系统的新模块 / 既有系统的既有模块），再按变更性质单选场景（`references/scenarios.md`）。
4. **定挑战点** → 按四信号找出 1–3 个真难点并编号 C1…Cn，其余标「标准做法」；这一步决定取证看什么、正文展开哪几节，「本期做什么」由它收口（判定见「定挑战点」）。**超过 3 个先逐个按四信号复核**：不命中的标「标准做法」并给复用依据；仍命中的拆「总纲 + 子方案」或分期，并写清下一期承接时间点。**定挑战点阶段站不住，唯一回退目标是第 1 步**（补问规模/依赖/历史）；只有取证后站不住才回第 4 步。
5. **选专题** → 可多选加固方向（`references/focus-areas.md`）；只加深挑战点与硬约束落在的那几节，与之无关的领域不选。
6. **取证** → 按落点确定取证对象（见 `references/scenarios.md` 的「落点义务增量」），**且只取证挑战点用得上的事实**：读代码、拉指标、盘调用方、查事故单，产出「已确认事实（带证据锚点）／未确认假设」两栏。**取证先于动笔；取证后挑战点变了就回 4。**
7. **对账** → 有上游文档（PRD / feature spec / API spec / ADR）时，先把上游需求逐条映射成「决策 + 验证手段」，映射不上的标 `[未覆盖]`；需求编号沿用上游既有体系。没有上游就自建编号并在「假设与约束」声明（`templates.md` 追溯表）。
8. **推理** → 按「叙事链」把 10 问问清楚再成文（`references/templates.md`）；发现阶段允许回溯，推翻前面的分解很正常。
9. **量化** → 关键论断的数字与口径（`references/quantification.md`），与撰写同步做。
10. **配图 + 撰写** → **先填视图清单、先出骨架图，再写正文**（图是论证骨架，不是文末插图）：结构类图先调 `diagram-design` 导出 `.svg`，时序/线性/ER 写 Mermaid，每张图按「导读段 → 图 → 落着」落位；下限见「配图下限」。正文先把「挑战点与取舍」一节写死，其余章节围着它写——没有挑战点撑腰的章节不展开。全程守 `references/quality-bar.md` 的红线与反模式；较大方案可先只出「问题定义 + 约束 + 挑战点 + 目标」请相关人（含宿主/调用方 owner）对齐，再展开方案。
11. **落盘 + 自检** → 按「交付与收尾」落盘，再逐条过「交付前自检」，不通过就改。
12. **门禁 + 评审 gate** → 先跑 `scripts/check-design-doc.mjs` 清机械项，再按 `references/review-gate.md` 跑独立评审（完整档必跑、标准档建议）。
13. **报告** → 见「交付与收尾」的报告格式。

**最小执行路径**（不是每档都走满 13 步）：轻量档 = 0→1→2→3→4（一句话，如「唯一难点是 X」）→6（只取现状/宿主相关证据）→10（含最小图集）→11→12（只跑门禁，gate 跳过）→13；标准档加 7、9，8 压缩成一段叙事；完整档全走。跳步的前提是「没有可讨论的取舍」——那种情况直接给实施清单，不写方案文档。

### 澄清问题清单（按优先级取前 5 个）

只问**决定文档结构的问题**，不问能从代码或用户原话里推出来的问题。

开口前先做两件事，能省掉一半无效提问：

1. **先读后问**：读用户点到的文件与其关联代码，读到能讲清「现状怎么跑、这次改动会碰到什么」为止。**不问项目已经回答的问题。**
2. **回声**（≤200 字，单独一条消息）：用自己的话讲「要什么 / 给谁 / 为什么 / 现状与影响」，末尾只留一个「答案最改变做法」的问题。回声错了比问题错了便宜得多。

| 优先级 | 问题 | 为什么必须问 |
|--------|------|--------------|
| 1 | **用途**：这份文档是**构建契约**（下游照着实施）还是**对齐材料**（拉着人对齐、把开放问题摆前面）？ | 决定详略与留白策略，与档位正交；答不上来按「构建契约」 |
| 2 | 规模量级：多少用户/多少数据/多大 QPS 或读写比？ | 没有规模既无法定轻重，也无法量化 |
| 3 | **落点与改动范围**：新系统 / 既有系统的新模块 / 既有系统的既有模块？改什么（新建/改造/重构/替换/下线/优化）？宿主或上下游是谁？ | **落点决定取证对象与义务增量，改动性质决定场景**，见 `references/scenarios.md` |
| 4 | 硬约束：技术栈、部署环境、可用性/延迟/合规要求、排期与人手？ | 决定选型边界与非目标 |
| 5 | 已有上游文档时：需求编号是什么？哪些已定、哪些留给我们决定？ | 决定对账的键与追溯表的「承接需求」列；没有就自建编号 |

用户答不上来时**不阻塞**：给一个明确默认值，标 `[假设]` 并写进「假设与约束」。

### 歧义扫描（提问前自查，避免问废话）

逐类标 `清晰 / 部分 / 缺失`，**只对「缺失且会改结构」的类提问**，问题总数 ≤5。

| 类目 | 缺失时的典型后果 |
|------|------------------|
| 功能范围与行为 | 目标写成功能清单，非目标写不出来 |
| 数据与生命周期 | 只列字段，说不清状态流转与数据所有权 |
| 交互与异常态 | 只写正常路径，错误码与降级让评审去猜 |
| 非功能（性能/容量/安全/合规） | 无法量化，验收标准写不成阈值 |
| 约束与依赖 | 选型边界不清，落地时被推翻 |
| 术语与命名 | 同一概念多个叫法，评审各说各话 |

### 未定项三记号（全文统一，门禁会查是否收口）

| 记号 | 含义 | 谁来收口 |
|------|------|----------|
| `[待核实]` | **事实**拿不到（现状、指标、调用方） | 去取证；取不到写成假设并给验证方式 |
| `[待澄清]` | **决策**没定（选哪个、范围到哪） | 写默认倾向 + 谁拍板，进「开放问题」 |
| `[假设]` | 我**替你定了**（默认值、估算前提） | 进「假设与约束」，请用户确认 |

三者都必须收口到「开放问题 / 假设与约束」，不许散在正文里。

**取证预算**：`[待核实]` 超过 5 处时，必须在「开放问题」逐条给出取证计划（查哪个面板 / 问谁 / 何时），不允许用标注代替取证。

### 定档（决定篇幅与评审范围）

| 档位 | 适用 | 判定信号 | 时间盒 | 骨架 |
|------|------|----------|--------|------|
| 轻量 | 单模块功能、小型优化、简单集成 | 改动面小、一次评审能过、无跨系统影响 | 30 分钟 | `templates.md` 轻量档 |
| 标准 | 子系统、中型业务模块 | 跨多个模块/服务，含数据与接口设计 | 半天到两天 | `templates.md` 标准档 |
| 完整 | 系统架构、跨系统集成、重构/迁移、大型平台 | 全链路评估，含容量/安全/成本/回滚 | 一周以上 | `templates.md` 完整档 |

拿不准先用轻量档；出现这些信号才上浮：跨团队评审、SLA 承诺、成本敏感、合规审查、不可逆变更。场景与档位的常配关系见 `references/scenarios.md` 速览表。**时间盒是校准器，不是上限**：到点还没收敛，通常是档位定高了（该下沉）或挑战点没找对（回第 4 步），不是「再写长一点」。

**体量红线**：完整档超过 ~20 屏就拆成「总纲 + 子方案」互链（总纲只留背景、目标、总体架构、决策追溯表、风险），别写一份没人读完的巨文——读不完的文档等于没有文档。**但篇幅只是阅读体验的提示，不是质量指标**：不要为压行数删掉证据、取舍、验证与回滚；该长就长，长到读不完才拆，而不是为达标砍内容。

**小需求停止规则**：澄清问题清单答完、挑战点也收敛之后，没有产生任何「在两个都合理的选项之间选一个」的分歧，就不要写设计文档，直接给改动清单——写文档的前提是存在可讨论的取舍，没有取舍的文档只是把确定的事重述一遍，还多一份维护成本。

**用途决定留白**（与档位正交）：**构建契约**要求决策闭合、接口与数据写死、验收可执行；**对齐材料**要求把开放问题前置、把「还没定的」显式化，不假装确定。

### 定落点（场景判定的第 0 问）

先问「这次设计落在哪里」。落点与变更性质**正交**，它不替代场景，但决定**取证对象、现状章节写什么、义务增量、必须谁签**。

| 落点 | 一句话判定 | 义务增量（详见 `references/scenarios.md`） |
|------|------------|--------------------------------------------|
| A 新系统 | 本系统无存量，从零做 | 集成点 + MVP 边界；删自身现状章节，但保留外部环境与可复用能力盘点 |
| B 既有系统的新模块 | 有宿主，改动以「加法」为主 | **宿主约束**（技术栈/容量/发布节奏/依赖版本/权限与监控接入）+ 对宿主的影响 + 模块边界与数据所有权 + 退出路径 |
| C 既有系统的既有模块 | 改既有实现或契约 | 现状与痛点（**带证据**）+ 影响面 + 兼容性 + 回归范围；对外行为不变时升级为行为基线与等价性验证 |

### 定场景（决定变更过程义务，单选）

| 场景 | 一句话判定 |
|------|------------|
| S1 新建 | 从零做，无存量（删现状类章节） |
| S2 增量改造 | 改或加既有功能，行为改变（要影响面 + 兼容性 + 回归范围） |
| S3 结构重构 | 结构变、行为应不变（要行为基线 + 等价性验证 + 切流回滚） |
| S4 替换与迁移 | 换存储/中间件/框架/供应商（要能力差异清单 + 对账 + 回退窗口） |
| S5 下线与废弃 | 移除既有能力（要消费者盘点 + 下线判据 + 数据处置） |
| S6 专项优化 | 结构不变、只冲指标（要指标基线 + 回归范围 + 收益代价） |

同时命中多个时取**风险更高、过程更长**者为主场景，另一场景的必答项作为补充义务并入；S1–S6 与落点的常配组合见 `references/scenarios.md` 的「组合规则」。判定顺序、必答项、章节增删、验收与回滚形态见 `references/scenarios.md`。

### 定挑战点（决定这一版做什么、写哪几节）

档位只决定「写多细」，挑战点决定「做什么」。一个系统里需要设计的只有 1–3 处，其余是行业标准答案：鉴权、日志、分页、部署、监控接入、CI，要么有现成组件，要么有团队规范，照做即可。把这些当挑战点展开，会把文档撑到没人读，同时把真正的难点埋在中间。

**判定信号**（命中任一才算真挑战；全不命中的点不该出现在正文里）：

| 信号 | 问句 | 命中后的典型产出 |
|------|------|------------------|
| **约束冲突** | 哪两个都合理的目标互斥（快 vs 准、省 vs 稳、灵活 vs 可控、开放 vs 安全）？ | 一次显式取舍 + 代价 |
| **数量级跨越** | 单机 → 分片、千级 → 十万级 QPS、GB → TB、单地域 → 多地域？ | 结构级变化（分片键、缓存层、异步化） |
| **状态所有权不清** | 同一份数据有没有两个「真相」？对账时以谁为准？ | 真相持有者 + 对账口径 |
| **失败不可逆** | 超卖、丢单、错价、数据擦除、已发出去的链接？ | 在设计里堵死，不留事后补偿 |

**产出**一句话：这个系统难的是 A、B，可能还有 C；除这三处之外按标准做法执行。文档里的落地形式是独立一节「挑战点与取舍」：每个挑战点一段，写清它为什么难、由此产生的取舍；其余章节只写「按团队规范 / 复用既有组件」，不展开。**标准档及以上给挑战点编号 C1…Cn**，追溯表的「挑战点」列用它承接——每个编号至少要有一个决策承接，挂不上决策的「难点」是风险描述，不是设计。

**四条纪律**：

- **挑战点先于范围**：本期做到哪、二期做什么，由挑战点决定。先把范围定死再找难点，难点一定被「二期再优化」糊过去，而二期不会来。
- **挑战点先于取证**：取证对象由挑战点与落点共同决定，不做全量盘点；取证后挑战点站不住就回去改，别硬写。
- **挑战点 ≤3**：从第 4 个开始基本是标准做法，或者该拆给下一版。超过 3 个不是想得全，是还没收敛。
- **写不出挑战点**：要么需求确实小（按「小需求停止规则」直接给改动清单，不写文档），要么澄清漏了东西（规模、依赖、历史没问）——回第 1 步补，不要硬写；文档仍必须写的，用 `挑战点豁免：<具体理由>` 显式收口。

### 选专题（决定加深哪几节，可多选）

**架构设计 / API 设计 / 数据模型设计 / 性能与容量 / 安全 / 迁移手法**（无命中则按模板原样展开）。

专题只决定技术领域的重心、必答项与可裁剪章节，**不承担过程义务**（迁移、兼容、回滚、等价性验证归场景）；多个专题叠加时同一章节取并集。**选专题前先有挑战点**：没有挑战点或硬约束撑腰的领域不选，否则会加深一堆标准做法。详见 `references/focus-areas.md`。

## 交付与收尾

1. **先探落盘约定**（顺序即优先级，命中即停）：
   1. 用户本次指定的路径 / 命名；
   2. 仓库既有方案目录与命名：`docs/design/`、`docs/rfc/`、`docs/adr/`、`docs/specs/`，或已有 `*-design-*.md`；
   3. 仓库或全局 AGENTS.md 声明的过程性文档位置（常见 `.dsh/docs/specs/`，文件名 `<YYYY-MM-DD>-<topic>-design.md`，日期在前）；
   4. 都没有才用默认 `{主题关键字}-design-{YYYYMMDD}.md`，存当前工作目录。

   落到 `.dsh/` 这类被 gitignore 的目录时，报告里点一句「该目录不入库，要入库请指定 `docs/` 路径」。
2. 用 `write` 完整落盘并确认成功。
3. 文档头部带**状态块**：状态（草案待评 / 评审中 / 已批准）、作者、评审人与拍板人（按落点定：宿主新模块要宿主 owner，既有模块改动要调用方 owner）、最后更新日期。较大方案可以先落盘「问题定义 + 约束 + 挑战点 + 目标」请人对齐，再补全方案，状态保持草案待评。
4. 文档配图先按 `quality-bar.md` 定工具，再按对应路径校验（脚本按自身位置相对定位，任一已注册路径都可用）：
   ```bash
   # Mermaid：真解析
   node <本skill目录>/scripts/check-mermaid.mjs <生成文件>
   # SVG：边拓扑审计（结构类图新画或重排后必跑；diagram-design 产物自动走几何推断）
   node <本skill目录>/scripts/audit-svg-topology.mjs [--expect 期望边清单.txt] <图.svg>...
   # SVG：目视预览（可选；自绘兜底时才需要，diagram-design 的产物直接看它的 HTML）
   node <本skill目录>/scripts/render-svg-preview.mjs <图.svg>...
   # 常见注册位置：~/.agents/skills/tech-design/（opencode 与 dsh 的统一技能安装位）
   ```
   `[MERMAID-ERROR]`、审计**退出码非 0** → 必须修复后重跑，**不静默放过**；`[MERMAID-WARN]`、`[EDGE-GAP]` 为提示级。SVG 图落成**文档同目录的 `.svg` 资产**（英文语义名），并在报告里列出。**简版 ER 图**（`erDiagram`）同样纳入 Mermaid 校验；附录 DDL 是代码块、不参与图校验，但要与正文表格逐项核对一致（`references/data-model.md`）。校验只覆盖「能否解析/渲染」「边是否贴合齐全」，ID 语义化、引号、视图服务关切等约定仍需人工过。**标准档及以上，图的两条门禁规则必须为 0**：`TD-NO-DIAGRAM`（某节缺图）与 `TD-DIAGRAM-MIN`（低于档位最小图集）。前者确不适用就在该节写 `图豁免：<理由>`；后者不能靠单节豁免绕过，只能补图或按轻量档重评。
5. 逐条过「交付前自检」，不通过就改。
6. **跑文档门禁**（机械项）：
   ```bash
   node <本skill目录>/scripts/check-design-doc.mjs <文档> --tier <light|standard|full> [--upstream <PRD>...]
   ```
   `error` 修完重跑；`warn` 逐条裁决（改掉，或在文档里显式豁免并写理由）；`note` 读一遍确认已收口。`--strict` 把 warn 也当失败，标准档与完整档建议加。**缺图是 warn，但不是「可忽略项」**：`TD-NO-DIAGRAM` / `TD-DIAGRAM-MIN` 出现即补图或写豁免，别把 0 error 当成图已齐。**`TD-CHALLENGE` 同样不是可忽略项**：先判断这份文档该不该写，再补挑战点；**只有当文档仍必须存在**（契约对齐、合规留痕、跨团队同步）而确无设计取舍时，才写 `挑战点豁免：<具体理由>`（理由要写实，抄占位符或写「无」不算）。脚本只覆盖机械项，语义判断不归它。
7. **跑评审 gate**（完整档必跑、标准档建议、轻量档跳过）：按 `references/review-gate.md` 三段走——门禁 → 清单判定 → 并行 lens，收口成单一裁决 `approve / revise`；每条发现按 `autofix / discuss / defer / ignore` 处置。`revise` 改完必须**重跑门禁**（改文档会引入新的机械问题）。落盘时按场景与档位生成评审检查清单（真源 `references/quality-bar.md`），作为文末小节或口头收口。
8. 报告格式：`✅ 技术方案文档已生成: <文件路径>`，并补五样：① 本次落点/场景/档位/专题；② **挑战点一句话**（1–3 个，如「难在预占与支付回调的时序、库存真相归属；其余按标准做法」；没有挑战点就说清为什么这份文档仍值得写）；③ **门禁原始输出末行 + gate 的 `VERDICT`**（贴原文，不写「应该没问题」；没跑 gate 就写清为什么）；④ **图清单**：共 N 张（Mermaid a / SVG b），每张落在哪一节（SVG 给相对路径）；⑤ 最需要评审拍板的 1-2 个点。
9. **不自动打开文件**（dsh Web 无 `code` 语义）。仅当用户明确要求且本机确有编辑器时才尝试，失败即提示手动打开路径。
10. 落盘后不做 `git add` / `git commit`。用户接着要独立 SVG 架构图或源码级验证时，分别提示 `diagram-design` / `project-insight`。

### 交付前自检（逐条过，任一不过就改）

**清单唯一真源在 `references/quality-bar.md`「表一 · 交付门槛（逐条）」**——按那张表逐条自检，任一不过就改；表一同时是评审模式的 rubric 来源，作者自检与评审同一把尺子。自检通过后再跑门禁 `check-design-doc.mjs`（无 error，warn 逐条裁决），最后按档位跑评审 gate。

## 注意事项

- **先判断该不该写方案**：答案唯一、没有可讨论的取舍（纯执行清单、按既定规范加个字段）就不走技术方案，直接给实施清单。判别信号：写不出「备选 + 代价」。
- **先定挑战点再动笔**：能说出 1–3 个真难点与各自取舍；说不出来，要么需求太小（不写），要么还没看懂（回第 1 步补规模/依赖/历史）。挑战点之外的章节按标准做法一句带过——把标准答案写长，是对想不清楚的掩盖。
- **先取证再动笔**：现状、影响面、调用方、容量水位这四类最容易编，一律先看真系统。
- **落点决定「现状写什么」与「必须谁签」**：别把「既有系统的新模块」当新系统写——它缺的不是集成点，是宿主约束。
- **门禁先于评审**：机械错误先让脚本清掉，评审者的注意力只该花在判断上；但门禁过了不等于方案成立，语义判断归评审。
- **备选差异只在参数或命名上，等于没做备选**：换的是思路与代价，不是措辞。
- **贴合规模与团队现实**：小需求不套企业级章节；选型给 2-3 个方案、中立并写取舍理由；术语首现给中文释义，非技术读者能读懂核心思路。
