# 落点判定与入库约定：文档落在哪、怎么被找到

> 由 SKILL.md「执行流程主干」的 step 1（落点判定）按需加载。
> 本文件承载：**产出目录为什么不能默认等于 cwd、两种落点模式、判定流程、分类归属与索引同步、
> frontmatter 约定、单页模式、门禁该对哪个目录跑**。

## 为什么落点要先判

**产出目录不默认等同于执行时的当前工作目录。** cwd 是一个偶然值，而落点有两个真实危险：

1. cwd 可能就在 `source_repo` 内 —— 直接违反"产物绝不落入被描述项目"这条底线；
2. cwd 可能是一个知识库仓库（KB），若在它外面另造一个平行目录，同一项目的文档会永久分裂成两处，检索割裂。

所以先判定，再确认一次，然后记为本次的**输出目录**并在会话内沿用。

## 两种模式

| 模式 | 目录 | 何时 |
|------|------|------|
| **独立模式（默认）** | `<cwd>/<项目名>-wiki/` | cwd 不是 KB，或用户选择独立输出 |
| **KB 模式** | `{kb_repo}/{分类}/{项目名}-wiki/` | cwd 命中 KB 信号，或用户指定 KB 路径 |

两种模式的**内部结构完全一致**（`README.md` + 主题页 + 可选 `assets/*.svg`，
见 [page-plan.md](page-plan.md)），差别只在父级；命名统一为 `<项目名>-wiki/`。

KB 模式下，wiki 与 project-insight 的产物 `{kb_repo}/{分类}/{项目名}/` 是**平级兄弟目录**：

- **零文件名冲突**——两边各有自己的 `README.md`、`architecture.md`…，互不覆盖；
- **wiki 不依赖 insight 先跑过**——没有父目录要创建，也不碰 insight 的树；
- 本 skill 的门禁语义原样成立（首页、索引、页面检查都只作用在 `-wiki/` 这一棵树内）。

`{项目名}` 取 `source_repo` 的目录名（`realpath` 后的 basename），用户可覆盖。

## 判定流程

```
realpath(source_repo)
├─ 候选落点若落在 source_repo 内 → 换兄弟目录，或问用户
├─ cwd 命中 KB 信号（{目录}/{目录}/README.md 或 {目录}/{目录}-wiki/README.md）
│     → 结构化二选一：① {kb_repo}/{分类}/{项目名}-wiki/   ② <cwd>/<项目名>-wiki/
├─ cwd 是源码工程根 / 空目录且无线索
│     → 同样二选一，但选项②不作为默认推荐，并说明原因
└─ 都不是 → 独立模式：<cwd>/<项目名>-wiki/
```

选定后**报告 final realpath**；KB 模式下**提前列出将要改动的索引文件**，让落点在动手前就是可见的。

### KB 信号与排除信号

- **KB 信号**：深度 2 扫描存在 `{目录}/{目录}/README.md` **或** `{目录}/{目录}-wiki/README.md`，
  且该二级目录不是常见源码工程目录名（排除 `src`、`node_modules`、`cmd`、`internal`、`.git` 等）。
  第二种形态是必须的：只做过 wiki 的项目在 KB 里**没有** `{项目}/README.md`。
- **落点禁区**：候选落点在 `source_repo` 内。这是全部门禁里**唯一以 error 档拦**的一条（`[DOC-DOCROOT-IN-SRC]`）——
  它可确定判定，且后果落在第三方仓库。确实要给项目自己加内嵌文档时用 `--allow-in-repo` 显式放行，
  **放行要出声**——程序照常输出一条 note 说明"已按显式放行跳过源码仓落点检查"（不静默跳过），并进交付清单；
  未传 `--source-repo`（或它不可读）时同样降级为 note"无法判定"，既不报错也不静默。
- **不推荐新建的信号**：cwd 是具体编程项目源码根（存在 `package.json` / `go.mod` / `Cargo.toml` 等工程清单
  且无知识库特征），或 cwd 为空且无任何 git / README 线索。此时提示："当前目录看起来是代码仓库而非知识库仓库，
  在这里新建文档结构可能不是你要的。"

### 二选一话术（结构化，不做开放式提问）

> "当前目录 {cwd} 未检测到 `分类/项目/README.md` 这类知识库结构（原因：{具体原因}）。是否：
> ① 指定一个已有知识库仓库路径（wiki 将落在 `{分类}/{项目名}-wiki/`）
> ② 就在当前目录 {cwd} 下新建 `<项目名>-wiki/`。请选择，或直接给出目标路径。"

## 分类归属：优先复用

同一个项目**只应出现在一个分类下**（project-insight 已踩过"项目被归到 `chat/` 而非 `IM/`"的坑，
导致后续模式判定漏判）。所以选分类前先扫一遍：

- `*/{项目名}/`（insight 的产物）与 `*/{项目名}-wiki/`（wiki 的产物）；
- `grep` 项目名 / 仓库地址 / 别名。

**命中即复用该分类**；都没有找到才问用户。分类不存在则新建，并在顶层 `README.md` 加一行
（顶层索引是**加分项**，非必要条件）。

## 索引同步（只增改本项目相关条目）

收尾时让 wiki 在 KB 里可被发现：

- **索引表一行一项目** → 在**本项目那一行的说明列**追加 `` `[Wiki]({项目名}-wiki/README.md)` ``，
  不新增行（避免同一项目在索引里出现两次）；
- **KB 已有独立的 wiki 区 / 行** → 沿用既有形态，不另起格式；
- **只动本项目相关条目**：不重排、不改写其他项目的条目格式；
- 将要改动的索引文件**提前列入交付清单**；只落盘，不代为 `git add/commit`。

`[DOC-KB-UNLINKED]`（note）用于提醒"入库了但没有任何 md 链接过去"：传了 `--kb-repo <路径>` 时，
程序核对存在某个 md 链接到本 wiki 的 `README.md`；不阻断（没有链接 = 读者找不到，属显形而非阻断的事）。

## frontmatter 约定

每页仍必须带 `title` + `description`；KB 模式下额外写：

```yaml
type: 项目 Wiki
```

用途是让同一份 KB 的检索层把两类产物分开（project-insight 用 `type: 项目解读`）。
`[DOC-FRONTMATTER-TYPE]` 只是 **note**，不阻断。

## 轻量形态：单页模式

用户只要一份概述、不要多页时，**单页模式**即可：只产出 `README.md`，不拆主题页。

- 这不是 project-insight 的"临时分析"——wiki 的产物**就是文件**，不落盘等于没有产物；
- 门禁天然支持：只有在存在 `README.md` 以外的页面时，才要求首页有索引章节；
  篇幅下限与"每页 ≥1 张图"照旧适用（见 [grounding-light.md](grounding-light.md)）。

## 门禁跑在哪

**只对 `<项目名>-wiki/` 目录跑 `check-all.mjs`，不要对 KB 根跑**：校验器会把"第一个 `README.md`"当首页、
把其余 md 当成本 wiki 的页面，对 KB 根跑会把其他项目的文档报成"未列出页"，刷出一屏假 error。

## 与基线、更新模式的接口

- **落点决定模式判定**：`{输出目录}/README.md` 存在且含页面索引 → 更新模式（[update-flow.md](update-flow.md)）；
  不存在 → 全新模式；
- **落点必须在基线工作树之外**（[version-contract.md](version-contract.md)），由 `[DOC-DOCROOT-IN-SRC]` 兜底；
- **口径独立性**：本约定与 project-insight 的 KB 结构保持**兼容**（同为 `{分类}/{项目}` 体系、索引同样只动本项目条目），
  但本文件是 wiki 自己的口径——任一侧修改该兼容约定时，另一侧需同步。这是**兼容声明，不是依赖**。
