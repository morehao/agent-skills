# 写作风格与代码准入

> 由 SKILL.md「执行流程主干」的 step 5（逐页写）按需加载。
> 本文件承载**怎么写**：读者画像、散文口径、表格化、**代码准入三问**、禁止清单。

## 读者画像（所有取舍的基准）

写每个句子前，想一遍读者是谁：

1. **技术选型者**：想知道这东西解不解决他的问题、代价是什么、能用多久。
2. **新加入的成员**：想快速建立整体印象，然后知道该往哪钻。
3. **跨团队同事**：懂技术但不熟悉这个领域，需要每个术语第一次出现时有人解释。

这三类人的共同点：**他们不会打开源码**。所以"见 `xxx.go:42`"对他们等于没写；
"用了洋葱模型，中间件能同时处理请求和响应两个阶段"才是他们能带走的东西。

## 散文口径

- **先结论后理由**：一段的第一句就是这段的结论，后面才是展开。
  读者扫第一句就能决定要不要细读。
- **一段一个意思**：一段里塞两个主题，读者就得来回找断点。
- **中文为主，术语/标识符保留英文**（`middleware`、`JWT`、类型名、命令名）。
  术语**首次出现**时给中文解释；引用英文原文时后面必须跟中文解读，不留孤立英文段落。
- **具体优先于形容**："高性能"没有信息量；"单进程可跑满多核、无锁队列"才有。
  给不出具体的，说明还没读懂，回去读源码。
- **不使用"显然 / 简单 / 众所周知"**：这些词只在读者卡住时制造挫败感。
- **不用"我们"**：文档不是团队周报，用"项目""该模块"或直接陈述。

## 能成表就成表

表格是密度最高、最省读者时间的表达。凡是"一堆同构的东西"，一律成表：

| 内容 | 表头 |
|------|------|
| 核心能力 | 能力 \| 说明 \| 典型场景 |
| 接口 / 命令 | 接口 \| 方法 \| 作用 \| 关键参数 |
| 配置项 | 配置 \| 类型 \| 默认值 \| 说明 |
| 数据实体 | 实体 \| 作用 \| 关键字段 \| 关系 |
| 错误码 | 码 \| 含义 \| 触发条件 \| 处置 |
| 技术栈 | 组件 \| 用途 \| 选型理由 |
| 同类对比 | 项目 \| 定位 \| 差异 |

反面：用一段散文罗列五个配置项——读者要自己切分，成本高得多。

## 列表：并列才用，不拿列表凑短

列表和表格一样是省读者时间的工具，但它的适用前提比表格更窄：**只用于并列且同构、可枚举、项间没有因果链的内容**。满足这个前提就上列表，不满足就老实写散文。

- **多步操作 → 有序列表**：安装步骤、发布流程、排查顺序这类有先后依赖、漏一步就跑不通的内容，用 `1. 2. 3.`。顺序本身是信息，无序列表会丢掉它。
- **并列要点 / 限制 / 检查项 → 无序列表**：几条互不隶属、可以任意调换先后的要点、边界条件、注意事项，用 `-`。读者一眼扫完，不必自己从段落里切分。
- **带因果、让步、转折的论述必须留散文**：为什么这么设计、先讲结论再讲理由再讲代价、A 成立但 B 会让它失效——这类内容是一条论证线，不是一组并列项。拆成 bullet 会把「因为……所以……」「虽然……但是……」的链条切断，读者反而要自己把逻辑拼回来。

判断标准和「能成表就成表」是同一条：**一堆同构的东西别塞进大段落，该列表就列表；但反过来，一条连贯的论证也别硬拆成列表。** 列表的边界不是「段落长短」，而是「项与项之间有没有逻辑流动」。

反面：把「先结论、后理由、再代价」的完整论证拆成三颗 bullet——

> - 结论：默认关闭该功能
> - 理由：开启后每页多一次全量扫描，成本高
> - 代价：需要的人要手动打开

三行看似整齐，但「因为成本高所以默认关，想要的人得手动开」是一条让步加因果的推演，bullet 之间没有承接词，读者得自己脑补衔接。正确做法是把它写成一句话散文：「该功能默认关闭——开启会让每页多一次全量扫描，成本偏高；确实需要的人再手动打开。」只有当这三条真的是**互不相干**的并列清单时，才该用列表。

## 风险提示与任务清单

列表之外还有两种语法能让「风险」和「进度」从字流里浮出来。二者各有唯一用途，**用对了它替读者省时间，用错了（混进叙事、语义串台）反而制造噪音**。

### `>` 只表风险与限制

正文引用块 `>` 的**唯一语义**是突出**前置风险、易错点、边界限制、上线前须知**——这类信息藏在段落里最容易被读者跳过，浮出来才能让人停下来看一眼。

硬前提：**同一份产出文档里，正文 `>` 只表达这一种语义**，不兼作引用原文、旁注、金句摘抄等他用。语义一旦被稀释，读者看到 `>` 就不知道该不该警惕，浮出来的效果也就没了。

> 本 skill 自身的文件头「加载说明」（如本文件顶部那两行）是**元文档语境**，不在本约束内——它约束的是你产出的 wiki 正文。

前（风险埋在流水句里，读者容易漏读）：

```markdown
注意这里如果并发写入可能造成死锁，所以上线前务必压测，另外这个接口不幂等，重试要自己保证。
```

后（浮成引用块，一眼看见「要当心什么」）：

```markdown
> **风险**：并发写入可能死锁，上线前必须压测；该接口不幂等，重试需调用方自行去重。
```

### 任务列表只用于清单

自检清单、落盘前 checklist、待办追踪，用任务列表 `- [ ]`（未完成）/ `- [x]`（已完成），**完成状态即语法**，比在 bullet 后面加「（已完成）/（待确认）」括注更好扫。它**只用于清单**，不塞进讲述性正文——正文里冒出 `- [ ]` 会像没写完的草稿。

前（状态靠括注，一眼看不出哪几项没做完）：

```markdown
- 代码预算达标（已完成）
- 校验痕迹已清理（已完成）
- Mermaid 全部渲染通过（待确认）
```

后（状态即语法，缺口一眼可辨）：

```markdown
- [x] 代码预算达标
- [x] 校验痕迹已清理
- [ ] Mermaid 全部渲染通过
```

落盘前的质量红线自检清单（见 [../SKILL.md](../SKILL.md)「质量红线」）就是任务列表的典型用例。

## 代码准入三问（硬规则）

**默认：这一页不放代码。** 只有下面三问**全部回答"是"**，才允许放，且必须短：

1. **不看这段代码，读者会误解吗？** —— 只是"更直观"不算，必须是不看就会理解错。
2. **能用散文、图或表替代吗？** —— 能替代就用替代。配置项用表，流程用图，接口用表。
3. **它能否压到 15 行以内、且只留不可绕过的核心？** —— 压不到就说明还没提炼出来。

配套要求：

- 代码块前后**必有散文解释**它在说什么、为什么要看它。禁止"核心逻辑见下" + 贴代码。
- 禁止逐行注释复述（`i++ // 自增`）；注释只写**为什么**，不写**做了什么**。
- 禁止把一个函数整段搬过来当"证据"。
- 伪代码、配置片段、SQL、目录结构树都算代码块，一并计入预算。

### 预算（程序校验，见 `scripts/check-docs.mjs`）

| 口径 | 默认上限 | 超出输出 |
|------|---------|---------|
| 单页代码块数 | 3 | `[DOC-CODE-HEAVY]` |
| 单块行数 | 15 | `[DOC-CODE-LONG]` |
| 单页代码总行数 | 40 | `[DOC-CODE-HEAVY]` |

超预算的处置只有两条：**删**，或在该页写一行
`<!-- code-budget: <为什么这段不可省> -->` 显式豁免。
豁免是"有意识的选择"，不是"忘了删"——评审时这行就是你的辩护词。

## 图替段落

凡是有形状的内容，**先想图，不要先写文字**：

| 内容 | 用什么 |
|------|--------|
| 系统分层、模块拓扑、部署形态 | 结构图 |
| 一次请求/一条数据怎么流动 | 时序图或流程图 |
| 状态流转、连接生命周期 | 状态图 |
| 实体与关系 | ER 图 |

判断标准：**一段文字如果能在纸上画成树或线，它就该是图**。
文字只负责图外的东西——例外条件、为什么这样设计、代价是什么。

图表选型与硬约束见 [diagrams.md](diagrams.md)。

## 禁止清单

- ❌ 满篇 `文件:行号`：读者不打开源码，行号对他没有意义。出处收进章末依据行。
- ❌ 逐函数/逐文件罗列："模块 A 有 f1、f2、f3"——聚合成职责。
- ❌ 抄 README 改排版：README 是**线索来源**，不是产出模板。
- ❌ 用"可能/大概/通常是"掩盖没核实的事：要么去核实，要么删掉。
- ❌ 把未完成项写成"刻意的设计选择"：未完成就写进「现状与边界」。
- ❌ 章节标题带数字前缀（`## 1. X`、`## 第N部分`）：用语义式标题表达从属关系。
- ❌ 整段未解释的英文：引用原文必须紧跟中文解读。
