# 页面规划与产出形态

> 由 SKILL.md「执行流程主干」的 step 3/4（探索 → 规划页面清单）按需加载。
> 本文件承载：**页集怎么定、产出长什么样、文件怎么命名**。每页内部的骨架见
> [page-templates.md](page-templates.md)。

## 为什么必须先规划页集

一份多页文档最容易出的两种毛病——**重复**（架构页和能力页各讲一遍模块）与
**遗漏**（README 吹的三个卖点只写了一个）——都不是写作问题，是**没有先定页集**。

所以顺序固定：**先产出页面清单，再写正文**。清单不是草稿，它直接落进首页
`README.md` 的索引表，成为最终产物的一部分（零额外文件、零收尾删除）。

## 产出形态

```
<输出目录>/
├── README.md          # 首页：这是什么 + 页面索引表 + 建议阅读顺序 + 依据版本
├── overview.md        # 项目是什么、解决什么问题、给谁用、技术栈
├── architecture.md    # 系统怎么组织（图为主）
├── <topic>.md         # 各主题页，一页一个问题
└── assets/*.svg       # 可选：复杂结构图落成独立 SVG
```

图默认是**内嵌在各页 `.md` 里的 Mermaid 代码块**；只有分层、左右对比、节点过多等
Mermaid 自动布局排不好的图，才落成 `assets/*.svg` 并在正文引用（选型见
[diagrams.md](diagrams.md)）。**"Markdown 产物"不等于"纯文字"**——图与表是一等表达手段，
只有确实没有形状的内容才通篇是散文。

- **首页 `README.md` 是入口而非概览正文**：概览内容放进 `overview.md`，
  首页只负责"这是谁 + 有哪些页 + 按什么顺序读"。
- **主题页主题语义命名**：`architecture.md`、`data-model.md`、`deployment.md`、
  `plugin-system.md`、`memory-system.md`……**不用 `01-`/`02-` 序号前缀**
  （序号一改就全错，且排序交给人读的索引表就够了）。
- **页数由内容决定，不凑数**：小项目 3-4 页正常；模块多的大项目 8-12 页。
  一页如果撑不起"读完知道一件事"，就并进相邻页。

## 页面清单（规划阶段的唯一产物格式）

在首页索引表里落成这张表，写正文前就写好：

```markdown
| 页面 | 一句话职责 | 重要度 | 依据文件 |
|------|-----------|--------|---------|
| [overview.md](overview.md) | 这个项目解决什么问题、给谁用 | 高 | `README.md`、`go.mod` |
| [architecture.md](architecture.md) | 系统分成哪几层、请求怎么流过去 | 高 | `internal/`、`cmd/` |
| … | … | … | … |
```

四项各自的作用：

- **一句话职责**：写完要能自检"这页和别的页讲的是不是同一件事"。**两页职责重叠就必须合并**。
- **重要度**（高/中/低）：只用于决定**先写哪页、写多细**，不设篇幅上限。
- **依据文件**：这页打算去哪几个文件/目录取证。写正文时不会现找；
  **动笔前就能发现"这页没有足够的源码支撑"**——那就该并页或降级，而不是硬写。
- **关联页**：可在正文里加"详见 `xxx.md`"的过渡句，让页面之间连成一条阅读线。

## 怎么定页集

### 提名来源（按权重）

1. **README 自述能力点（权重最高）**：作者浓墨重彩宣传的功能，就是"读者想知道什么"的信号。
   顺着它去源码核实——属实且够写一页就成页；源码没有支撑的，**写进"现状与边界"而不是当成能力**。
2. **项目形态**：不同形态的项目天然带不同的页（见下表）。
3. **系统的形状**：凡是有"一条链、一套状态、一组实体、一个扩展点"的地方，都值得一页。

### 项目形态 → 候选页面

| 项目形态 | 典型页面 |
|---------|---------|
| 可部署服务 / 基础设施 | `architecture.md`、`deployment.md`、`configuration.md`、`observability.md` |
| 有持久化的系统 | `data-model.md`、`data-flow.md` |
| 库 / SDK / 框架 | `concepts.md`（核心概念模型）、`api-design.md`、`extension.md`、`recipes.md`（常见用法） |
| CLI 工具 | `concepts.md`、`commands.md`、`configuration.md` |
| 智能体 / AI 应用 | `agent-loop.md`、`tool-calling.md`、`memory-system.md`、`model-integration.md` |
| 前端 / UI | `architecture.md`、`state-management.md`、`rendering.md` |
| 编译器 / 运行时 | `pipeline.md`（前端到后端）、`type-system.md`、`runtime-model.md` |

这张表只做提名，**不做强制**。README 点名而表里没有的关注面，同样要写。

### 页集自检

- [ ] 每页一句话职责能说清，且**互不重叠**
- [ ] README 宣传的核心能力，每一条都能落到某一页；落不到的要交代原因
- [ ] 每页的"依据文件"都真实存在，且**足以支撑一页**（撑不起就并页）
- [ ] 读者按索引顺序读一遍，能回答"这是什么、怎么运转、怎么用/怎么部署"
- [ ] 没有"为了凑页数"而拆出来的薄页

## 首页 `README.md` 骨架

```markdown
---
title: <项目名> 项目文档
description: 面向使用者的 <项目名> 文档：<覆盖的主题一句话>。
---

# <项目名>

<一段话：这个项目是什么、解决什么问题、给谁用。两三句，不铺垫。>

**本文档依据**：<ref>（<短SHA>），<日期>

## 页面索引

| 页面 | 内容 | 重要度 |
|------|------|--------|
| [overview.md](overview.md) | 是什么、解决什么问题、技术栈 | 高 |
| [architecture.md](architecture.md) | 系统架构与请求链路 | 高 |
| … | … | … |

## 建议阅读顺序

1. [overview.md](overview.md) —— 先建立整体印象
2. [architecture.md](architecture.md) —— 再看系统怎么组织
3. …（按读者目的给出分叉：只想用 → 跳到 `usage.md`；要部署 → 跳到 `deployment.md`）

## 现状与边界

<这个项目**不做什么**、当前的限制、已知的未完成项。诚实写，不吹不黑。>
```

「现状与边界」不是可选项：一份只讲优点的文档，读者无法据此做技术选型。
