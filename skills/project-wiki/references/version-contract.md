# 版本契约：这份文档描述的是哪个版本

> 由 SKILL.md「执行流程主干」的 step 0（定基线）与 step 0.5（版本契约）按需加载。
> 本文件承载：**基线为什么必须先定、为什么只记一处、契约行怎么写怎么核、陈旧冲突怎么裁决、
> 校验根怎么落地、旧产物没有契约行时怎么办**。

## 为什么基线必须先定，且只记一处

行号只在确定的快照上成立。`scripts/check-all.mjs` 对依据行的校验是"**路径真实存在 + 行号落在该文件行数范围内**"，
这两件事都相对某一棵具体的源码工作树才有意义——换了树，校验通过也无意义。

契约行（首页那行版本声明）同时是三样东西：

1. **读者口径声明**：读者据此知道"我读的是哪一版"，选型与升级判断都建立在这上面；
2. **校验根的声明**：它指明这次校验该在哪棵工作树上进行；
3. **更新模式的 diff 左端**：下次随上游版本更新时，`git diff <旧>..<新>` 的起点就是它（见 [update-flow.md](update-flow.md)）。

**只记一处**是刻意的：本 skill 不维护 `CHANGELOG.md`，每次只写当前基线。
两处记录必然产生两个真源，而它们迟早会不一致，读者不知道该信哪个。

## 契约行格式与核对

位置：首页 `README.md` 的开场一段之后，**全文唯一一处**。

```markdown
**本文档依据**：`v1.2.3`（`abc1234`，2026-08-14）
```

三元组各自的作用与来源：

| 元素 | 写法 | 来源 |
|------|------|------|
| ref | 一个 code span，如 `` `v1.2.3` ``（分支基线则为分支名） | `scripts/select-baseline.mjs` 选定结果 |
| 短 SHA | 一个 code span，如 `` `abc1234` `` | 该 ref 指向的提交 |
| 日期 | ISO 日期，如 `2026-08-14` | **取自 git**（该 tag / commit 的日期），不由模型生成 |

ref 与短 SHA **各用一个 code span**，括号与逗号用全角。日期必须来自 git：
写日期与写版本号一样，属于「不可编造清单」范围（见 [grounding-light.md](grounding-light.md)）。
（门禁对反引号有容错——三元组齐全、日期合法即可解析；但请照上面的形态写，与依据行风格一致。）

核对方式——把校验根与自述基线一起交给门禁：

```bash
node scripts/check-all.mjs <输出目录> --source-repo <基线工作树> --expect-baseline <ref>
```

| 输出码 | 档 | 什么情况 |
|--------|----|----------|
| `[DOC-BASELINE-MISSING]` | note | 首页没有契约行 |
| `[DOC-BASELINE-FORMAT]` | note | 契约行在，但解析不出完整三元组（ref / 短 SHA / ISO 日期缺一，或写成了别的形状） |
| `[DOC-BASELINE-UNRESOLVED]` | note | ref/SHA 在该工作树里不存在、SHA 与 ref 对不上、日期与 git 不符；**缺 git 或 `--source-repo` 不是 git 仓库时也是这一条**（无法核对即如实报出，不静默当通过） |
| `[DOC-SRC-BASELINE-MISMATCH]` | note + **结论降级** | `--source-repo` 的 HEAD ≠ 自述基线，或压根没传 `--expect-baseline` |

这几条**都是 note，不阻断**（严重度规则见 [grounding-light.md](grounding-light.md)「严重度与归级判据」）。
代价由「结论不越权」补偿：未在自述基线上校验时，输出会**如实说明"已校验项不覆盖行号是否属于该版本"**，
而不是假装通过。也就是说，**不传 `--expect-baseline` 不会让门禁失败，但会让"校验通过"这句话失去部分含义**。

## 怎么选：跑脚本，不凭印象

```bash
node scripts/select-baseline.mjs <本地路径|远端URL> [--ref <ref>] [--package <名>] [--json]
```

优先级：**稳定 tag > 稳定分支（`release*` / `stable*` / `maintenance*` / `1.x`）> 默认分支（`main` / `master` / 远端 `HEAD`）
> 无 `main`/`master` 兜底矩阵**。

脚本只读，输出选定结果与落地建议命令；**退出码 2 = 需要用户确认或选择**（陈旧 / 歧义），走下面的结构化裁决。

## 陈旧冲突与三选一裁决

**含义**：脚本选出的"最高稳定 tag"如果落后默认分支超过阈值（默认 **500 commits / 730 天**，可用
`--stale-commits` / `--stale-days` 调整），会打 `[BASELINE-STALE]` 并要求确认。

为什么说它是**冲突**而不是一条警告：两个都合理的目标指向了不同的 ref。

| 目标 | 它要求基线是 | 陈旧时会发生什么 |
|------|--------------|------------------|
| 读者的现实 | 读者能下载、能安装的**发布版** | tag 太老 → 文档描述的是一年前的项目，读者据此选型会误判 |
| 项目的现状 | 项目**现在的样子**（默认分支） | 没有对应发布物，接口与行号随开发漂移 |

本 skill 的读者**不读源码**，没有"点开源码自己分辨"的兜底手段，所以这个冲突必须当场裁决。

**三选一（结构化，不做开放式提问）**：

1. **接受陈旧 tag** —— 基线仍用该 tag，并在正文写一句**读者可见的声明**：
   "本文档基于 `v1.2.3`（2026-08-14），晚于该版本的变更未涵盖。"
2. **改按默认分支** —— 基线改为默认分支，产物声明"**未发布版本**"（契约行 ref 写分支名与 SHA）。
3. **用户给 ref** —— 按用户指定的 ref 撰写，声明"按用户指定 ref 撰写，非稳定版"。

裁决**发生在选基线那一刻**，结果只体现在契约行 + 那句声明里；不存在"事后补一个新鲜度位置"的机制。

## 无稳定 tag 时

仓库没有稳定 tag 是常态，按**兜底矩阵**逐级下落（远端 `HEAD` 符号引用 → 本地 `origin/HEAD` →
当前分支（仅当它不是特性/临时分支）→ 常见主干名 → 最近提交的非特性分支 → 最新 tag），
选定后产物声明"**未发布版本**"。

命中 `[BASELINE-AMBIGUOUS]`（多包 tag 并列无法唯一定位项目版本、无任何可依基线）时，
同样走**结构化二选一**：列出候选与各自代价（"按 A 更稳但可能漏掉新版本；按 B 最新但行号会随开发漂移"），
请用户选择或直接给出 ref。

**禁止**把 detached HEAD 或特性分支（`feat/*`、`wip/*`…）当基线——那可能是任何人的半成品。

## 校验根 = 该基线工作树

- `--source-repo` **必须**指向基线工作树（`realpath` 后的绝对路径），并且与 `--expect-baseline` 一起传，
  才构成一次**有效校验**。
- 工作树已经等于选定基线时**跳过检出**，不折腾。
- 产物落点见 [landing.md](landing.md)：它**必须在这棵工作树之外**。产物落在 `source_repo` 内是唯一以
  **error** 档拦住的检查（`[DOC-DOCROOT-IN-SRC]`）。

## 落地动作：从 ref 到可读工作树

选定 ref 只是元数据，校验需要一份磁盘工作树。默认动作是最轻的那种——**让基线成为"进入"的起点，而不是事后回退**：

| 输入形态 | 工作树状态 | 默认动作 | 理由 |
|----------|-----------|----------|------|
| 远端 URL（最常见） | — | `git clone --branch <ref> --depth=1 <url> <dest>` | 基线即克隆起点，一次到位；tag 同样支持 `--branch`。**禁止裸 `--depth=1`**（丢 tags、锁死默认分支）；需要 diff 历史时改 `--filter=blob:none` 或不带 `--depth` |
| 本地路径 | 干净 | 就地 `git checkout <ref>` | 最省事。**进入前记下原 HEAD（分支名或 SHA），收尾恢复**，并向用户报告这两步 |
| 本地路径 | 脏（有未提交改动） | **不静默覆盖**：① `git worktree add <tmp> <ref>`（非破坏性，推荐）② 经用户同意后 `git stash` + `checkout` + 收尾 `stash pop` | 用户改动可能与本任务无关，本 skill 无权丢弃 |
| 本地路径 | git 过旧 / 不支持 worktree | `git archive <ref> \| tar -x -C <tmp>` | 有独立工作树可读，代价是拿不到 `git diff` 历史 |

收尾：恢复原 ref（worktree 场景 `git worktree remove <tmp>`），并在交付说明里写清"文档在 `<ref>` 上完成、原工作树已恢复"。

## 旧产物没有契约行

老产物（本约定生效前产出的 wiki）没有契约行时：

- 找不到 diff 左端 → 更新时退化为**代码快照比对**；
- 必须在产出中显式声明"**本次依据代码快照比对，非官方 release 差异**"；
- 并在**交付清单里点名这次退化**（见 [update-flow.md](update-flow.md)）。

不静默退化的原因与其余「反静默」机制一致：读者与下次更新都要知道"这次的差异依据是什么强度"。
