# 更新已有分析

> 当目标目录已有该项目的架构分析（或用户说"更新一下""跟到新版本"）时，由 SKILL.md 六步主干末尾的路由进入。核心：**先读旧文，再按上游变化改，只动受影响的部分。**

## 三条铁律

1. **先读再写**：不读旧文就重写 = 丢失已有判断、重复劳动。
2. **差异驱动**：每处改动都要能追溯到上游 diff、release notes 或明确的用户要求。没有依据的"顺手优化"不做。
3. **结构保护**：已有章节标题与顺序原样保留；新增内容用 `###` 子节，不重排全局。

## 更新流程

1. **定位旧文与基线**：读文档开头的基线行；没有记录就查 `git log`/tag，或按代码快照比对（并在文首声明）。
2. **取上游变化**：
   - 有 git 历史与基线：`git diff <旧>..<新> --stat` → 只读变更文件；
   - 有 release notes：按条目映射到文档章节；
   - 都拿不到：对比当前代码与旧文描述，只改明显不符的地方，并声明依据。
3. **列影响清单**：哪些章节/决策卡/模式卡会变；哪些不变。
4. **只改清单内的内容**：
   - 数字/版本/模块名变化 → 就地更新；
   - 新增能力 → 新 `###` 小节或新决策卡；
   - 删除/废弃 → 在"边界、风险与开放问题"里说明，不悄悄抹掉历史。
5. **更新基线行**，必要时在文末加一行"本次更新依据"。
6. **重跑校验**：图用 `check-mermaid.mjs` / SVG 拓扑审计；有证据附录才跑 `verify-references.mjs`；零索引模式抽查新增模块名/路径。

## 范围控制

| 变更 | 处理 |
|---|---|
| 版本号、依赖、默认值 | 就地改，别改结构 |
| 新增一个能力 | 先判断它是否改变架构判断；只加事实不构成更新 |
| 新增一个核心决策 | 加一张决策卡；必要时调整"可迁移手法" |
| 模块拆分/合并 | 可以改"模块责任矩阵"，但仍保留旧章节的叙事位置 |
| 只是重构、无行为变化 | 通常不改；最多在基线行说明 |
| 上游大版本、架构换血 | 与用户确认是否按"全新分析"重写，别默默覆盖 |

## 版本变更记录（可选）

- 默认在文首基线行更新即可，不强制单独 `CHANGELOG.md`。
- 用户要求持续跟踪、或更新频繁时，再建 `CHANGELOG.md`：最新版本在最前，每条写"依据 + 变化摘要"，旧条目原样保留。
- 不要把 changelog 写成第二份分析；它只记录"这一版改了什么判断"。

## 什么时候该重写

- 上游架构发生换血（分层/协议/存储模型变了），旧文的决策卡大面积失效；
- 旧文只有功能罗列、没有判断，更新价值低于重写；
- 用户明确要求"重新来一遍"。

重写前先与用户确认；若旧文仍有参考价值，保留原文件并另起新文件，不要原地覆盖到无法回溯。

## 常见错误

| 错误 | 纠正 |
|---|---|
| 不看旧文，直接生成一份新的 | 先读；差异驱动 |
| 借更新之名重排全部章节 | 结构是资产，只加不改 |
| 把版本号改了就算更新 | 判断有没有变；没变就不改 |
| 旧结论被推翻却悄悄删掉 | 在风险/边界里说明为何推翻 |
| 更新后不重跑图校验 | 结构改了图也可能失效，重跑 |
