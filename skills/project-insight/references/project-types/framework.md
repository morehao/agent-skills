# framework 类型规格（framework）

> 适用于：Web 框架 / SDK / 基础库 / CLI / 编译器 类项目。
> 判定信号见 [../dimension-triggers.md](../dimension-triggers.md)「类型判定与分流」；本规格在通用默认规格（[_default.md](_default.md)）基础上**追加** framework 特有要求，不得放宽通用铁律（真源验证 / mermaid 校验 / kb_repo 判定 / 增量铁律 / 写作规范 / 质量红线 / 索引同步 / 规模门控）。可叠加：语言惯用法（按项目语言触发，见 [../dimension-triggers.md](../dimension-triggers.md)「语言惯用法维度」）。

## 固定结构块（硬规格）

### 产出形态

通用产出形态 / 分文件判定 / 信息密度分配 / 索引约定见 [_default.md](_default.md)，本规格仅追加 framework 特有要求：

- 必拆子文档候选（命中并够深才拆，主题语义命名、无 `01-` 序号前缀，按关注面）：
  - `extension.md`：扩展点机制（中间件链、路由表、插件系统、生命周期 Hooks）
  - `api-design.md`：公共 API 与类型设计、错误约定、向前兼容策略
  - 语言惯用法文档（见必含要素块，主题语义命名）：`goroutine-model.md` / `ownership-lifetimes.md` / `typesystem-depth.md` 等
- 小而专的库可维持单文件 `README.md`；大框架按上述关注面拆多文档。
- 拆出子文档后按其索引约定回写（见 `_default.md`）。

### 信息密度分配

- 承接 `_default.md` 的 README 概览口径；README 架构总览侧重「框架内核 vs 扩展层」的分层（核心内部环路 / 对外扩展契约）。
- 子文档承载扩展机制、公共 API 设计、语言惯用法等深度关注点。

## 必含要素块（硬规格）

在通用必含要素清单（`_default.md`：根因 / 概览 / 架构 / 链路 / 深挖 / 全局关联 / 真源引用）之外，framework 类**必须**额外覆盖以下硬规格；可放任意标题任意顺序，顺序交给叙事主线，但逐项齐全才算完成：

- **扩展点机制**：中间件链 / 路由表 / 插件系统 / 生命周期 Hooks。讲清用户代码如何在何时注入、用什么机制被调度（如 Koa 洋葱模型、Hono 路由基数树、Express 线性中间件、Vite 插件生命周期）；每条论断带 `文件:行号`，命中「强制图位清单」（见 [../writing-guide.md](../writing-guide.md)）即给 `sequenceDiagram`/`graph`（如一次请求穿过中间件链的时序）。
- **公共 API 设计**：类型系统（对外类型的边界与约束方式）、错误约定（错误如何浮现、如何传播、如何被调用方识别）、向前兼容策略（API 版本化 / 废弃 / 语义化版本）。判断这些设计如何反映框架对用户的心智模型。
- **语言惯用法**（高价值深挖）：Go 并发/接口组合、Rust 所有权/Result、TS 类型系统深度使用等。每个论断带 `文件:行号` + **"为什么选这个模型"** 的权衡，落在设计语境（该语言特性如何支撑框架的扩展或性能承诺），不写成语言教科书（不讲语言特性本身是什么，只讲在此处的取舍）。

每篇子文档满足通用四要素（核心结构 / 执行流程 / 设计决策 / 依赖）+ `文件:行号` 真源引用，且每篇至少 1 张属于本关注面的核心链路图。

## 自由纵深块（软区）

- 「值得学什么」落点：扩展性与性能的权衡（简单性 / 灵活性 / 性能 三角）、API 设计案例、语言惯用法的迁移价值。
- 常见坑：
  - 把"用了中间件模式"写成 What 缺 Why——应讲清该扩展机制解决了什么约束、替代方案为何不选。
  - 把语言主题写成教科书而非设计决策——聚焦该语言特性在此框架中承担的角色与权衡，不铺陈语言通识。
  - 只讲"支持哪些扩展点"，不讲扩展点之间的边界与调度成本。
- 深挖指引：比较扩展机制（洋葱 vs 线性 vs 管道，如 Koa / Express / 管线式管道）、是否把 API 演进策略（版本化 / 废弃 / 兼容保证）讲清；深度不足标 `[WIP]`/`TODO`，不硬凑。
