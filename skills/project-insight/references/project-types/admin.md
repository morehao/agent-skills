# admin 类型规格（admin）

> 适用于：后台管理系统 / 管理面板 / 内网运营平台 类项目。
> 判定信号见 [../dimension-triggers.md](../dimension-triggers.md)「类型判定与分流」；本规格在通用默认规格（[_default.md](_default.md)）基础上**追加** admin 特有要求，不得放宽通用铁律（真源验证 / mermaid 校验 / kb_repo 判定 / 增量铁律 / 写作规范 / 质量红线 / 索引同步 / 规模门控 / 数据模型探测）。可叠加：framework（暴露插件/扩展接口时）。

## 固定结构块（硬规格）

### 产出形态

通用产出形态 / 分文件判定 / 信息密度分配 / 索引约定见 [_default.md](_default.md)，本规格仅追加 admin 特有要求：

- 必拆子文档候选（命中并够深才拆，主题语义命名、无 `01-` 序号前缀）：
  - `data-model.md`：数据模型（`goadmin_*` 系统表 / `migrations` / `models` 实体命中即触发，按数据模型五要素成文）
  - `auth-rbac.md`：认证与权限（RBAC 模型、菜单/权限/角色、审计日志）
  - `deployment.md`：部署（Docker / 安装器 / 云，见通用「可部署项目」判据）
- 拆出子文档后按其索引约定回写（见 `_default.md`）。

### 信息密度分配

- 承接 `_default.md` 的 README 概览口径；README 架构总览侧重前后端分层（管理端 SPA ↔ 服务端）与核心模块导读。
- 子文档承载数据模型、权限模型、部署等深度关注点；每篇满足通用四要素（核心结构/执行流程/设计决策/依赖）+ `文件:行号` 真源引用，且每篇至少 1 张属于本关注面的核心链路图。

## 必含要素块（硬规格）

在通用必含要素清单（`_default.md`：根因 / 概览 / 架构 / 链路 / 深挖 / 全局关联 / 真源引用）之外，admin 类**必须**额外覆盖以下硬规格；可放任意标题任意顺序，顺序交给叙事主线，但逐项齐全才算完成：

- **权限与 RBAC 模型**：用户 / 角色 / 菜单权限 / 按钮权限 / 数据权限、权限数据模型。（RBAC 表设计如何落地：role-permission 关联、数据权限范围如按机构/部门/自定义过滤；每条论断带 `文件:行号`；权限判定链路命中「强制图位清单」（见 [../writing-guide.md](../writing-guide.md)）即给 `sequenceDiagram`/`graph`，如"请求 → 认证 → 鉴权 → 数据范围过滤"的时序，不写纯文字长段）
- **数据模型**：核心业务表 + 系统表（session / oper log / role / permission / menu），按数据模型五要素成文（不只列字段，讲存储选型 / 演进 / 读写路径）。
- **部署与运维**：Docker Compose / 云部署形态、初始化流程（建库建表 / 种子数据 / 超级用户）、配置管理（环境变量 / 配置文件 / 密钥）。
- **前后端分层**：管理端 SPA 与服务端的分工、接口契约、状态管理（谁渲染菜单路由、谁做权限判定、权限如何下发到前端）。

## 自由纵深块（软区）

- 「值得学什么」落点：权限模型如何落到数据表（RBAC 表设计及其取舍）、租户 / 多组织的数据隔离、审计日志与操作追踪。
- 常见坑：
  - 把数据模型写成字段清单罗列——应讲存储选型 / 演进 / 读写路径（Why>What），而不是罗列表字段。
  - 权限只写前端按钮显隐，忽略后端校验与数据权限过滤——前后端需同时覆盖。
- 深挖指引：比较不同 admin 框架的权限 / 去构建方案，提炼可迁移的 RBAC 设计与部署形态；深度不足标 `[WIP]`/`TODO`，不硬凑。
