# 探索方法：从仓库到架构判断

> 由 SKILL.md 六步主干的 step 1（快速建模）与 step 3（垂直切片）按需加载。目标不是"读完仓库"，而是**用最少的阅读建立可证伪的架构模型**。

## 先判原型，再定策略

同一个仓库，原型不同，值得读的东西完全不同。读业务代码之前，先用根目录信号判一个主原型（可叠加副原型）：

| 原型 | 典型信号 | 探索重心 | 默认必答 |
|---|---|---|---|
| 后端服务 / 网关 | `cmd/*/main.go`、`routes/`、`api/`、Dockerfile + 常驻进程 | 请求生命周期、状态与存储、失败传播 | 一次请求怎么进来、怎么出去 |
| 框架 / 库 / SDK | 导出面（`src/index.ts`、`pkg/`、`lib/`）、无 main、扩展点 | 扩展机制、公共 API 契约、兼容策略 | 用户代码在何时、以什么方式被调度 |
| CLI / 开发工具 | `bin/`、`cmd/`、参数解析、插件目录 | 命令生命周期、配置解析、退出码 | 一条命令从参数到副作用 |
| 数据库 / 存储引擎 | WAL、LSM/B+Tree、page cache、compaction | 读写路径、崩溃恢复、一致性 | 一次写入何时持久、一次读取命中什么 |
| AI Agent / LLM 应用 | agent loop、tools、prompt、memory、session | 循环与停止条件、上下文管理、工具可靠性 | 一轮对话里谁决定下一步 |
| AI 基础设施 | 推理服务、batching、KV cache、向量索引、RAG 管线 | 调度与吞吐、召回与成本 | 一次推理/检索的端到端路径 |
| 基础设施 / DevOps | controller/reconcile、CRD、Helm、Terraform | 控制循环、依赖图、故障域 | 期望状态如何收敛到实际状态 |
| 前端应用 | 组件树、状态管理、路由、渲染层 | 状态与渲染、数据获取、交互边界 | 一次交互如何触发重渲染 |

判定只用 5 分钟：README 自述 + 顶层目录 + 构建清单。判错不致命，**但不要跳过**——它决定后面读什么。

选定主类型后，打开 [types/README.md](types/README.md) 取该类系统的提问清单（挑 8–10 个，不逐条填表）。清单只负责“问对问题”，不规定章节，也不要求逐项覆盖。

## 快速建模（时间盒 20–30 分钟）

按顺序，每步只取"能形成判断"的信息：

1. **README / 官方文档**：摘出作者自述的核心能力与卖点（后面要逐条对账），一句写出根因。
2. **目录树**：两三层即可；用目录名推断模块边界，但**不把目录结构当架构**——它只反映团队如何摆放文件。
3. **构建与运行入口**：`package.json` / `go.mod` / `Cargo.toml` / `Makefile` / Dockerfile / compose；找 `main`、server 启动、CLI 入口。
4. **配置与部署形态**：有几种装配方式（单机 / 集群 / 云 / 嵌入）；配置从哪来。
5. **测试与示例**：测试常暴露真实调用方式；示例常暴露设计意图。

产出 10 行以内的"心智模型"：这是什么、边界在哪、核心部件有哪几个、主链路是什么。写不出来就继续读，别急着开写。

**不读什么**：生成代码、依赖锁文件、大段测试夹具、样式与文案、与主链路无关的工具脚本。读它们不会让判断更好，只会耗尽上下文。

## 垂直切片：用 1–2 条链路理解系统

架构不是靠"每个模块读一遍"拼出来的，而是靠**一条端到端路径**串起来的。按原型选切片：

| 原型 | 切片 |
|---|---|
| 后端 / 网关 | 一次请求：接入 → 鉴权 → 路由 → 业务 → 存储 → 响应 |
| 框架 / SDK | 一次典型调用：用户代码 → 注册/扩展点 → 框架调度 → 回调 |
| CLI | 一条命令：参数解析 → 配置 → 执行 → 输出/退出码 |
| 存储 | 一次写 + 一次读：入口 → 日志/缓存 → 持久化 → 查询 |
| Agent | 一轮任务：输入 → 规划 → 工具调用 → 观察 → 停止 |
| 基础设施 | 一次 reconcile：事件 → 期望状态 → 差异计算 → 执行 |
| 前端 | 一次交互：事件 → 状态更新 → 渲染 → 副作用 |

走链路时记录四样东西，直接决定后面能不能写出决策卡：

1. **经过的部件**与每跳的职责；
2. **状态变化**：谁持有、何时写、谁是真相源；
3. **分叉与异常**：失败、重试、超时、降级、回滚；
4. **沿途的取舍**：为什么在这里切、为什么不合并到上一跳。

链路上每遇到一个"看起来多此一举"的设计，先标记为候选决策，别急着评价——它可能在守一个边界情况。只走主路径不够，**至少看一条失败路径**。

## 通用提问清单（按项目取 8–10 个）

1. 系统边界在哪？什么在系统内，什么明确交给外部？
2. 一个请求/任务从进入到返回，经过哪些部件？
3. 状态存在哪？谁是真相源？缓存与持久化如何分工？
4. 允许的依赖方向是什么？哪些依赖是被刻意禁止的？
5. 并发模型是什么？共享什么、隔离什么？
6. 失败如何传播、重试、降级、恢复？
7. 扩展点在哪？用户/插件代码如何注入、何时被调用？
8. 配置从哪来？不同环境/部署形态如何隔离？
9. 数据与协议如何演进？兼容与迁移策略是什么？
10. 信任边界在哪？认证、授权、租户隔离落在哪一层？
11. 可观测性靠什么？出问题时先看什么？
12. 哪些设计是为规模/性能做的，哪些是为简单性做的？

能答的写成判断，答不上的写进"边界、风险与开放问题"，**不要用泛泛而谈填空**。

## 大仓策略：按主题切，不追求覆盖率

有效代码超过单次上下文能承载的量（经验线 ~5 万行，但以"读不完"为准）时：

1. **先画全局骨架**：边界、主要部件、依赖方向。骨架由主 agent 完成，不外包。
2. **按主题切 3–5 片**：数据流 / 扩展机制 / 并发与调度 / 存储与一致性 / 部署与运维。每片对应一个"读者会问的问题"，不是目录。
3. **并行时只派"找证据 + 提判断"的任务**：要求子代理返回"链路 + 候选决策 + 不确定项"，不要返回文件摘要。
4. **主 agent 做三件事**：合并叙事、交叉验证关键论断、把重复/矛盾的点收敛成决策卡。
5. **抽样而非全覆盖**：每片读 30–60% 的关键文件即可形成判断；覆盖率不是目标，**判断能否被证伪**才是。读不到的部分写进"未覆盖"。

不要为每个模块产出一篇文档；主题分册只在"每篇都能独立回答一个设计问题"时才成立。

## README 自述对账

README 是作者"想让读者看到什么"的信号，不是事实。逐条列出其宣称的核心能力：

- **属实且够深** → 进入候选主题，可能就是一个决策卡；
- **属实但浅** → 一句带过，不单独成章；
- **过时/夸大/源码无支撑** → 写进"边界、风险与开放问题"，这是高价值发现；
- **README 没提但代码很特别** → 也值得挖，作者未必意识到自己做了什么。

## 常见失败

| 失败 | 后果 | 纠正 |
|---|---|---|
| 从目录结构直接推架构 | 把"文件摆放"当"设计" | 用链路验证依赖方向 |
| 先读实现细节再找问题 | 陷入局部，写成一堆代码审查 | 先定 8–10 个问题，再带着问题读 |
| 只走 happy path | 看不到失败处理与边界，决策卡空洞 | 至少追一条错误/超时/降级路径 |
| 追求覆盖率 | 上下文耗尽，产出文件摘要 | 抽样 + 主题切片 + 显式"未覆盖" |
| 把 README 当事实 | 复述宣传，甚至写出不存在的模块 | 逐条对账，冲突写进风险 |
| 读完就写 | 没有判断，只有描述 | 先写 3 张决策卡草稿，再动笔成文 |
