# 落地目标判定与入库约定

> 由 SKILL.md「执行流程主干」的 step 0（落地目标判定）/ step 1（模式判定）/ step 8（索引同步）按需加载。承载：输入处理、`kb_repo` 判定、模式判定、输出规范（入库约定）——即"解读落到哪里、怎么组织、怎么同步索引"的全部约定。

## 输入

### 源码：本地绝对路径

默认输入是本地源码仓库的绝对路径，如 `/Users/me/src/wukong`：

1. 解析为统一 `source_repo`，用 `os.path.realpath` 规范化并确认存在，作为所有真源引用验证的根。
2. 用户只给远端地址（如 `github.com/xx/foo`）时，**先定基线再克隆**（step 0.5，见 [version-baseline.md](version-baseline.md)）：`git ls-remote`（`--tags --refs` / `--heads` / `--symref HEAD`，只枚举不下载）→ 按优先级选定 ref → `git clone --branch <ref> --depth=1` 落地。**禁止裸 `--depth=1`**（丢 tags、锁死默认分支）；需要 `git diff` 历史时用 `--filter=blob:none`。真源验证必须读本地真实文件，不能对着远端记忆写；网络不可用则明确告知并请求本地路径。
3. **本地路径同样要定基线**：按 [version-baseline.md](version-baseline.md) 选定 ref 后就地 `git checkout <ref>`（脏工作树**不静默覆盖**，走 `git worktree` 兜底），`source_repo` 即该基线工作树；收尾恢复原 HEAD 并报告。
4. 所有 `文件:行号` 引用以 `source_repo` 为根校验，防路径穿越。

### 临时分析判别

默认按"入库"规范执行（完整目录树 + 索引同步）。若用户只要一段临场解读、明确不落进知识库仓库，产出主体解读即可，并主动告知"本次未做索引同步、未做落地目录判定"；否则默认走完整入库流程（含下方 `kb_repo` 判定）。

## 落地目标：知识库仓库判定（自动 + 确认兜底）

产出目录**不默认等同于**执行时的当前工作目录，先做判定，确认后记为 `kb_repo`。

**目标结构模式：** `{分类}/{项目名}/README.md`（多关注面项目 + 主题式深读子文档），如 `IM/wukong/README.md`、`IM/wukong/architecture.md`。顶层 `README.md`（总索引）为加分项，非必要条件。

**判定信号（满足任一即视为"当前目录 = 目标知识库仓库"）：**

1. **结构扫描命中**：对当前目录深度为 2 扫描，存在至少一组 `{目录}/{目录}/README.md`，且该二级目录不是常见源码工程目录名（排除 `src`、`node_modules`、`cmd`、`internal`、`.git` 等，避免把源码仓库自身的 `pkg/utils/README.md` 误判为知识库结构）。
2. **显式索引命中**：顶层 `README.md` 内容含 `[分类](分类/README.md)` 或表格形式的模块索引链接。

**排除信号（命中即不匹配，禁止直接落地）：**

- 当前目录即本次 `source_repo` 或其子目录。
- 当前目录是具体编程项目源码根（存在 `package.json`/`go.mod`/`Cargo.toml` 等工程清单且无 md 知识库特征）。
- 当前目录为空且无任何 git/README 线索。

**执行逻辑：**

```
判定当前目录
├─ 命中判定信号 且 未命中排除信号 → 以当前目录为 kb_repo，落地
├─ 命中排除信号 → 停止，说明原因 → 走"用户选择"分支
└─ 两类信号都未命中（拿不准） → 展示目录树摘要 → 走"用户选择"分支
```

**用户选择分支（结构化二选一，不做开放式提问）：**

1. **指定其他目录** —— 用户提供已存在的知识库仓库绝对路径作 `kb_repo`；远端地址先 clone；不符合 `{分类}/{项目}/README.md` 结构则视为全新知识库仓库，按规范初始化。
2. **就在当前目录下新建** —— 以当前目录为 `kb_repo`，视为全新知识库仓库起点，按输出规范创建 `{分类}/{项目}/README.md` 并新建顶层 `README.md` 索引雏形。

示例确认话术：

> "当前目录 {cwd} 未检测到 `分类/项目/README.md` 这类知识库结构（原因：{具体原因}）。是否：① 指定一个已有知识库仓库路径 ② 就在当前目录 {cwd} 下新建这套知识库结构。请选择，或直接给出目标路径。"

> **特别提示：** 若由**排除信号**触发（如当前目录被识别为源码工程根），选项②不作为默认推荐，额外提示："注意：当前目录检测到 {go.mod/package.json 等}，看起来是代码仓库而非知识库仓库，在这里新建解读结构可能不是你要的，请确认。"

用户选定后记为 `kb_repo`，本次会话内模式判定、落地、索引同步均以此为根，不再重复询问。

## 模式判定

前提：`kb_repo` 已确认。

依据 `kb_repo/{分类}/{项目}/README.md` 是否已存在（或别名 grep 命中）：

- **存在（或 grep 命中）→ 默认增量模式**（必须先读现有文档再动笔，走 [flow-incremental.md](flow-incremental.md)）。
  - **例外：用户明确要求全量 / 重新解读**（如"重写""全量重新分析""不要增量，重新来过"）→ **先删除既有解读，再走全新分析模式**（[flow-new.md](flow-new.md)）：
    1. 删除前与用户确认删除范围：`{分类}/{项目}/` 下全部文档（README + 所有子文档 + 图），以及分类索引行、README「子文档索引」章节。
    2. 删除后同步清理索引：`{分类}/README.md` 删掉该项目行；若该分类下再无项目，处理顶层 `README.md` 的分类条目。
    3. 再按全新流程从零产出。删除同样是落盘动作，不代为 git commit，列入变更清单。
- 不存在 → 在 `kb_repo` 下按 `*/*/README.md` 全局扫描 + grep 项目名/仓库地址/别名，排除"已用别的分类名或别名建过索引"（如 wukong 被归到 `chat/` 而非 `IM/`）。
  - grep 命中 → 分类归属不一致导致的漏判，按上方"存在"分支处理（默认增量；用户明确要求全量则删后全量），并询问是否顺带纠正分类归属。
  - grep 未命中 → 确认为全新项目，走全新分析模式（见 [flow-new.md](flow-new.md)）。

## 输出规范（入库约定）

产出以 **Markdown 为主**，落在已确认的 `kb_repo` 下，按此目录形态组织：

```
{kb_repo}/
├── README.md                # 顶层总索引（各技术分类 + 每项目一行）
├── {分类}/                  # 按技术领域分类，如 IM/ auth/ rag/ devops/
│   ├── README.md            # 分类索引表：项目 | 语言 | 说明 | 协议 | 仓库
│   └── {项目}/
│       ├── README.md        # 项目解读主文档（`##` 语义式章节）
│       ├── architecture.md │ 关注面子文档（多关注面项目必备，一个关注面一篇）
│       └── arch.svg         # 可选：复杂架构图导出 SVG
```
每篇解读文档（README / 子文档）开头带轻量 YAML frontmatter：
```yaml
---
type: 项目解读
title: 项目名 深度解读
description: 一句面向检索的摘要（项目做什么 + 本次解读覆盖的关注面）
tags: [项目名, 技术域]
---
```
`description` 专门服务知识库检索，务必含项目与关注面关键词；不写时间戳/版本
等程序字段（留给外部索引）；增量时保留未知扩展字段。

- **主产出 = 项目解读页**（`{分类}/{项目}/README.md`），用 `##` 语义式章节组织（不加数字前缀标题，见 SKILL.md「必含要素清单」）；**多关注面项目必须按主题拆 `xxx.md` 子文档**，README 只承载 概览 / 架构总览 / 核心模块导读表 / 总结，深读放子文档，README 内链接跳转；禁止把全部内容压进单个 README。
- **README 子文档索引章节（强制，拆分即填）**：README 正文新增**一个独立章节**承载全部子文档索引，**一行一条**列出，格式：`- [\`xxx.md\`](xxx.md) — 一句话定位`。拆分/新增子文档必须同步回写此处，遗漏一项视为未完成。此章节是**全量子文档的总一览入口**；正文各章节、导读表每一行还需按下文「README 正文导航」就近给出内链，两处互补、共同构成读者入口。多关注面项目 README 结构模板：
  ```
  # 标题

  ## 子文档索引

  - [`architecture.md`](architecture.md) — 架构总览与协议
  - [`memory-system.md`](memory-system.md) — 记忆系统 …
  （逐个列出全部子文档）
  ```
- **README 正文导航（强制，与「子文档索引」章节互补）**：独立「子文档索引」章节负责"一览全部子文档"，README **正文**则负责"按阅读路径就近跳转"——「核心模块导读表」每一行都用 `[\`xxx.md\`](xxx.md)` 链接到对应子文档；概览 / 架构总览 / 总结章节中提到某一关注面时，同样就地给出 `[\`xxx.md\`](xxx.md)` 内链。两处不可互相替代：导读表每行可点超链是读者顺着模块点击深读的主入口，遗漏一个行内链接即视为该关注面入口缺失。
- **分类归属**：按技术领域归类到对应 `{分类}/`；不确定或需新建分类时向用户确认。
- **索引同步（收尾三步）**：建 `{分类}/{项目}/README.md` → 更新 `{分类}/README.md` 索引表 → 若分类不存在则新建并加入顶层 `README.md`。
  - **索引只动本项目**：`{分类}/README.md` 与顶层 `README.md` 仅增改本项目行/条目，
    不重排/改写其他项目条目格式。
  - **产物不落源码仓库**：解读产物一律落在已确认 `kb_repo`，绝不写入当前
    `source_repo` 根内；即使 `kb_repo` 判定走到"用户选择"分支，也不得在
    `source_repo` 内落解读文档。
- **可渲染格式**（无需额外工具，GitHub / VS Code 原生支持）：
  - 图表：` ```mermaid ` 代码块，或 `.svg` 资产（按上方选型规则决定用哪种）。
  - 对照/数据/清单：Markdown 表格。
  - 线性流程：ASCII 列表图（过长收束为关键步骤）。
- **图表工具选型（按图的职责选，不唯 Mermaid）**：Mermaid 与 SVG 均为**一等公民**，二选一，不要对同一张图重复产出。
  - **结构类 → SVG**：拓扑 / 分层 / 部署 / 泳道类图，**位置本身即论据**（谁在底层、谁在入口、边界在哪）。Mermaid 的自动布局不认这类语义，且加一个节点全图重排，破坏结构图应有的稳定性。
  - **映射类 → SVG**：二部图、多对多映射、需靠重排两侧节点消除交叉线的图。
  - **对比类 → SVG**：左右并列、需同构对齐表达"旧 vs 新 / 方案 A vs B"的图。
  - **带回边的状态机 → SVG**：自动布局会把回边绕远、标签易压在连线上。
  - **时序类 → Mermaid**（`sequenceDiagram` 是 Mermaid 强项，**不要**升级为 SVG）。
  - **线性流程 / 简单拓扑 → Mermaid**：节点少、无交叉、位置不承载论据时，纯文本更易维护、可 diff。
  - 若一张图用文字/表格承载信息更多，**改用文字或表格**，不要为了凑图而画。
  - **SVG 生成走 `svg-maker` skill**：选型判定为 SVG 的图，**调用 `svg-maker` skill 产出**（`architecture-svg` 用于软件/基础设施拓扑，`clean-svg` 用于概念/流程/生命周期），不要自行临时编写一套样式规范——那会与既有的图和其它项目的图产生风格漂移。**若当前环境无 `svg-maker`，先说明再退回自绘**，此时必须守住下方自包含约束。
  - **SVG 资产约束**（无论走哪条路线都必须满足，`scripts/scan-narrative.mjs` 会校验）：自包含（内联 CSS）、零外部资源（无 `<image>`/远程字体/JS/渐变）、`<title>`+`<desc>` 齐备、固定 `viewBox`、可离线双击打开；放 md 同目录（或该目录下的 `assets/`），命名用**英文语义名**（不用 `01-` 序号前缀）。
  - **SVG 写法一致性（校验按标签名匹配，别指望字面巧合）**：`<title>`/`<desc>` **不带属性**（写成 `<title id="...">` 会被 `scripts/scan-narrative.mjs` 判为缺失，已实际踩过）；根元素**只写 `viewBox`**，不写 `width`/`height`；调色板沿用 `:root` 变量 + `prefers-color-scheme` 暗色适配；先画 connector 再画 node；盒内文字留 ≥24px；中文标点统一全角（`：`、`（）`）。多图批量产出见 [figure-batch-workflow.md](figure-batch-workflow.md)。
  - **一处编号只写一次**：正文不写「图 N」，SVG 的 `<title>` 里也不要写序号——正文一改结构编号就错位（本项目已踩过：删掉一章后图号整体失效）。确需编号时由正文按出现顺序统一生成。
- **命名**：子文档**统一主题语义命名**（如 `architecture.md`、`deployment.md`、`data-model.md`、`memory-system.md`、`llm-route-system.md`），**不用 `01-`/`02-` 序号前缀**（个别存量项目的历史编号式命名不沿用）；图与引用它的 md 同目录。

## 叙述型文档：架构设计说明（`architecture-design.md`）

除证据型子文档外，**每个项目都应额外产出一篇**叙述型架构设计文档，供人快速理解系统的设计意图。它与证据型文档**完全隔离**。

### 硬约束

- **零代码索引**：正文不得出现 `路径.ext:行号`、锚点指纹、仓库相对源码路径、函数/类型名。**不得链接任何证据型文档**，也不得自述为"无代码索引/叙述型"——读者不需要知道这个分类。
- **是独立读物**：脱离本项目解读目录也应能读懂，不依赖同目录任何其他文件。
- **由证据型产出派生**：**必须先完成证据型深读，再改写成叙述型**。禁止跳过证据环节直接生成叙述型文档——否则它会退化成散文，失去全部防幻觉保障。
- **取舍必写代价**：每条设计决策都要写出代价或权衡（只讲选了什么、不讲代价 = 宣传材料）。
- **必含（缺一形态就不成立）**：设计信条与质量模型 / 设计输入（约束 + 非目标 + 技术选型代价）/ **总体架构**（边界 + 分层与依赖方向 + 运行形态）/ **核心模块责任矩阵**（含"明确不做什么"）/ 端到端数据流（含任务调度与状态机）/ 处理策略（解析与切分这类"怎么做"的主张 + 执行约束）/ 读取链路（含可溯源性）/ 状态与持久化真源划分 / 关键设计决策与代价 / **备选方案与复审触发条件** / 部署形态 / **容量与性能口径** / 已知边界 + **验收标准与开放问题**。逐章骨架与必答问题见 [narrative-design-template.md](narrative-design-template.md)。
- **设计输入必须分级**：每条输入标注**证实**（有源码/文档依据）、**推断**（由现状反推，正文标 `（推断）`）、**不可复原**（原始需求与指标未留存，集中一节声明"本文不臆造"）。三者不得混为一谈。
- **禁止把欠账写成决策**：未完成项（如"目前只有 CPU 路径"）必须落在"已知边界 / 开放问题"，不得包装成"刻意的设计选择"——这是最伤可信度的一种合理化。
- **量化**：有实测给实测；没有实测但机制清楚时给**可校准口径模型**（公式 + 参数表 + 档位示例 + 校准步骤 + 非实测声明）；确实不可复原则显式声明。禁止编造数字，也禁止只写"指标缺失"（见 [quantification.md](quantification.md)）。
- **编号纪律（本 skill 通则的明确豁免）**：设计文档允许 `## 一、` 与 `### N.M` 编号（长文交叉引用依赖编号），代价是必须**唯一、递增、引用可解析**，由 `[HEADING-SEQ]` / `[XREF-DANGLING]` 强制；**重排章节后必须重跑**。
- **图表**：按上方选型规则；结构类图优先 SVG；**图前必须有导读段、图后必须有着落**（只有图的小节会被 `[FIGURE-ONLY]` 提示）。
- **索引**：在项目 `README.md` 子文档索引中**排第 1 位**，标注"建议先读"。

### 核实机制（产出后必须跑）

```bash
node scripts/scan-narrative.mjs [--repo-root <解读目录>] <architecture-design.md>
```

覆盖可程序化的部分：零代码索引、零跨文档引用、`<details>` 内不得藏索引、引用的 SVG 存在且自包含且带 `<title>`/`<desc>`、**标题编号唯一递增（`[HEADING-SEQ]`）**、**交叉引用可解析（`[XREF-DANGLING]`）**、有图、**图不是孤立插图（`[FIGURE-ONLY]`）**、取舍章节提到代价。退出码非 0 = 未通过。

推荐用一键入口（顺带跑 mermaid 校验与 SVG 边拓扑审计，避免"只跑了其中一个"）：

```bash
node scripts/check-narrative-all.mjs [--repo-root <解读目录>] [--preview] [--strict-topology] <architecture-design.md>
```

- `scripts/audit-svg-topology.mjs`：逐张 SVG 打印「起点节点 → 终点节点」，核对边拓扑（`--expect <清单>` 可逐条断言；`--strict` 让提示级间隙也算失败）。**新画或重排图后必跑**——"看着对、边连错"只能靠它发现。端点间隙分两级：>40px 记 `[EDGE-DANGLING]`（错误），6-40px 记 `[EDGE-GAP]`（提示，标签式箭头可能有意留白）；独立文字锚点（`起点`/`终点` 这类标签）也算合法落点。
- `scripts/render-svg-preview.mjs`：先把 `var()` 展平成字面色再出 PNG，供目视核验（librsvg 不解析 CSS 自定义属性，直接渲染会全黑）。
