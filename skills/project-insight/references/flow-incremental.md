# 增量分析模式

> 由 SKILL.md「执行流程主干」的 step 1 判定为**增量模式**（已有解读文档）时按需加载。对**已有解读文档**做更新或补充。**变更的唯一依据 = 上游 git diff / release notes**，禁止凭空重写或凭偏好重排。**diff 的两端必须先定基线**（[version-baseline.md](version-baseline.md)）：起点 = 既有解读记录的基线 ref（项目 `README.md` 概览「解读基线」/ `CHANGELOG.md` 顶部「依据：<ref>@<sha>」），终点 = 本次 `scripts/select-baseline.mjs` 选定的新 ref；拿到两端再 `git diff <旧ref>..<新ref>`。拿不到 git diff / release notes（本地仓库无 `.git` 历史、上游未写 changelog、老解读未署基线）时退化为**代码快照比对**：对比当前代码与既有文档描述差异，并在文中显式声明"本次依据代码快照比对，非官方 changelog"。

## 铁律（违反即重来）

1. **先读现有文档，再动笔。** 不先读就改 = 失败。
2. **差异驱动。** 每处变更必须能追溯到上游 diff / release notes（或声明的代码快照比对）。找不到依据的改动不做。
3. **确认覆盖范围。** 先定位现有文档已覆盖内容，避免重复；先在仓库或上游核对**真实地址与版本**：从既有解读取出记录的基线 ref（`README.md` 概览 / `CHANGELOG.md` 顶部）→ 用 `select-baseline.mjs` 选定新 ref → `git diff <旧ref>..<新ref>`（或对 release notes）取实际变更作依据，不只听口头描述；基线记录缺失时退化为代码快照比对并在文中声明。
4. **最小破坏结构。** 已有 `##` 章节标题原样保留，不移动、不删除、不重排标题。

5. **引用预检门禁（程序化输入）**：**先定新基线并 checkout 到基线工作树**（[version-baseline.md](version-baseline.md)；引用重定位只对基线快照有意义），再增量**动笔前必须先跑**
   `node scripts/verify-references.mjs --diff <source_repo> <现有解读.md>...`，
   把现有解读里每条 `文件:行号` 引用对**基线源码**重解析，得到
   `STABLE / STALE / UNRESOLVED` 清单。**仅 STALE（带真实行号）与
   UNRESOLVED 对应章节允许改动；STABLE 章节原文保留，不得重写。**
   此清单即增量差异依据之一，与上游 diff / release notes 并列；拿不到
   diff 时以本清单为主。

## 变更粒度（从轻到重，够用就好）

1. **改段落** —— 更新"现状描述"里过时的数字/表述。
2. **加独立 md** —— 新增一个主题就新建 `xx.md`，别把 README 主体越堆越长。
3. **重排主体结构** —— 仅在确有必要时，几乎不该发生。

> 同一项目的版本演进优先**就地编辑 + 演进说明**，不为此分散归档历史版本；跨版本的集中式变更汇总落进**独立 `CHANGELOG.md`**（见下文「版本变更汇总」），本地既有的演进说明仍按「结构保护与演进标注」就地保留。

## 范围界定（什么值得写）

**值得写：** 影响"现状描述一致性"的数字（引擎数、默认库、接口数量）；新增的独立能力点；用户可感知的接入/用例变化。
**不值得写：** 在正文里为每个历史版本加脚注造成噪音；拆分新文件只为了不破坏结构；修改**竞品**行描述（它不是本项目组件）。历史变更的集中归档统一走独立 `CHANGELOG.md`，不在正文各个小节堆积版本脚注。

## 增量止损（noop）

`--diff` 预检**全部引用均返回 STABLE**、且当前无新 release / 无提交变更时，
判为"无需增量"：输出预检清单，提示"本次无改动的引用依据"并停笔——源码无实质
变化且零 issue 时直接跳过重写。仅在疑似漏检
（既有解读缺强引用、用户明确要求重梳）时才继续增量。

## 版本变更汇总：独立 CHANGELOG.md

为支持「各个版本的更新内容」按版本查阅，增量产物维护一份**独立 `CHANGELOG.md`**（项目解读目录下、与 `README.md` 平级），按版本号集中归档每次增量的变更。这是跨版本变更的**唯一集中入口**；正文仍按「结构保护与演进标注」就地演进，但各版本历史一览以本文件为准。

- **文件头**：第一行语义式标题（`# 变更记录` 或 `# Changelog`），下一行用引用块说明定位与依据：`> 本解读对 {项目} 的跨版本变更汇总；按版本倒序。描述清楚相关变动即可：若上游有官方 changelog，参照它并结合代码变动生成；没有则基于代码变动（git diff / release notes / 代码快照比对）生成。`
- **追加条目**：每次增量**在文件顶部、最新版本在最前**，新增一个 `## [版本号]` 小节。小节内：
  - 首行写更新日期与依据来源，**并记录本次解读基线**（下一步增量要靠它取 diff 起点）：`依据：<ref>@<短SHA>`（旧 ref → 新 ref）；**上游有官方 changelog → 参照它并结合代码变动**；无 → **基于代码变动**（git diff / commit 区间 / release notes / 快照比对）生成；
  - 用列表逐条列出相比**上一版本**的主要变更，描述到功能/行为层面，用版本号或上游 diff 佐证即可，**不强求 `文件:行号` 引用**（CHANGELOG 是版本说明而非技术解构，不进真源校验）；
  - 变更分类可按需分段（新增能力 / 交互与接入变化 / 接口或 API 变更 / Schema 与数据演进 / 移除与废弃）。
- **归档而非覆盖**：旧版本条目**原样保留**，只新增、不删除不改写已写入的历史（对已过时表述，同「本地演进说明」原则，不再回改历史条目）。
- **README 挂链接**：在项目 `README.md` 正文（通常靠「概览」处）加一行 `- [\`CHANGELOG.md\`](CHANGELOG.md) — 各版本变更汇总`，作为集中入口；无 `CHANGELOG.md` 的已有项目首次增量时创建并回写此链接。
- **一致性**：能力清单、技术栈表、架构图、对比表里的数字要**同步更新**（只改正文会漏），且这些更新若属「相比上一版的变化」，同样在对应 `CHANGELOG.md` 条目内交代一句，避免文档与汇总脱节。
- **落盘**：与其余产物一致，只提示变更清单，不代为 `git commit`。

## 结构保护与演进标注

- 新增小节用 `###` 三级标题，与同部分兄弟小节平级，不挤进顶层 `##` 章节层级。
- 删掉的现状数字不直接抹掉，用 `> **演进说明(版本号)**` 引用块保留历史轨迹，再写新现状。
- 文档头更新版本号，加一段"本版增量更新说明"，简述相比上一版的主要变更；同时更新 README 概览的「解读基线：`<ref>`（`<短SHA>`）」一行（见 [version-baseline.md](version-baseline.md)「基线记录」）；并在 `CHANGELOG.md` 顶部按「版本变更汇总」追加对应版本条目（与文档头的本版说明呼应，文档头只说当前这版，历史一览交给 CHANGELOG）。
- 能力清单、技术栈表、架构图、对比表里的数字要**同步更新**，只改正文会漏。全篇 grep 核对一致性。
- 真源校验与全新分析流程一致：改完后重跑一遍 `scripts/verify-references.mjs` 与 `scripts/check-mermaid.mjs`（用法见 [grounding-guide.md](grounding-guide.md)），新增/改动的引用同样经程序重定位，失败标 `[UNVERIFIED]`；`[MERMAID-ERROR]` 修复至全 `OK`。
- 落盘后同样只提示变更清单，不代为 `git commit`。
