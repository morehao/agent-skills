# 产物骨架与写法

> 由 SKILL.md 六步主干的 step 2（架构骨架）与 step 5（成文自检）按需加载。本文件回答：**一份可学习的架构分析长什么样、每章至少要回答什么、写到什么程度算够**。推理方法见 [decisions.md](decisions.md)，好坏对照见 [examples.md](examples.md)。

## 先定档位

| 档 | 骨架 | 篇幅参考 | 适用 |
|---|---|---|---|
| 速览 | 一句话结论 + 架构图 + 3 张决策卡 + 2 个模式卡 + 未覆盖 | 800–1500 字 | 选型、快速判断值不值得学 |
| 标准 | 下面 8 个正文章节全写（证据按需） | 3–6K 字 | 常规深读 |
| 深读 | 标准 + 证据附录 + 同类对比 + 可选分册 | 6K+ | 写系列、做内部分享、大而深项目 |

**不要默认写深读。** 档位由用户意图决定；用户没说时按标准档，读完再判断是否值得加厚。

## 标准档骨架与逐章必答

### 一句话结论

开头给 3 条"可带走"的判断，每条一句，不铺垫。读者只读这一段也应有所得。

### 问题与约束

- 它解决什么根本问题？**不做会怎样**（失败的形态）？
- 硬约束是什么：部署形态、性能/成本、团队规模、生态兼容、合规？
- 哪些是**非目标**（明确不做）？

> 判据：如果这一节换成任何同类项目都成立，说明没写出这个项目的约束。

### 架构全景

- 边界：什么在系统内，什么交给外部（数据库、模型、宿主、云服务）？
- 部件清单：每件一句话职责，**不按目录罗列**。
- 依赖方向：允许谁依赖谁；哪些方向是刻意禁止的？
- 运行形态：有几种装配方式（单机/集群/嵌入/云）？差异在哪？
- 一张边界图（选型见 [diagrams.md](diagrams.md)）。

> 判据：读者能据此画出"谁在入口、谁在底层、哪里是边界"。

### 模块责任矩阵

| 模块 | 负责什么 | 明确不做什么 | 依赖谁 | 失效模式 |
|---|---|---|---|---|

"明确不做什么"是这张表的灵魂：只写职责会得到一份目录说明，写清边界才看得出设计。

### 关键链路

1–2 条端到端链路，每条给图 + 沿途取舍。必须包含：

- 主路径（正常输入 → 输出）；
- 至少一个分叉/异常（失败、超时、降级、重试、回滚）；
- 每一步"为什么在这里切"，而不是"这里调用了什么"。

> 判据：读者能沿着链路指出"如果这一步挂了，系统会怎样"。

### 设计决策卡（3–6 张）

每张卡先回答五个核心问题（缺一不算决策），末尾补一句迁移提示：

```markdown
### 决策：<一句话，用"选了 A 而非 B"的句式>

- **约束**：什么外部条件逼出了这个选择（部署形态 / 延迟 / 团队 / 兼容 / 成本）
- **选择**：具体选了什么（机制、协议、数据结构、分层）
- **否掉的备选**：A 为什么不行；B 的代价是什么
- **代价**：这个选择带来了什么负担（复杂度 / 内存 / 运维 / 学习曲线）
- **反转条件**：出现什么信号时应该重新评估（规模、延迟目标、团队变化）
- **迁移提示**：什么类型的项目可以借鉴，什么类型不该
```

示例（虚构，仅示范写法）：

> **决策：在连接建立阶段完成鉴权，而不是每个请求都验一次。**
> 约束：长连接、单连接多路复用、请求频率高；选择：握手时验签并把权限快照挂到连接上；否掉的备选：每请求查权限（延迟 + 存储压力）与无状态 JWT（撤销困难）；代价：权限变更需要断开重连或推送刷新；反转条件：权限需要秒级生效、或单连接跨多租户时。

### 可迁移的手法（3–5 张模式卡）

从具体项目里"去名字"，抽象成可搬运的做法：

```markdown
### 模式：<名字>

- **解决**：什么共性问题（一句话）
- **做法**：核心机制 2–3 句，必要时给一张小图
- **适用**：什么约束下值得用
- **不适用**：什么情况下会变负担
- **代价**：引入的复杂度 / 运维成本 / 学习成本
- **落地步骤**：如果要在我自己的项目里用，第一步做什么
- **本项目落点**：（可选）哪个模块体现了它
```

> 判据：把项目名抹掉后，这段仍然成立；否则它只是项目描述，不是模式。

### 边界、风险与开放问题

- 已知缺口与不适用场景（按影响面排序）；
- 宣传与实现不符、过度设计、明显的技术债；
- 作者刻意做的取舍 vs 尚未完成的欠账——**不要把欠账写成"刻意的设计选择"**。

### 学习路径与练习

给三条可执行的路径，而不是"建议阅读源码"：

- **30 分钟**：读哪 2–3 个文件、看哪张图，建立最小模型；
- **半天**：按哪条链路走一遍，配合哪个测试/示例；
- **动手改**：一个低风险改动（加一个配置项 / 一个中间件 / 一个命令），验证对架构的理解。

再给 3 个自测问题（能答上说明真读懂），例如"如果去掉 X，哪条链路会先坏？"

### 附录 A：证据（可选）

只放需要核验的论断，每条一行 + 锚点。没有就不写这一章，不要用"源码见 xxx"凑数。格式与校验见 [evidence.md](evidence.md)。

### 附录 B：术语与同类对比（可选）

- 术语对照：项目用词 ↔ 通用架构用词；
- 同类对比：只比设计取舍，不比 star 数；没有把握就不写。

## 写作纪律

- **中文为主**，术语、标识符、协议名保留英文；英文引文必须紧跟中文解读。
- **标题用语义层级**（`##` / `###`），不加 `## 1.` 这类数字前缀；顺序交给叙事主线（问题 → 结构 → 链路 → 决策）。
- **能用图/表就不用长段**：结构图、责任矩阵、决策表优先；图必须有导读与着落，不能只放一张图。
- **不贴整段源码**：默认零代码块；必要片段 ≤15 行，且只保留承载设计的那几行。
- **不写"某某模块很优雅"**：每个评价后面跟机制、代价或对比。
- **不确定就标**：`[待核]`、`（推断）`、`（未读到）` 比编造好。
- **同一篇内不重复**：架构全景讲过的，模块章节不再复述，只讲该模块特有的决策。

## 数据模型（有持久化时可选加一节）

命中 `*.sql`、`migrations/`、models 实体、ORM 建表入口时，加一节，至少回答：

1. 存储选型：为什么是关系型/文档/KV/列存？代价是什么？
2. 实体关系：一张 ER 图或实体清单；
3. 核心表：每表字段表（字段 | 类型 | 约束 | 说明），**写成设计而非数据字典**；
4. 演进策略：迁移、兼容、回滚；
5. 读写路径：谁写、何时写、谁读、经过什么缓存。

不是每张表都要列；只列承载核心链路的表。

## 量化与容量（有数字时）

没有实测数据时，按三档处理，禁止编造：

| 档 | 情形 | 写法 |
|---|---|---|
| A 实测 | 有基准/监控/官方数据 | 数字 + 条件（机器、数据量、基线版本） |
| B 可校准口径 | 机制清楚、参数可数 | 公式 + 参数表 + 2–4 个档位示例 + 校准步骤 + "非实测"声明 |
| C 不可复原 | 原始指标没留存 | 明说不可复原，登记进开放问题 |

容量三件套：存储 ≈ 条数 × 单条字节 ×（副本数 + 索引系数）；吞吐 ≈ 并发数 ÷ 单次请求延迟（Little 定律，注意单位）；延迟按分段求和，分 p50/p95。

## 单文件还是拆分

- 默认独立落点：`<cwd>/<项目>-架构分析.md`；知识库入库时主文档沿用 `{分类}/{项目}/README.md`。
- 只有在**≥3 个主题、每个都能独立回答一个设计问题、且各自够深**时才拆目录；拆了就给阅读顺序，不强制索引表。
- 拆分的判据是"主题独立"，不是代码行数；为拆而拆会让每篇都变薄。

## 深读可选：长文骨架

分析一个大型系统、或要写成系列文章时，可以在标准骨架上扩成设计说明式长文（不是必需，也不要求编号）：

1. 背景与定位：为什么做、目标用户、问题的起点；
2. 设计输入：约束、非目标、无法复原的输入；
3. 总体架构：边界、部件、依赖方向、运行形态；
4. 模块责任：每个模块负责/不负责/依赖/失效模式；
5. 写入或请求链路：端到端全景 + 状态机 + 并发控制；
6. 处理策略：从输入到可消费结果的关键策略与参数；
7. 读取或消费链路：从请求到结果；
8. 执行模型（有 Agent/工作流时）：循环、工具、记忆、运行时；
9. 状态与持久化：真相源、幂等、迁移；
10. 关键决策与代价：备选 + 反转条件；
11. 部署形态与运行拓扑；
12. 容量与性能口径；
13. 已知边界、验收标准与开放问题。

**四章不能省**：总体架构、模块责任、决策备选、验收/边界。长文也不需要代码索引；证据仍进附录。

## 入库模式（仅在用户明确要求时）

用户要求落进知识库时，才按 `{分类}/{项目}/` 组织：

- 目录：`{分类}/{项目}/README.md` + `assets/`（图）+ 可选 `CHANGELOG.md`；项目名沿用仓库名，不改写；
- 主文档 `README.md`（沿用 KB 约定；独立落点仍用 `<项目>-架构分析.md`）承载概览 + 架构全景 + 阅读顺序；
- 主题文档一篇一个设计问题；正文用相对链接指向 `assets/`，不写本机绝对路径；
- 索引：按知识库现有列补一行（通常含项目、一句话、链接、基线），只动本项目条目，不重排整表；
- frontmatter 用 `type/title/description/tags`，`description` 面向检索；基线仍写在正文开头；
- 仍然不代提交。

## 收尾自检：学习效果五问

让一个没读过该项目的人（或自己隔一天）回答：

1. 系统的边界在哪？什么在系统外？
2. 画出主要部件与依赖方向。
3. 说 3 个关键决策的代价与反转条件。
4. 哪 2 个模式可以搬到别的项目？什么情况下不该搬？
5. 如果只改一处来验证理解，改哪里？

答不上来的章节，就是还没写透的章节。
