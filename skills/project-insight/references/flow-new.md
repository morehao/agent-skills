# 全新分析流程

> 由 SKILL.md「执行流程主干」的 step 1 判定为**全新模式**时按需加载：新项目冷启动解读的完整流程（step 1-9 + 分文件判定）。执行主干（路由总览）见 SKILL.md；类型判定与关注面触发判据见 [dimension-triggers.md](dimension-triggers.md)；落地目标判定/输出规范见 [kb-repo-rules.md](kb-repo-rules.md)。

## 前置一：基线工作树已就位（step 0.5）

本流程的一切探索与校验都发生在 [version-baseline.md](version-baseline.md) 选定的**基线工作树**上（稳定 tag > 稳定分支 > 默认分支 > 无 main/master 兜底矩阵，由 `scripts/select-baseline.mjs` 程序化选定），该工作树 `realpath` 后的路径即 `source_repo` 与引用校验根。**基线未定不得进入下面的探索**——行号只在确定的快照上成立。用户显式指定 ref 时以用户为准，并在产物中声明"按用户指定 ref 解读，非稳定版"。

## 前置二：确立根因先行

读项目自述/README，一句写出"解决什么根本问题"。这是全篇的锚，防止写成功能罗列。

## 规模门控·复杂度×规模分流（关键分流）

估算有效代码行（剔除测试/构建/生成/示例代码），结合仓库复杂度倾向走四条路径。5 万行是"单 agent 单次上下文耗尽风险线"的**经验默认锚点**，但**合理性优先**——不以行数硬切，先判断复杂度倾向，再按规模收口：

```
step 2 复杂度 × 规模分流
├─ 小规模(≲5K 行) 且 算法/并发/类型密集（"小但复杂"）
│     → 路径 A：不拆文件，单篇按【四要素】深挖 + 多个 sequenceDiagram 拆流程 + 反事实推理
├─ 中规模 或 常规形态
│     → 路径 B：现有关注面驱动单 agent 流程（step 3 以下）
├─ 大规模 且 核心模块多、有统一核心数据/请求链路/设计哲学（"大而深"）
│     → 路径 C：转 [large-repo-workflow.md](large-repo-workflow.md) 并行流程
└─ 大规模 但 模块彼此独立、耦合弱、无共享核心哲学（"大而浅"）
      → 路径 D：不强行并行深度拆分，退化为单 agent，按关注的模块群分组解读
```

- **"深/浅"判定信号（快速启发式，须在上下文耗尽前早期做出，不花大量读取去"确认"）**：顶层目录划分是否对应业务功能（深）还是工具/零散功能拼凑（浅）；有无贯穿的单一核心数据流/请求链路（深）还是各模块各管各的（浅）；README/自述能否按功能点直接列清单（浅信号）。
- **路径 C/D 取舍以合理性为准**：宁可把边界项目按浅处理退化为单 agent，也不让"大而浅"的仓库被行数拖进并行深度流程、产出大量无深度子文档。
- 数据模型探测（step 3）与类型/语言关注面触发判据（见 [dimension-triggers.md](dimension-triggers.md)）在路径 A-D 都照常生效，路径 C 传给各并行 subagent。

## 探索数据源（按序）

README → 架构/设计文档 → 目录树（推模块划分）→ 核心模块代码 → 关键链路（启动流程 / 主请求链路）。

- **README 既是探索入口，也是 step 5 定维度的候选关注面来源**——读它时除了一句写根因，还要顺带摘录其自述的核心能力点，作为后续「README 自述提名」的备料（见 step 5）。
- 在「目录树 → 核心模块代码」之间，必须对源码做一次**数据模型探测**（探测信号见 [data-model-guide.md](data-model-guide.md)），命中即登记为候选数据模型关注面——这是流程里跑不掉的一步，不是凭「这项目像不像业务应用」的主观印象来决定。类型触发判据第 1 条（见 [dimension-triggers.md](dimension-triggers.md)）是否命中，以此探测信号为准。

## 类型判定与分流

在探索完数据源后、进入定维度写深之前，判定项目类型并据此加载对应产出规格。**判定来源、主+副叠加、加载与回落规则详见 [dimension-triggers.md](dimension-triggers.md)**；要点：判定按 README 自述关键词 + 顶层目录特征（主+副叠加，冲突以主类型为准）→ 加载 `references/project-types/{类型}.md`；无法识别加载 [_default.md](project-types/_default.md) 回落通用默认产出，不阻塞解读；产物 README 顶部标注「本解读按 {类型} 类规格产出 / 回落通用默认规格」。类型规格只能细化该类型关注的产出结构，**不得放宽本 skill 任何通用铁律**（真源验证 / mermaid 校验 / 增量模式 / 写作规范 / 质量红线 / 索引同步）。

## 定维度，非全覆盖

从维度（概览/架构/认证/核心实现/存储/设计模式/部署/测试/社区/同类对比）里选项目特点最突出的 2-4 个深入，不要每个都写一段。**"项目特点"来自两个互补的候选来源：**

- **README 自述提名（优先级最高）**：被分析项目 README 浓墨重彩的功能/卖点，就是作者"想让读者看到什么"的信号，列为候选关注面——这是 README 最重要的分析权重。即使某个能力落在静态类型模板之外，也要尝试深挖，不能因"模板没列"而忽略。
- **类型 / 语言模板提名**：按类型判定加载的规格（`references/project-types/{类型}.md`）+ 语言惯用法触发判据（见 [dimension-triggers.md](dimension-triggers.md)）提名。
- **两者均只是候选，须经源码探测验证后落地**：候选关注面在源码里有对应实现、且能展开带 `文件:行号` 佐证的深度内容才成文；README 宣称过时/夸大、源码缺乏支撑的，标注并剔除，不硬凑（这条约束保住「让程序验证，不让模型自证」的铁律，README 只提名、不作论断依据）。

## 写作口径确认（叙述型文档前置四问）

开写 `architecture-design.md` 之前**一次问清**四件事，避免边写边改口径（实际项目里分了三轮才问清，代价是返工）：

1. **是否带源码索引**：叙述型文档一律零代码索引；需确认的是会话内"论断↔证据"如何核对（不落盘，见 [kb-repo-rules.md](kb-repo-rules.md)「同源兜底不落盘」）。
2. **版本号粒度**：产品名写不写版本、基线版本写在哪（README/CHANGELOG 已有约定）。
3. **是否含同类项目对比**：叙述型文档默认**不做**同类对比（对比属证据型文档）。
4. **量化指标有没有实测数据**：没有则走**可校准口径模型**（见 [quantification.md](quantification.md)），并事先说明"给的是口径不是承诺"。

第 4 问直接决定是否需要"容量与性能口径"整章，所以必须写在动笔之前；骨架与逐章必答问题见 [narrative-design-template.md](narrative-design-template.md)。

## 写深，不翻译

遵循 [analysis-guide.md](analysis-guide.md) 的深度方法论（Why>What、权衡、叙事连贯、全局关联、四要素完整性）与 [writing-guide.md](writing-guide.md) 的写作细则（中文为主 / 贴码克制 / 图表约束 / 信息密度）。深度不足标 `[WIP]`/`TODO`，不硬凑。

## 真源校验（不可跳过）

- **代码引用**：对本次产出的全部 md 跑 `node scripts/verify-references.mjs <source_repo> <产物.md>...` → 逐条重定位（有首末行锚点指纹则精确校验，无指纹降级弱校验）→ `[GROUNDER-MISMATCH]` 用真实行号覆盖；`[GROUNDER-UNVERIFIED]` **保留原样并追加 `[UNVERIFIED]` 标记**，不静默通过，并在文末列出所有 `[UNVERIFIED]` 项提示人工复核；`[GROUNDER-TRAVERSAL]` 必须修复路径。退出码非 0 视为未通过。（用法与原理见 [grounding-guide.md](grounding-guide.md)。）**校验根 = 基线工作树**（见「前置一」）：脚本只读磁盘文件，若校验跑在与写作不同的树上，行号核对毫无意义。
- **Mermaid 图**：对本次产出的全部 md 跑 `scripts/check-mermaid.mjs` → 任一 `[MERMAID-ERROR]` 修复至全 `OK`，不保留渲染报错图（详见 [writing-guide.md](writing-guide.md)「图表约束」）。

## 维护索引（收尾三步）

在 `kb_repo` 下创建 `{分类}/{项目}/README.md` → 更新 `{分类}/README.md` 索引表 → 若分类尚不存在，在 `kb_repo` 顶层 README 添加新分类。目录形态与索引约定见 [kb-repo-rules.md](kb-repo-rules.md)。

## 提交边界

本 skill 只负责落盘（写文件、更新索引），**不自动执行 `git add/commit/push`**。若 `kb_repo` 是 git 仓库，落地后列出本次变更文件清单，提示用户自行决定是否提交，不代为决策。

# 分文件判定（按项目复杂度/类型，不按代码量）

**拆分依据是"项目是否有多个可独立成文、且各自够深挖的关注面"，而不是代码行数或预计 README 体积。** 代码量大往往伴随关注面多，但行数只是复杂度的弱代理，最终以"关注面"为准：

- 项目可被自然切出 **≥3 个相对独立的关注面**（如数据模型、会话/记忆、Agent runtime、插件系统、MCP、LLM 编排、渠道接入、安全、部署……），且每个至少能展开一段有 `文件:行号` 佐证的深度内容，就**必须**为每个关注面独立成一篇子文档，README 只作索引/概览。
- **反向判断**：如果拆出来的子文档每篇都凑不够深度（没有可展开的 Why/权衡/源码佐证），说明是**为了拆而拆**，应退化为单文件。
- **关注面由"项目类型"驱动**：同一类型项目天然带同几类文档，遇之即拆、篇幅足够即独立成篇。类型触发判据见 [dimension-triggers.md](dimension-triggers.md)。

**产出形态：** 中小/单一关注面项目 → 单文件 `README.md`；多关注面项目 → `README.md`（概览 + 架构总览 + 核心模块导读表 + 总结，每子文档一行链接）+ `xxx.md`（关注面深读，主题语义命名，一个主题一篇）。**通用默认产出明细（分文件判定 / 丰富内容菜单 / 信息密度分配）见 [_default.md](project-types/_default.md)**；具体类型项目的差异化产出规格见 `references/project-types/{类型}.md`（类型注册表见 [project-types/README.md](project-types/README.md)）。子文档索引约定（README 专章列全 + 正文就近内链）见 [kb-repo-rules.md](kb-repo-rules.md)。
