# 写作规范与图表约束（入库约定）

> 由 SKILL.md「执行流程主干」的 step 6（写作）/ step 7（图表校验）按需加载。深度方法论（Why>What、权衡、叙事连贯、四要素）见 [analysis-guide.md](analysis-guide.md)；本文件承载**写作细则**：语言/贴码/标题规则、阅读体验配额、丰富内容菜单、图表约束（含 Mermaid 程序校验）。必含要素清单（统一核查底线）见 SKILL.md；分文件判定见 [flow-new.md](flow-new.md)。

## 写作规范（入库约定）

- **中文为主，术语/标识符保留英文**（ForwardAuth、JWT、sqlc、类型/字段/变量名、命令）。正文一律中文；引用**非中文原始片段**（官方文档原话、README 引文等）时：优先用中文转述核心论断；确需保留英文原句的，**必须紧跟一段中文解读**，禁止出现孤立无解读的整段英文。检验标准：一个不读源码的阅读者只看中文也能理解每个论断的设计含义。
- 代码块标注语言：`go`/`ts`/`yaml`/`sql`。
- 未完成章节用 `[WIP]`，待补充用 `TODO`；列表统一用 `-`。
- **代码引用统一为 `文件:行号` 且须经真源重定位验证**（格式见 SKILL.md「引用格式」，完整细则见 [grounding-guide.md](grounding-guide.md)），禁止写记忆中的行号与路径；定位失败一律标 `[UNVERIFIED]`。
- 深度标准遵循 [analysis-guide.md](analysis-guide.md)：每个关键论断带 Why、权衡与对比，避免泛泛而谈。
- **标题一律用 Markdown 天然层级，不加数字序号前缀。** 顶层 `##` 即最高章节，`###`/`####` 表达从属关系；不写 `## 1. X`、`## 0. X`、`## 第N部分：X` 这类数字前缀标题。**唯一例外是叙述型 `architecture-design.md`**：它允许 `## 一、` 与 `### N.M` 编号（设计文档惯例、长文交叉引用依赖编号），代价由 `[HEADING-SEQ]` / `[XREF-DANGLING]` 校验兜底（见 [narrative-design-template.md](narrative-design-template.md)）。并列列举如需在标题里体现顺序，用语义词（如 `## 决策一`、`### 亮点`、`### 问题`），而非纯数字前缀；列表项内部的 `.`/`-` 序号是列表，不算标题数字。
- **硬化"要素"而非"章节标题/顺序"。** 必含要素清单是统一核查底线，它**不绑定标题、也不绑定顺序**——标题用语义式、顺序交给叙事主线（数据流 / 分层 / 问题驱动，见 [analysis-guide.md](analysis-guide.md)）。不同语言/类型项目叙事主线本就不同，要素则人人一致，二者一文一固、相互配合。

## 阅读体验配额（结构护栏）

**篇幅决定权交给"关注面与深度"，不设任何行数上限。** 主 `README.md` 是概览 + 导读，深度内容按关注面拆进子文档（见 [flow-new.md](flow-new.md)「分文件判定」）；因此篇幅天然由项目复杂度驱动——单关注面小项目一页即够，多关注面大项目 README + 若干子文档各说各话，不为达标而压缩有效内容、也不为凑篇幅硬填。

**篇幅自查以"该拆已拆、无拖沓"为准：** 超常规篇幅先自查——是否把多关注面硬塞进了单个 README（应拆子文档）、是否有可压缩的拖沓；若拆分已合理、每段都承载设计纵深，篇幅长是合理的。反过来，单关注面项目篇幅短正常，**不必硬凑**。

**内容配额（比篇幅更难、更需要纪律，这是真正的强制项）：**

- **代码引用只作"依据"，不作"素材"**：正文每处引用自带一句结论/权衡/叙述 + `[路径:行号]` 标点，**不内嵌整段代码**（格式与理由见 [grounding-guide.md](grounding-guide.md)）。非-mermaid 代码块**数量以传达设计为准，不追求凑数**，仅保留真正承载设计的关键类型/接口（精简片段，不整段贴实现）。**指纹注释同理：每条引用至多首末行两行原文，不整段贴码。**
- **文字能用图替就替**：启动流程、核心请求链路、连接/会话生命周期、跨模块时序，命中即用 `sequenceDiagram`/`graph`（见下方「图表约束」强制清单），禁止纯文字长段描述过程。
- **信息密度优先**：能成表的转表格，能成图转图，能用一句理由说明就不铺三句；"泛泛而谈"比"缺内容"更严重。

## 丰富内容菜单

沉淀本知识库既有完整分析共享的内容组合。**不是每篇都要写满**，而是按项目特点取子集、挑可展开的深入；多关注面项目主 README 篇幅主要花在"概览 + 架构总览 + 核心模块导读表"三块，具体设计/决策深读下放子文档，避免 README 膨胀成超大单体。

> **本菜单为通用默认产出的一部分，其完整明细（分文件判定 / 信息密度分配）统一收敛在 [_default.md](project-types/_default.md)**；这里保留概要供速查，具体类型项目以 `references/project-types/{类型}.md` 规格为准（注册表见 [project-types/README.md](project-types/README.md)）。

```
1. 项目概览                定位 / 一句话根因 / 痛点 / 适用场景
2. 核心能力清单表
3. 技术栈一览表
4. 同类定位对比            对比表（同领域 3-6 个，含本项目的差异列）
5. 项目规模                指标表（文件数 / 模块数 / 行数参考 / Stars / 协议）
6. 架构总览                结构图（按选型规则用 SVG 或 Mermaid）
7. 启动流程 / 核心请求链路  选其一或都写；长流程配 sequenceDiagram 时序图
8. 核心模块导读            表列出各模块，**每一行用 `[xxx.md](xxx.md)` 超链接到对应子文档**（读者顺表即可逐篇点进深读）
9. 深度子文档              一个关注面一篇 xxx.md（主题语义命名）
10. 设计亮点               每点带 Why/权衡/对比 + 文件:行号
11. 不足 / 风险             伴论证，不吹不黑
12. 可借鉴的设计            ≥3 条，可跨项目迁移
13. 总结回扣根因             呼应开篇根因锚点
```

- **类型驱动的候选子文档**（篇幅足够深挖即独立成篇）：部署文档 / 数据模型 / 记忆机制 / 完整业务流程时序图 / 语言惯用法（如 Go 并发、Rust 所有权）——触发判据见 [dimension-triggers.md](dimension-triggers.md)。
- **数量与命名不设固定篇数**：子文档个数由关注面决定，多关注面项目常见 3-7 篇；结构参照上方第 8/9 项（README 作导读 + 各关注面一篇子文档）。
- 既有分析新增章节统一用 `###` 三级标题，不改动已存在的 `##` 语义式标题（符合增量最小破坏）。

## 图表约束（入库约定）

图表是解读的可视化支撑，必须"可渲染、可核对"，不允许留下渲染报错的图。**「可渲染」不是靠模型自我断言，而是落盘前跑程序校验（见下方「Mermaid 语法程序校验」）。**

**先选工具，再选类型**（选型规则见 [kb-repo-rules.md](kb-repo-rules.md)「图表工具选型」，不唯 Mermaid）：

- **结构类 / 映射类 / 对比类 / 带回边的状态机 → SVG**（位置即论据，自动布局会破坏语义）：**调用 `svg-maker` skill 产出**，不要自绘样式规范
- **时序类 / 线性流程 / 简单拓扑 → Mermaid**（下表给出对应类型）

Mermaid 侧的**类型映射**：

| 图表用途 | Mermaid 类型 | 说明 |
|---------|-------------|------|
| 架构总览 | `graph TB` / `graph LR` | 模块层次、整体架构 |
| 流程图 / 启动流程 | `graph TB` | 步骤、请求链路、程序流程 |
| 时序图 | `sequenceDiagram` | 模块间交互、请求时序（Mermaid 强项） |
| 状态图 | `stateDiagram-v2` | 状态流转、生命周期（回边多时改用 SVG） |

**规模与原则：**

- 图谱以保证可读性为准：过于复杂就拆成多个图分别标注主题，不因贪图单图完整而牺牲可读性。
- 不追求面面俱到——抓关键链路，标注核心数据流方向。
- 线性流程（如启动流程）直接用列表式 ASCII 图，过长则收束为关键步骤。
- 落盘前对本 skill 产出的所有 mermaid 块跑一遍 `scripts/check-mermaid.mjs`（见下方校验节），有 `[MERMAID-ERROR]` 必须先修复再落盘，不保留渲染报错的图；`<br>` 换行的 `[MERMAID-WARN]` 也应收敛为 0，避免长标签在预览下挤压。可渲染与否是**程序判定**，不是「模型认为没问题」。

### Mermaid 语法程序校验

沿用「让程序验证，不让模型自证」铁律：mermaid 是否可渲染，交给 `scripts/check-mermaid.mjs`（`mermaid.parse()` 真解析所有 ` ```mermaid ` 块）程序判定，不是模型自查。**落盘前对本 skill 产出全部 md 跑一遍**：`node scripts/check-mermaid.mjs <解读.md>...`（不传参从 stdin 读；依赖 `mermaid`+`jsdom`，首次在 `scripts/` 下 `npm install`，复制注册的 skill 副本需重装）。任一 `[MERMAID-ERROR]` 必须按真实解析器报错定位修复至全 `OK` 才落盘（同 `[UNVERIFIED]` 原则，不静默放过）；`[MERMAID-WARN]`（`<br>` 换行 lint，提示级）收敛为 0。脚本只读、不改动解读文档；输出格式与 `<br>` 三条规则详见脚本头注释。

**强制图位清单（命中即必须给图，禁止纯文字长段走流程）：**

| 触发 | 必给图 |
|------|--------|
| 架构总览 | `graph TB/LR` 模块图 |
| 启动流程 / 主请求链路 | `sequenceDiagram` 或 `graph` 阶段图 |
| 连接 / 会话生命周期 | `stateDiagram-v2` 或 `sequenceDiagram` |
| 跨模块数据流 / 时序 | `sequenceDiagram` |

- 子文档每篇**至少 1 张**属于本关注面的核心链路图（README 的架构总览图不重复计入）。
- 图是读懂过程的主体，旁注文字只做图外补叙与权衡说明。

**与 SVG 分工（复杂度阈值）**：默认优先 mermaid（纯文本、可 diff）；**命中任一条即改用 SVG**——

- 节点数 **≥12**；
- 含**分叉 / 汇合 / 回边 / 泳道 / 分区**（位置与分组本身承载语义）；
- 一张图要同时表达"接入—服务—领域—资源"这类**纵向层次**。

Mermaid 保留给：时序图、真·线性小图（≤8 节点、无交叉）、简单拓扑。**长链不要排成一列**：>12 节点先分段/分列再画。同一张图不做双份。

**图必须被正文包裹**：图所在小节要有图前导读段（这张图是什么、为什么存在）与图后着落（该看什么、代价是什么）。只放一张图的小节会被 `[FIGURE-ONLY]` 提示——图不是插图。

**mermaid → SVG 转换必须等价**：节点标签、边的起止与分支标签逐一对应；转换后跑 `scripts/audit-svg-topology.mjs` 打印「起点 → 终点」清单与原文对照——这是唯一能程序化发现"看着对、边连错"的手段。
