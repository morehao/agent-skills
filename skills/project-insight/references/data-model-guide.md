# 数据模型文档规范（判定信号 + 五要素成文细则）

> 由 SKILL.md「执行流程主干」step 3（探索与数据模型探测）与 [dimension-triggers.md](dimension-triggers.md)「触发判据」第 1 条按需加载。本文件承载**判定信号**（是否进入本关注面，程序化探测决定）与**成文细则**（五要素）。数据模型是"关注面"中最容易退化成"字段清单罗列"的一类——本细则与其说是补内容，不如说是**强制把它写成设计，而非数据字典**。判断标准：一个读者看完能回答"为什么用这套存储、数据怎么演进、写读路径怎么走"，而不是只看到一张表。

## 判定：数据模型主动探测（流程内强制一步，探索阶段执行）

**是否进入本关注面，由「数据模型主动探测」的程序化扫描决定**，不由"这项目是不是业务应用"的主观印象决定。在探索数据源（目录树 → 核心模块代码之间）执行，任一信号命中即登记候选数据模型关注面：

- **文件形态**：glob `**/*.sql`、`**/migrations*/`、`**/schema*/`；含 `CREATE TABLE` 的迁移/建表脚本。
- **语言/ORM 约定**：`models/`、`entities/`、`domain/` 目录；（Node）`*.prisma`；（Python）`alembic/versions*`、`models.py`；（Go）ORM `Sync2`/`AutoMigrate` 建表入口（本项目用 `xorm.io/xorm` 的在 `engine` 或插件 `InitPlugin` 处建系统表）。
- **会话/元数据存储**：会话、配置、操作日志等非业务表的持久化定义（如 `goadmin_session`、`goadmin_operation_log`）。
- 库/框架型项目自带 `goadmin_*` 系统表、`data/migrations/`、models 实体即命中，**不得因"自带而非业务应用"跳过**。

> 触发示例（go-admin）：探测命中 `data/migrations/`、`plugins/admin/models/`（7 个模型）、`plugins/admin/data/mysql/admin.sql`（10 张 `goadmin_*` 表）→ 应产出 `data-model.md`，而非让表只散落在 table-dsl / auth-rbac 里。

命中且篇幅足够独立深挖则单独成篇 `data-model.md`；篇幅偏浅可先并入 README 对应小节，但**必须**至少有 ER 图 + 核心表字段表 + 一句存储选型理由，不得整段省略。

数据模型文档**必含**以下五部分（缺一部分即未完成）：

> **必含清单（成文时二者皆需）：** Mermaid `erDiagram`（或 `graph`）实体关系总览图 + **每张核心表一个 Markdown 字段表**（`字段 | 类型 | 约束 | 说明`）。ER 图承担"有哪些实体、怎么关联"，字段表承担"每张表有哪些字段、约束如何"，缺图或缺表均视为未完整交付。

## 实体关系总览

优先用 Mermaid `erDiagram` 画实体/表及其关系（一对多、多对多经中间表等）；不适用 `erDiagram` 的场景（文档型 / 键值型）用 `graph TB` 表达实体集合与引用。同受 [writing-guide.md](writing-guide.md)「图表约束」的 `check-mermaid.mjs` 程序校验，落盘前全 `OK`。关系图是本节主体，文字只做图外补叙与权衡说明。

## 存储选型与理由

说清**为什么选这套存储**，而不是罗列用了什么：关系型 vs 文档型 vs 键值型的权衡、一致性/可用性/分区三种取向、对比不选方案的代价。这是数据模型的"根因"，也是最体现设计深度的部分。

## 核心表 / 实体设计

ER 图只表达了"有哪些表、怎么关联"，还缺字段级信息。因此**对每张核心表**都配一个 Markdown 字段表，作为 ER 图之外的结构化补充——这正是"ER 图 + 表格形式数据表说明"的组合：

| 字段 | 类型 | 约束（主/外键、索引、非空、默认） | 说明 |
|------|------|--------------------------------------|------|

- 每表一张字段表，紧随该表在 ER 图中的表述或其后集中列出；表头前用**一句叙述**说清该表职责，并用 `文件:行号` 指向实际 schema / 实体定义。
- 字段表是"更结构化的叙述"，不是把建表 SQL 原样照搬：字段、类型、主外键、索引、默认值以**表格字段**呈现，行序按设计要点而非建表语句顺序，另配"说明"列写该字段承载的设计取舍与关联。
- 贴码克制铁律沿用（见 [grounding-guide.md](grounding-guide.md)「引用展示与指纹分离」）：**仍不整段复制建表 SQL / 类型定义块**；每张表的精确字段改由字段表 + `文件:行号` 提供，读者可点开真实 schema 复核。仅当某字段或索引结构本身就是不可绕过的设计载体时才放精简片段。

## Schema 演进策略

数据怎么随版本演进：迁移机制（migration 工具 / 手动 DDL）、JSON blob + 提升列的渐进式加字段、向后兼容与读写双写、灰度与回滚。没有迁移层时也要说明当前如何保证演进安全。

## 读写路径

数据从写入到读取的关键链路（谁写、何时写、谁读、经什么中间层）。命中 [writing-guide.md](writing-guide.md)「图表约束」强制图位即用 `sequenceDiagram` 承载时序，标注关键 `文件:行号`，文字只做图外补叙。

> **与上下文的全局关联（沿用 [writing-guide.md](writing-guide.md)「写作规范」全局关联铁律）：** 数据模型不是孤立的表清单——每类数据都要连回它服务哪个业务能力、支撑哪条请求链路，与 README 概览、架构总览、其他子文档间保留过渡句。
