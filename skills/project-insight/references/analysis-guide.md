# 深度解读方法论

> 配合 [flow-new.md](flow-new.md)（全新分析模式）/ [flow-incremental.md](flow-incremental.md)（增量分析模式）使用。写每一段解读前想一遍：
> 这一段给出的是抽象概括，还是能让另一个工程师凭它理解架构、提出质疑的**洞察**？

## 核心立场

深度解读是**技术解构与提炼**，不是代码说明书。判断标准：读者读完能看懂这个项目为什么这样设计、有哪些权衡、能参与架构讨论。每个论断都应包含：**代码依据（`文件:行号`）+ 对比基准 + 推理过程**。`文件:行号` 是叙述的**依据**而非**素材**——用一句话 + 引用指出设计点落在源码何处即可，不必把完整函数体/数据结构复制进解读；需要深究细节的读者自会顺着引用去看源码。

> **引用 = 结论/权衡 + 行号标点，不贴码。** 正文每处引用自带一句说明设计选型的一句话，落 `[路径:行号]` 标点；完整实现不出现在正文。只有"该段代码本身就是不可绕过的设计载体"且用户明确要求时才放精简片段（只取不可绕过的核心，不整段照搬）。反复用 `> [path] — 整段源码` 刷篇幅，是把"依据"误当"素材"，属于深度假象。**真源校验用的指纹注释（`<!-- anchor: … -->`）同理只取引用区间首末行锚点（各 ≤1 行原文），不是把整段代码搬进注释——产出物里出现的代码总量必须收敛到"承载设计的精简片段"这一档。**

> "错误处理统一用 Result 类型而非异常" 不是洞察。
> 洞察是："项目统一用 Option/Result 让错误在类型层面可见，代价是调用方样板代码增加——对这个强调稳定性的基础设施项目，这个权衡是合理的"。

## Why > What（强制）

每个关键论断除了描述"是什么"，必须回答"为什么"。至少追问一层：

- **为什么这样设计？** 不只是"用了什么模式"，而是"为什么适合这个场景"。
- **如果不这样会怎样？** 替代方案的代价是什么。
- **与业界最佳实践比？** 领先之处与改进空间。
- **换你重新设计？** 展示是否真的理解。

> ❌ 路由系统用了中间件模式，支持链式调用。
>
> ✅ 路由选择洋葱模型而非线性管道。线性管道实现更简单，但洋葱模型让每个中间件都能同时处理请求和响应两个阶段——这对日志、计时、错误恢复至关重要。Express 当年选线性模型，后来不得不用各种 hack 处理响应后逻辑，Koa 吸取教训才转向洋葱模型。

## 深够不够？先用 materiality 判据自测

深挖/删剪前先问一句：**如果这条论断是假的，
会不会真的改变读者的架构模型、实现决策、运维预期或安全改法？** —— 不会，就删。
- **atomic 不退化**：一个论断 = 一个可独立证伪的**观点**，不是"每出现一个符号 /
  每行 / 每个文件"就凑一条。同一个函数可为多个不同实质真相各成一条；反之，
  仅为符号存在就罗列不算深度。
- **materiality 与"文件:行号"配套**：够深的论断必然能落到 `文件:行号` 支撑；
  够不上的就要么补引用、要么判为不够实质而删。这条判据放在"深度达标"红线
  之前跑——先把每条论断过滤到"全是实质"，再谈四要素与叙事。

> 本判据不新增要素，只给现有"深度基准"一个可快速自问的收敛式入口：把
> "Why>What、权衡、对比"这类原则罗列，收敛为一句可自测的判别式。

## 对比式思考 / 反事实推理

每个设计决策都存在于一个选择空间里。别只写"选了什么"，要写**"没选什么 + 为什么"**。

更好的检验手法是**反事实**：如果去掉这个设计元素，系统会怎样？
- 仍然正常 → 可能是过度设计。
- 会出严重问题 → 值得展开解释它防住了什么。

> ❌ 模块间用事件总线通信。
>
> ✅ 模块间通信选事件总线而非直接调用。直接调用更简单、调试更容易，但让模块产生编译期依赖——任何接口变更都波及调用方。事件总线代价是运行时才暴露通信错误，换来了模块独立开发部署。对插件化架构，这个权衡是合理的。

## 设计权衡三角

大多数架构决策是在三个目标间做倾斜。找出目标维度，说清项目往哪边倾斜、放弃了哪边，这比笼统说"好/不好"有价值得多。

常见三角：
- 简单性 / 灵活性 / 性能
- 一致性 / 可用性 / 分区容忍
- 开发速度 / 运行时安全 / 学习曲线

## 全局关联

**每个局部分析都要连回项目整体设计哲学。** 这是区分"代码说明书"和"架构解构"的关键。（本 skill 的产物是解读文档，不是独立代码审查。）

- 分析一个模块：先说它在整个系统扮演什么角色。
- 解释一个决策：说明它如何服务整体设计哲学。
- 发现一个问题：评估它对整个系统的影响面。

反面：孤立分析每个模块再拼一起 = 一堆独立代码审查，缺乏整体叙事。

## 叙事连贯

**解读不是章节的拼接，是一条有逻辑的叙事线。** 用户无需目录也懂为什么先讲 A 再讲 B。

常见叙事主线：
- **数据流驱动**：跟一个请求从进来到出去的路径，沿途讲每个模块。适合 Web 框架、API 网关等请求驱动系统。
- **分层驱动**：从底层基础设施讲到上层接口。适合 OS、编译器。
- **问题驱动**：从核心业务问题说起，逐步引入解决子问题的模块。适合复杂业务系统。

模块间要写过渡句，起点是上一个模块的不足或未尽之处，自然引出下一个。

> ✅ Gateway 完成请求的认证与分发，但它只负责"谁可以进来"，不负责"进来之后能做什么"。这个行为控制，由策略引擎承担。
>
> ❌ 接下来我们分析策略引擎模块。

（本 skill 输出是"解读知识库文档"，叙事要求对内嵌在 README 主文档里的一章 `##` / 子文档的一组章节尤其重要——别让每节变成孤立段落。）

## 找到值得深挖的点

不要套模板。发现每个项目独特的"有趣之处"：

- **追问动机**：看到设计选择，问"为什么不用更常见的方案？"没有理由 → 可能是改进点；揭示了深层约束 → 值得展开的洞察。
- **寻找张力点**：性能 vs 可读性、灵活性 vs 简单性。张力的解往往是分析价值最高处。
- **识别设计哲学**：多数成熟项目有贯穿始终的风格（约定优于配置、零成本抽象…）。识别后检验它是否被一致贯彻——不一致处往往有故事。
- **关注边界**：模块/抽象/系统边界。边界定下来就很难改，比内部实现更体现架构思考。

发现亮点的具体手法：**对比法**（"换我设计会怎么做"，和他的方案不同就深挖取舍）、**追问法**（"这解决了什么不明显的问题"，看似过度设计处可能守着一个边界情况）、**场景法**（高并发/网络分区/数据暴增/下游挂掉时如何退化）、**演进法**（git 历史与注释，复杂往往是踩坑后的结晶）。

- **以项目自述为找点线索**：被分析项目 README/文档宣传的能力，是作者"想让读者看到"的信号，常是定位"架构级亮点"的起点——顺着这些宣传点去源码核实：宣传点背后若有真构架、权衡，就是该深挖的候选关注面；若源码并无对应支撑，本身就是该写进"不足/风险"的发现。避免反向（先看实现再猜卖点）。这条线索只负责"提名"，最终仍须 `文件:行号` 源码验证（与 [flow-new.md](flow-new.md)「定维度，非全覆盖」的 README 候选机制同口径）。

亮点的层次决定展开力度：

| 层次 | 示例 | 展开 |
|------|------|------|
| 架构级 | 独特模块化策略、创新扩展机制 | 重点深入 |
| 设计模式级 | 巧妙状态管理、优雅错误传播 | 一段解释 |
| 实现级 | 精巧算法、数据结构 | 仅在体现设计思想时展开 |

> 展开力度与"贴码"是两回事：重点深入的架构级亮点，同样以叙述 + `文件:行号` 为主；仅当用户主动要求、或某段代码本身就是不可绕过的设计载体时，才用精简代码片段。**默认不贴码。** 架构级、设计模式级、实现级三个层次都要遵守由高到低递减的贴码克制——读者要的是"为什么这么设计"，不是回放源码；源码他点 `[路径:行号]` 自己看。

## 批判性对比

诚实评价，不吹不黑：

- **有代码依据**：结论指向具体 `文件:行号`，不凭印象。
- **有对比基准**：说"好/不好"时，对比的是什么——业界实践？同类项目？项目自身目标？
- **区分"不同"与"不好"**：非主流选择不等于错误，可能是在不同约束下的合理权衡。
- **只提架构级问题**：不纠结命名/格式；解释问题实际后果；能给出改进方向时给，不要求完整方案；承认项目约束——有些"问题"在特定约束下是合理妥协。
- **承认不确定性**："从代码看可能是 X，但也可能有我没看到的约束"。
- **不同成熟度不比实现质量**：2 人项目和 200 人项目面对的问题不同，比设计选择而非成熟度。

负面清单：凑问题、回避缺陷、把"非主流"写成错误、没有论证下结论。

## 四要素完整性检验（每个核心模块自检）

一个核心模块/核心实现的解读必须覆盖四要素，缺一项不算完整：

1. **核心数据结构** — 指出理解设计必须的关键类型/接口（**一句定位 + `文件:行号` 指向**，不整段复制类型定义；仅当类型本身就是设计时给精简片段）。
2. **执行流程** — 用**图**（或文字）描述调用链，**标注 `文件:行号`**（须经真源重定位）。**过程性内容一律优先给图**，工具按 [kb-repo-rules.md](kb-repo-rules.md) 的选型规则定（时序/线性流程用 Mermaid；结构/映射/对比/回边状态机用 SVG）；文字只做图外补叙与权衡。
3. **设计决策** — 为什么这么选、不选什么、权衡了什么。
4. **模块间依赖** — 谁调用谁、数据怎么流转、共享了什么状态。

**可复现性检验**：若另一个工程师只读你的解读（不看源码），能否画出架构图并讲清工作原理？如果不能 → 缺了要素。

## 图替段：过程是图，不是文字长段

**读者读图远比读文字快。** 启动流程、请求链路、连接/会话生命周期、跨模块时序这类"过程性"内容，一律**优先画图**（工具按 [kb-repo-rules.md](kb-repo-rules.md) 选型规则），**禁止写成连续文字长段**。文字只做：图外补叙的例外条件、阶段间的 Why/权衡、不好画进图的设计说明。判断标准：一段文字若能被改写成一棵流程树/时序线，就该是图。

> ❌ 用四五行文字铺：*"连接先推到 connect.challenge，客户端带 connect 提交握手，服务端依次校验首帧是 connect、鉴权设备、派生 scope，最后发 hello-ok 进 ready 态……"*
>
> ✅ 一张 `sequenceDiagram`（见 [writing-guide.md](writing-guide.md)「强制图位清单」），节点/泳道各自标注关键 `[路径:行号]`，每步一句边注说明取舍：
>
> ```mermaid
> sequenceDiagram
>     participant C as Client
>     participant G as Gateway
>     C->>G: WS upgrade
>     G-->>C: connect.challenge{nonce}
>     C->>G: req connect (device.signature(nonce)+auth)
>     Note over G: validate→authenticate→authorize→attach（`ws-connection/message-handler.ts:283-392`）
>     G-->>C: res hello-ok (features/policy/role)
>     Note over G: phase="ready"
> ```

（图内要标 `文件:行号`，把"过程 + 落点"合一，读者点图内引用直接跳源码。）

## 正反例对比

**有深度：**
> 路由用基数树而非哈希表。哈希表查找 O(1)，但不支持参数路由 `/users/:id` 与通配符——要支持就退化为线性扫描。基数树静态路由接近 O(1)，同时天然支持前缀匹配，让参数路由与通配符成为一等公民。代价是实现复杂、内存略大，但对以路由性能为卖点的框架值得。Fastify、Hono 也做同样的选择，已是高性能路由事实标准。

特征：具体技术推理 + 量化权衡 + 业界对比 + "为什么适合本项目"的判断。

**没有深度：**
> 路由系统采用高效数据结构存储匹配，支持参数路由与通配符，性能表现优秀。

特征：泛泛而谈、没有推理、换任何项目都成立。

## 大型仓库的文档切分

配合 [flow-new.md](flow-new.md)「分文件判定 / 规模门控·复杂度×规模分流」、[writing-guide.md](writing-guide.md)「丰富内容菜单」、[dimension-triggers.md](dimension-triggers.md)「关注面触发判据」使用，适用于可自然切出多个关注面的项目（**大而深**项目，路径 C）。「小但复杂」项目不拆文件、按四要素单篇深挖（路径 A）；「大而浅」项目退化单 agent 按模块群解读（路径 D），均不适用本节。

- **切分单位 = 关注面，不是目录层级。** 数据模型、问答、skill、MCP、LLM、渠道、会话记忆、语言惯用法……每个能独立成文且够深的关注面一篇子文档，README 只承载概览/架构/导读/总结。关注面由**两个维度**驱动（见 [dimension-triggers.md](dimension-triggers.md)「关注面触发判据」）：**产品类型**（可部署 → 部署文档；有存储 → 数据模型；长流程 → 时序图；智能体 → 记忆机制；Web 框架 / CLI / 编译器 / 数据库 / 前端 / DevOps 各有天然关注面）与**语言惯用法**（Go 并发、Rust 所有权、TS 状态管理等——每个论断落 `文件:行号` + "为什么选这个模型"，落在设计语境，不写成语言教科书）。触发判据见 [dimension-triggers.md](dimension-triggers.md)，**数据模型文档五要素写法**见 [data-model-guide.md](data-model-guide.md)，务必写成设计而非字段清单。
- **README 独立「子文档索引」章节 = 强制**：拆了 N 篇子文档，README 正文就要有专章列 N 条链接（一行一条 + 一句话定位）。新增/拆分随时回写，别等收尾——这是读者导航的入口，遗漏本文档的入口就是"拆了却没人能进"。**「子文档索引」章节只负责"一览全部"，正文导航负责"就近跳转"**：README 的「核心模块导读」表每一行都要用 `[\`xxx.md\`](xxx.md)` 链接到对应子文档，概览 / 架构总览 / 总结中提到某关注面时同样就地给内链——两处互补，读者既能按篇一览、也能顺阅读路径直点深读。
- **为何 README 不承载全部深读**：超大单文档难定位、难增量更新、难审查、git 冲突面大；既有知识库中的多关注面大项目均如此组织。读懂这些项目 = 先看 README 导读表，再顺着链接钻进各关注面子文档。
- **每个子文档仍是完整独立的一篇**：回扣整体设计哲学（全局关联铁律）、与相邻子文档/README 间保留过渡句（叙事连贯）、四要素完整性 + `文件:行号` 真源验证要求一律不变，不因拆分降级。
- **反例**：
  - 一个 500 行 README 硬塞 7 个模块 = 该拆没拆，变成超长难检索的单体。
  - 拆了但每篇只有 50 行罗列 = 为了拆而拆，是碎片的堆叠而非深度解读。
