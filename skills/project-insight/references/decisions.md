# 提炼设计判断：决策卡与模式卡

> 由 SKILL.md 六步主干的 step 4（提炼判断）按需加载。骨架与模板见 [artifact.md](artifact.md)；本文件解决"怎么想出、怎么证伪、怎么避免写成宣传"。

## 先过 materiality：这条判断值得写吗

对每条候选论断问一句：

> **如果它是假的，会不会改变读者的架构模型、实现决策、运维预期或迁移判断？**

不会 → 删掉。会 → 留下，并继续回答下面五个问题。深度不是篇幅，是**每条都承担一个可证伪的判断**。

反例："项目采用了分层架构，模块职责清晰。"——换成任何项目都成立，且不可证伪。
正例："网关把鉴权放在连接建立阶段，代价是权限变更需要断连刷新；当权限要求秒级生效时这个设计会失效。"

## 设计决策从哪找

不要等"看到明显选择"才写。优先在这些地方找：

| 来源 | 要找什么 |
|---|---|
| 系统边界 | 为什么把某能力放进系统内/推给外部？边界一改，全局都变 |
| 依赖方向 | 哪些依赖被刻意禁止？为什么不让 A 直接调 B？ |
| 跨切面 | 鉴权、日志、错误、配置、重试为什么放在这一层而不是那一层？ |
| "多此一举"的设计 | 多余的间接层、队列、状态机、协议——它通常守着一个边界情况 |
| 失败路径 | 超时、重试、降级、回滚、幂等；错误处理最能暴露真实约束 |
| 性能关键路径 | 缓存、批处理、零拷贝、锁粒度；为什么这里值得优化 |
| README 卖点 | 作者最想让你看到的能力，背后往往有一个核心决策 |
| 历史与注释 | TODO、兼容层、废弃路径；但别把"欠账"当"设计" |

规模判据：3–6 张决策卡足够。全写会变成设计文档目录；只写 1 张又撑不起"架构分析"。

## 五要素怎么填（不是填空，是推理）

### 约束

写**外部条件**，不是"我们想这样"。约束通常来自：部署形态（单机/边缘/多租户）、延迟与成本目标、团队规模与运维能力、生态兼容、合规与安全、历史包袱。

> 坏："为了高性能。"
> 好："单机要扛 10k 长连接，且不能引入外部缓存——部署目标是单二进制交付。"

### 选择

写机制，不写口号。"用了事件驱动"不是选择，"模块间通过进程内事件总线解耦，事件在同一个事件循环里同步派发"才是。

### 备选

至少写一个**真实被考虑过**的替代方案，并说清它为什么不行。常见备选：更简单的直接调用、更解耦的消息队列、更成熟的第三方组件、无状态方案、同步改异步。

如果找不到备选，可能不是决策，只是实现细节；或者你还没读到作者的取舍。

### 代价

每个选择都有代价：复杂度、内存、延迟、运维、学习曲线、可调试性、迁移成本。**写不出代价的决策卡，等于宣传材料。**

### 反转条件

写"出现什么信号时应该重新评估"，而不是"未来可能改"。可操作的反转条件长这样：

- 规模：连接数 / 数据量 / QPS 超过某个量级；
- 目标：延迟预算从 100ms 降到 20ms；
- 组织：从单团队变成多团队并行；
- 合规：需要审计或数据驻留；
- 生态：上游协议/依赖发生不兼容变更。

反转条件是决策卡的"保质期"，也是读者最能迁移的部分。

## 反事实：检验理解最快的方法

对每个候选决策做三次"如果"：

1. **去掉它**：如果删掉这个中间层/缓存/状态机，系统会先坏在哪？坏不了 → 可能过度设计。
2. **放大 10 倍**：流量、数据、租户、团队任一放大 10 倍，这个设计还成立吗？先坏的是哪一环？
3. **换约束**：如果部署从单机变多租户、从自建变云托管，这个选择还合理吗？

反事实的答案通常就是"代价"和"反转条件"，比抽象讨论有效得多。

## 权衡三角

大多数架构决策是在三个目标间倾斜。先找出这个项目的三角，再说它往哪边偏、放弃了哪边：

- 简单性 / 灵活性 / 性能
- 一致性 / 可用性 / 分区容忍
- 开发速度 / 运行时安全 / 学习曲线
- 通用性 / 可调试性 / 交付速度

> 不要笼统说"设计很好"。说清"它优先了 X，代价是 Y；在这个约束下合理/不合理"。

## 从决策到模式卡：去掉项目名还能成立吗

模式卡不是"这个项目做了什么"，而是"别人能搬走什么"。提炼步骤：

1. 用一句话写出**共性问题**（不含项目名）；
2. 写出**核心机制**（2–3 句，必要时一张小图）；
3. 写**适用条件**与**不适用条件**（后者更重要，防止读者误搬）；
4. 写**代价**与**落地第一步**；
5. 做"换项目测试"：把名字抹掉，这段是否仍然成立？是否对另一个领域也有意义？

好的模式卡通常来自：边界划分方式、状态所有权、扩展点设计、失败隔离、协议分层、缓存与一致性策略、配置与多环境隔离。

## 避免五种写法

| 写法 | 问题 | 纠正 |
|---|---|---|
| 功能复述 | 没有判断，只是 README 翻译 | 每条功能追问"所以设计上做了什么取舍" |
| 只夸不批 | 读者学不到边界 | 每个亮点配一个代价或失效条件 |
| 假平衡 | "各有优劣"却不给判断 | 给出"在这个约束下选 A 更合理"的结论 |
| 把非主流当错误 | 误读约束 | 先问"它在什么约束下是合理的" |
| 把欠账当决策 | 破坏可信度 | 未完成项放进"边界、风险与开放问题" |

## 成熟度与对比的边界

- 不比"谁更强"，比"在什么约束下谁更合适"；
- 不拿 2 人项目和 200 人项目比工程成熟度；
- 同类对比只在有把握时写，且只比设计取舍（协议、分层、状态所有权），不比 star 数或功能数量；
- 承认不确定性："从代码看是 X，但可能有我没看到的约束。"

## 一张决策卡的合格线

- [ ] 约束是外部的，不是"我们想这样"
- [ ] 选择写到机制层，不是口号
- [ ] 至少一个真实备选，且说清为何不选
- [ ] 代价具体（复杂度/延迟/运维/学习曲线）
- [ ] 反转条件可操作（规模/目标/组织/合规/生态）
- [ ] 抹掉项目名后仍然成立
