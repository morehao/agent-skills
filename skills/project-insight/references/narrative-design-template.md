# 叙述型架构设计说明：骨架模板与形态判据

> 由 SKILL.md「执行流程主干」step 6 与 [kb-repo-rules.md](kb-repo-rules.md)「叙述型文档」按需加载。本文件解决一个具体问题：**同样"要素都写了"，为什么有的文档像架构设计说明，有的像一篇设计评述**——差别往往不在要素多少，而在**骨架**。

## 形态判据：设计文档 vs 设计评述

用读者视角判别，两句话够了：

- **设计文档**：没参与过这个项目的人读它，能理解"系统为什么长成这样"；要改一处时，知道**约束在哪、代价是什么、什么条件下该重新评估**。
- **设计评述**：读起来都对、都在赞赏，但读不出"当初否掉了什么、边界在哪、怎么验收"。

下面任一信号出现，文档就在向"评述"滑落：

| 滑落信号 | 缺的是什么 |
|---|---|
| 通篇讲"系统做了什么"，没有"为什么不做另外那个" | 设计输入（约束与非目标）+ 备选方案 |
| 有原则、有分层，却没有一节回答"整体由哪些部件构成、允许的依赖方向是什么" | 总体架构视图 |
| 说某模块"负责 A、B、C"，却说不出"它对外承诺什么、明确不做什么" | 模块责任矩阵 |
| 只有"选了什么"，没有"什么条件下该回头" | 复审触发条件 |
| 说"性能好/容量足"，却没有可校准的参数与公式 | 量化口径（见 [quantification.md](quantification.md)） |
| 结尾没有"当前不能做什么" | 已知边界 + 验收标准与开放问题 |

## 七步骨架（为什么做 → 怎么落地）

七个问题就是骨架，顺序即叙事主线。**"要素"是核查底线，"骨架"是组织方式**，二者互补、都不能省：

| 步 | 读者的问题 | 建议章节 | 必须回答 |
|---|---|---|---|
| 1 | 为什么做这个系统 | 背景与定位 | 产品定位、目标用户、问题的起点（不是功能列表） |
| 2 | 要解决什么问题 | 背景与定位 | 不解决会怎样；失败的形态是什么 |
| 3 | 有哪些约束 | 设计输入 | 交付/算力/后端/可靠性/多租户/许可约束 + **非目标** + 无法复原的输入 |
| 4 | 系统整体怎么设计 | 总体架构 | 边界在内还是在外、部件清单、允许的依赖方向、运行形态（几种装配） |
| 5 | 核心模块怎么拆 | 核心模块与职责 | 每模块：负责什么 / 对外提供什么 / **明确不做什么** / 依赖谁 |
| 6 | 数据与请求怎么流转 | 写入链路、处理策略、读取链路、状态与持久化 | 端到端链路 + 关键状态机 + 真源划分 |
| 7 | 为什么这么设计、怎么落地 | 决策与代价、部署形态、容量口径、已知边界、验收与开放问题 | 每条决策的代价、备选方案与**复审触发条件**、可验收的承诺 |

## 13 章骨架（可直接套用，替换项目内容即可）

| 章 | 标题 | 承载 | 常见疏漏 |
|---|---|---|---|
| 一 | 背景与定位：为什么做、要解决什么问题 | 定位 / 目标用户 / 问题的起点 / 设计信条与质量模型 | 写成功能清单 |
| 二 | 设计输入：约束、非目标与技术选型 | 需求与约束 / 非目标 / 无法复原项 / 技术栈与其代价 | 只写选型不写代价；把欠账写成"刻意选择" |
| 三 | 总体架构：边界、部件与依赖方向 | 系统边界视图 / 分层与依赖方向 / 运行形态 / 协作承诺 | **整章缺失**（最常见） |
| 四 | 核心模块与职责 | 组织原则 / 模块责任矩阵（含"明确不做什么"） | 只列目录、不列边界 |
| 五 | 写入链路：完整生命周期（含任务调度） | 端到端全景 / 状态机 / 并发控制 / 租约 / 重复投递 / 本章边界 | 写成操作手册 |
| 六 | 处理策略：从原始输入到可检索单元 | 策略主张 + 执行约束 + 可调参数 + 代价 | 写成参数说明，没有"为什么这样处理" |
| 七 | 读取链路：从提问到可溯源回答 | 运行时视图 / 召回与排序 / 引用与溯源 | 只写"检索+生成"，缺可溯源性 |
| 八 | 执行模型（有 Agent / 工作流时） | 画布与运行时 / 工具面 / 记忆 / 多渠道 | 与链路章重复 |
| 九 | 状态与持久化全景 | 真源划分 / 幂等 / 迁移策略 | 画成 ER 图（那是证据型文档的活） |
| 十 | 关键设计决策与代价 | 决策表（选了什么 + 代价）+ **备选方案与复审触发条件** | 无备选、无触发条件 |
| 十一 | 部署形态与运行拓扑 | 进程与外部依赖 / 配置分层 / 启动期易错点 | 与总体架构重复 |
| 十二 | 容量与性能口径 | 吞吐 / 延迟 / 容量估算模型 + 档位示例 | 编造指标，或只写"指标缺失" |
| 十三 | 已知边界与缺口 | 按影响面排序的限制 | 写成免责声明 |
| 十四 | 验收标准与开放问题 | 可自动化验收点 + 只能人工抽样的部分 + 开放问题 | 最容易漏掉的一章 |
| 附录 A | 概念与实现用词对照 | 读者用词 ↔ 实现用词 | — |
| 附录 B | 场景索引：问题到架构位置 | "我要做 X → 看哪一节" | 长文没有它，检索成本极高 |

章数不必与上表一致（项目简单时可合并），但**总体架构、模块责任、决策备选、验收**四章不得省。

## 编号与交叉引用纪律（叙述型文档的豁免与代价）

本 skill 通则要求"标题不加数字序号前缀"；**叙述型文档是明确豁免**：设计文档用 `## 一、` 与 `### 3.1` 编号是行业惯例，长文交叉引用（"见 5.8"）依赖它。

豁免有条件，三条且由程序兜底：

1. **唯一**：`##` 章序号不得重复；同章内 `### N.M` 不得重复。
2. **递增**：同章小节号严格递增（跳号会被提示）。
3. **可解析**：正文出现的 `见 N.M` / `第N章` / `附录 X` 必须真实存在。

三条由 `scripts/scan-narrative.mjs` 的 `[HEADING-SEQ]` / `[XREF-DANGLING]` 强制。**重排章节后必须重跑**——重排最容易只改到一半（本项目实际发生过：`### 7.2` 重复 + 6 处交叉引用失效，程序一跑就现形）。

> 交叉引用只写章节号，**不要写"图 N"**：图号会随结构失效。确需编号时按出现顺序统一生成。

## 图与表在骨架里的位置

- **图前必须有导读段，图后必须有着落**：图不是插图。一个小节只有一张图、没有任何正文，会被 `[FIGURE-ONLY]` 提示——读者不知道该看什么。
- 结构类图（拓扑 / 分层 / 部署 / 边界）用 SVG；时序与真·线性小图用 mermaid；阈值见 [writing-guide.md](writing-guide.md)「图表约束」。
- 量化内容优先"表格 + 公式"，不要写成形容词（见 [quantification.md](quantification.md)）。
