# 好坏对照：一份分析应该长什么样

> 由 SKILL.md step 5（成文自检）按需加载。以下示例均为**虚构项目 Nimbus**（一个长连接网关），只示范写法，不构成事实。

## 一句话结论

**差**

> Nimbus 是一个高性能、可扩展的长连接网关，架构清晰，模块职责明确，值得学习。

问题：换成任何网关都成立；没有判断，不可证伪。

**好**

> Nimbus 最值得学的是三件事：把鉴权前移到连接建立阶段（代价是权限变更要断连）、用单进程事件循环替掉外部缓存（代价是不能水平扩单连接）、把协议演进做成可协商的能力位（代价是握手变复杂）。它不适合需要秒级权限撤销或多租户共享连接池的场景。

好在哪：每条都有机制 + 代价 + 不适用；读者能立刻判断"与我的场景是否相关"。

## 架构全景（节选）

**差**

> 项目分为 gateway、session、protocol、store 四个模块。gateway 负责连接管理，session 负责会话，protocol 负责协议解析，store 负责存储。模块之间通过接口解耦，结构清晰。

问题：这是目录说明；没有边界、依赖方向、运行形态，也没有取舍。

**好**

> 系统的边界画在"连接"上：Nimbus 只负责连接生命周期、帧路由与背压，消息持久化推给外部 store；因此它可以在无状态进程里跑，也能单二进制交付。依赖方向是单向的——protocol 不感知 session，session 不感知 gateway 的具体 transport；这条约束让同一套会话逻辑能同时跑在 TCP 与 WebSocket 上。运行形态只有两种：单进程（默认）与"网关 + 外部 store"（持久化开启时）。代价是跨进程的会话查询要多一次网络往返，换来的是部署形态的简单。

好在哪：边界、依赖方向、运行形态、代价都在；读者能画出图。

## 决策卡（完整示例）

```markdown
### 决策：在连接建立阶段完成鉴权，而不是每个请求都验一次

- **约束**：单机要扛 10k 长连接；请求频率高；部署目标是单二进制，不能引入外部缓存。
- **选择**：握手时验签，把权限快照挂到连接对象上；后续帧只做轻量校验。
- **否掉的备选**：
  - 每请求查权限：多一次存储/缓存调用，延迟与连接数线性放大；
  - 无状态 JWT：验签便宜，但撤销要等过期，无法满足"踢下线"。
- **代价**：权限变更需要断连重连或服务端主动推送刷新；连接对象持有权限快照，内存随连接数增长。
- **反转条件**：权限需要秒级生效、单连接跨多租户、或连接数增长到快照内存不可忽略时，应改为"每请求轻量校验 + 集中策略缓存"。
- **迁移提示**：适合长连接、权限变化不频繁、单租户网关；不适合短连接 API 网关或多租户共享连接池。
```

合格线：约束是外部的、备选真实、代价具体、反转条件可操作、抹掉项目名仍成立。

## 模式卡（完整示例）

```markdown
### 模式：能力位协商（capability negotiation）

- **解决**：协议要向前兼容，又不能为每个版本维护一套解析分支。
- **做法**：握手时双方交换能力位；后续帧只使用双方都声明支持的字段；未知能力位忽略而不是报错。
- **适用**：长连接、客户端版本不可控、需要灰度上线新特性的协议。
- **不适用**：安全关键字段（不能"忽略"）、一次性短连接、双方版本可强制统一的内部系统。
- **代价**：握手变复杂；每个新能力都要定义降级行为；测试矩阵随能力组合增长。
- **落地步骤**：先定义能力位与缺省行为 → 握手交换 → 服务端按连接能力裁剪响应 → 为每对能力组合补契约测试。
- **本项目落点**：protocol 的 hello 帧与会话建立阶段。
```

合格线：项目名抹掉仍成立；"不适用"比"适用"更有价值。

## 学习路径（示例）

```markdown
## 学习路径与练习

- **30 分钟**：读 `README` 的协议一节 + 连接握手入口 + 一张时序图，回答"鉴权发生在哪一步"。
- **半天**：沿着"客户端连接 → 握手 → 首帧 → 路由"走一遍，对照测试用例看失败路径（鉴权失败、超时、重复连接）。
- **动手改**：加一个"连接建立时打印协商出的能力位"的调试日志，验证你对握手阶段的理解。

自测：
1. 如果去掉权限快照，哪条链路会先坏？
2. 连接数放大 10 倍，最先成为瓶颈的是哪一环？
3. 要让新能力对旧客户端透明，需要改哪几处？
```

## 常见坏味道速查

| 坏味道 | 一眼识别 | 改法 |
|---|---|---|
| 功能复述 | "支持 A、B、C" | 每条追问设计取舍 |
| 目录说明 | "X 模块负责…" | 写边界、依赖方向、失效模式 |
| 无代价 | 全是优点 | 每个亮点配一个代价 |
| 假精确 | "性能提升 300%" 无口径 | 给条件或改成口径模型 |
| 引用堆砌 | 每段都是 `path:line` | 移进附录，正文只留判断 |
| 图无着落 | 一节只有一张图 | 补导读与"该看什么" |
