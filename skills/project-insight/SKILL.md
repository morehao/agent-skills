# 开源项目架构分析

## 这个 skill 产出什么

一份**能带走的架构学习文档**，不是项目说明书，也不是源码导读。判断标准：读者读完能做到四件事——

1. 画出系统边界与依赖方向；
2. 说出 3 个关键设计决策的约束、代价与反转条件；
3. 指出 2–3 个可迁移到自己项目的模式，并知道什么情况下不该用；
4. 知道下一步读哪、动手改哪。

**三条原则**

- **结构先于细节**：先定边界、部件、依赖方向，再进模块。
- **决策先于功能**：功能清单谁都能抄；值钱的是"为什么这样、否掉了什么"。
- **证据按需**：默认用叙述与结论；只有需要核验的论断才补 `文件:行号`。

> **不编造**模块、接口、数字与版本。不确定就标 `[待核]` 并放进"边界、风险与开放问题"，不要用流畅的文字掩盖没读到的东西。

## 两种模式

| 模式 | 何时用 | 代码索引 |
|---|---|---|
| 学习分析（默认） | "读懂/学架构/值得学什么/为什么这样设计" | 不需要；文件名、模块名可提 |
| 证据核验（可选） | 用户明确要求可核验；或结论涉及安全/性能数字、与项目自述冲突、要写公开文章 | 需要：集中到「附录 A」给 `path:line`，跑 `verify-references.mjs` |

**同一个项目只产出一份文档**（深读档可按主题分册，但仍是一套同性质的文档）。证据是附录，不是第二份文档；不要同时写"证据版 README + 叙述版设计文档"。

## 何时不用

- 写使用教程、API 文档、官方文档翻译；
- 给不读源码的人做项目介绍 → `project-wiki`；
- 给自己系统写技术方案 → `tech-design`；
- 只想要一张独立图表 → `svg-maker`。

## 三档深度（先定档，避免小题大做）

| 档 | 触发 | 产出 |
|---|---|---|
| 速览 | "快速看看 / 值不值得学" | 1 页：架构图 + 3 条决策 + 2 个可迁移点 |
| 标准（默认） | 常规深读 | 完整骨架，约 3–6K 字 |
| 深读 | 大而深项目 / 要写系列 | 标准 + 证据附录 + 同类对比 + 可按主题分册 |

## 六步主干

| 步 | 做什么 | 按需加载 |
|---|---|---|
| 0 输入与范围 | 本地路径 / 远端；记录基线一行；明确想学什么（没说就按标准档全貌）；只读，不改源码 | [evidence.md](references/evidence.md)（远端克隆 / 基线） |
| 1 快速建模 | README → 目录 → 构建与入口；判定项目原型 | [method.md](references/method.md)「原型判定」 |
| 2 架构骨架 | 边界、部件、依赖方向、运行形态；画第一版图 | [artifact.md](references/artifact.md)「架构全景」+ [diagrams.md](references/diagrams.md) |
| 3 垂直切片 | 走 1–2 条关键链路，记录沿途决策与异常路径 | [method.md](references/method.md)「垂直切片」 |
| 4 提炼判断 | 决策卡 + 模式卡 + 反事实推理 | [decisions.md](references/decisions.md) |
| 5 成文自检 | 按骨架写；图与链接校验（`check-doc` / `check-mermaid` / SVG 审计）；学习效果五问；需要时补证据附录 | [artifact.md](references/artifact.md) + [examples.md](references/examples.md) |

已有分析要更新 → [incremental.md](references/incremental.md)：先读旧文，再按上游 diff / 发布说明改，只动受影响部分。

## 产物骨架（标准档）

```markdown
# <项目> 架构分析

> 一句话结论 + 3 条可带走

## 问题与约束       它解决什么根本问题；不做会怎样；硬约束（部署/性能/团队/生态）
## 架构全景         边界图、部件清单、允许与禁止的依赖方向、运行形态
## 模块责任矩阵     负责 / 明确不做什么 / 依赖谁 / 失效模式
## 关键链路         1–2 条端到端链路（图）+ 沿途取舍
## 设计决策卡       约束 / 选择 / 否掉的备选 / 代价 / 反转条件
## 可迁移的手法     模式卡：适用 / 不适用 / 代价 / 落地步骤
## 边界、风险与开放问题
## 学习路径与练习   30 分钟 / 半天 / 动手改 + 3 个自测问题
## 附录 A：证据（可选）
## 附录 B：术语与同类对比（可选）
```

章节名可随项目调整，但**决策卡、模式卡、学习路径**三件不能省——它们是"文档"与"教材"的分水岭。逐章必答问题、模板与好坏示例见 [artifact.md](references/artifact.md)、[examples.md](references/examples.md)。

## 证据规则

默认正文不出现行号。只有以下情况补证据，且**集中到附录 A**：

| 触发 | 例子 |
|---|---|
| 反直觉 / 关键机制 | "用两阶段提交保证一致性""连接建立时就把权限定死" |
| 与 README / 官方文档冲突 | "宣传支持 X，实际只支持 X 的子集" |
| 数字 / 性能 / 容量 / 安全 | 延迟、吞吐、内存估算、限流阈值 |
| 用户明确要求核验 | "给出行号 / 要能点开验证" |
| 增量更新 | 上游 diff / release notes 作为改动依据 |

- 格式：`- [路径/文件.ext:start-end](可选链接) — 一句话结论`，紧跟逐字锚点（首末行各 ≤1 行）；跑 `node scripts/verify-references.mjs <source_repo> <doc.md>`。
- 零索引模式：抽 10 个模块/文件名核对存在性（`check-doc.mjs --source-repo` 可选）；编造即返工。
- 数字没有实测 → 写"估算口径 + 参数 + 假设"，不写假精确；确实不可复原 → 明说。细则见 [evidence.md](references/evidence.md)。

## 落点与提交边界

- **用户指定目录优先**；未指定时写当前目录 `<项目>-架构分析.md`。
- **绝不写进 `source_repo`**（含其子目录）。cwd 在源码仓库内时，写到仓库外（如父目录），写前用 `realpath` 确认目标不在 `source_repo` 下；不确定就问。
- 默认单文件；确有 ≥3 个可独立深挖的主题、且每篇都够深，才拆成 `<项目>-架构分析/` + 主题文件，并给一个简短阅读顺序（不强制索引表）。
- 只有用户明确要求落入知识库时，才做 `{分类}/{项目}/` 结构与索引同步（见 [artifact.md](references/artifact.md)「入库模式」）。
- 只写文件，**不执行 `git add/commit/push`**；落盘后列出变更清单，交给用户决定。

## 质量红线（落盘前逐项自检）

- [ ] 根因与约束说清（不是功能清单）
- [ ] 架构全景图（结构/边界/依赖方向）
- [ ] ≥3 张决策卡：备选、代价、反转条件齐全
- [ ] 模式卡：速览档 ≥2，标准/深读 ≥3；适用 / 不适用 / 代价 / 落地步骤齐全
- [ ] 边界、风险与开放问题明确；宣传与实现不符处已标注；不确定项写进开放问题
- [ ] 标准/深读档：模块责任矩阵（含"明确不做什么"）+ ≥1 条关键链路 + 学习路径 + 3 个自测问题
- [ ] 无编造：模块 / 文件 / 数字真实；不确定标 `[待核]`
- [ ] 图可渲染、无重复图（`check-doc.mjs` 查链接与 SVG 元信息；Mermaid 跑 `check-mermaid.mjs`；SVG 跑 `audit-svg-topology.mjs`）
- [ ] 未写进 `source_repo`；未擅自提交

## 与相邻技能的分工

| 需求 | 用 |

| 学这个项目的架构设计、要判断与可迁移模式 | **本 skill** |

| 只要一张独立图表 | `svg-maker` |

## 常见失败

- 把 README 功能列表翻译一遍 → 回到「问题与约束」，先写"不做会怎样"。
- 只讲"选了什么"、不讲"否掉了什么" → 决策卡缺备选，返工。
- 满篇路径行号、没有判断 → 切回默认模式，把证据移进附录。
- 图很漂亮但边连错 → 跑 `scripts/audit-svg-topology.mjs`，别靠目测。
- 大仓读不完就硬啃 → 按 [method.md](references/method.md)「大仓策略」分主题，不追求覆盖率。
- 模块/文件/数字没核实就写 → 标 `[待核]` 或删掉；**流畅不等于正确**。
