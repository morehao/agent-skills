# Tech Design + Research（调研驱动的技术设计文档）

**一句话**：`tech-design` 负责把方案写「对、全、可评审」；本技能负责让方案**在动笔前就有参照系**——先调研同类开源实现并读源码取证，用业界主流校准取舍，再落盘、再评审闭环。产物与 tech-design 一样是一份设计文档，区别是它**带着开源对标背书**。

典型形态：写一个经典系统设计题（短链服务、秒杀、IM、Feed 流、分布式任务调度、CDN、限流器……）。先看业界成熟实现怎么做的，再写自己的，避免「自己拍脑袋想一套，业界早有更好的」。

## 和相邻技能的分工（开工先判）

| 用户要什么 | 走哪个 |
| --- | --- |
| 写方案，且要**参考开源 / 符合主流 / 看看业界怎么做** | **本技能** |
| 只写方案，不需要开源调研 | `tech-design`（本技能是它的增强，不重复它的内容） |
| 只深度解读**一个**开源项目源码 | `project-insight` |
| 只要一份独立 SVG / HTML 图表 | `diagram-design` |

本技能**不重写 tech-design**：写作骨架、档位/场景/专题、五条硬要求、`check-design-doc.mjs` 门禁、评审 gate 的 lens 定义，**全部以 `tech-design` 为真源**。本技能只补「调研前置、终局取舍、输出落点、闭环收尾」，并给出串接顺序。

## 流程（按序；开工确认与调研都在写作之前）

> **顺序要点**：调研（第 1 段）**先于**第一版（第 2 段）。先把业界参照系摸清，第一版就带着它写，而不是写完再回头打补丁。哪段发现前面错了就回去改。

### 第 0 段：定课题、档位与输出落点（5 分钟，别跳过）

**A. 用 `tech-design` 的「开工先判」定三件事**：落点（新系统 A / 既有新模块 B / 既有模块 C）、场景（S1–S6 单选）、档位（轻量/标准/完整；**默认完整档**，作答见第 0.5 段）。

**B. 定输出落点——先探测环境，再给选项让用户选一次**（细则见 `references/delivery.md`「输出位置规则」）：

1. **用户本次明确指定了路径 / 文件名** → 用用户的，最高优先，不再问。
2. 没指定 → **探测环境**：向上找 `.obsidian/`（判断是否在 Obsidian 库内），并在库里找与课题最贴合的主题目录。
3. 用 `ask_user_question` 给选项，**Obsidian 存在时把「写入库内某主题目录」排第一并标推荐，且把具体路径直接写进选项**（如 `Learning/Programming/架构与设计/系统设计实战/`），不要只给「Obsidian」三个字让用户自己翻；同时留「库内其它目录 / 自定义绝对路径」等可选项。
4. **没拿到用户选择就别写盘**（除非用户一开始就给了明确路径）。

**C. 问清基调**：这次是「**设计阶段、面向终局**」还是「**当期落地、最小改动**」？两者对同一决策答案常相反（见第 2 段 `domain_id`）。用户没说 → 按「面向终局、求合理与主流」——本技能默认立场。

### 第 0.5 段：开工确认（用选项问，每项都带推荐，别替用户拍板）

下面这些点**答案会显著改变产出、我无法从上下文可靠推断**——用 `ask_user_question` 一次问清（多问题一次问完，别挤牙膏）。能从用户原话或上下文推断的就不问。

**硬性要求：每个问题都要给推荐项，推荐项排第一、并在选项 label 末尾标「（推荐）」**；用户跳过某题就按下面的默认值表走，并在交付报告里点明用了默认。

| 待确认项 | 为什么问 / 影响什么 | 选项（首项即推荐） | 默认（用户不答） |
| --- | --- | --- | --- |
| **基调：终局 vs 当期**（推荐：终局） | 决定 `domain_id` 这类不可逆结构要不要前置；答错整篇返工 | ①**面向终局**（推荐，结构一次到位、允许为未来多定）②当期落地（最小可用） | 面向终局 |
| **档位**（推荐：完整） | 决定篇幅与评审范围 | ①**完整**（推荐，+成本/容灾/压测企业级章节）②标准（完整方案+详细设计）③轻量（1–2 屏骨架） | 完整档 |
| **评审深度**（推荐：标准评审） | 评审有成本；要不要起 subagent 跑语义 lens | ①**标准评审**（推荐，门禁+图校验+1–2 关键 lens）②完整评审（全 lens+builder）③只跑机械门禁 | 完整档→完整评审，其余→标准评审 |
| **交付动作**（推荐：只分析） | 只分析 vs 直接改文档，是两回事 | ①**只分析/出建议**（推荐，先给你看再改）②直接改文档 | 只分析、不改 |
| **取舍拍板权**（推荐：我按终局自决并标理由） | 涉及范围与成本的取舍要不要你逐条拍 | ①**我按终局自行决定并写理由、需你拍板的列开放问题**（推荐）②涉及范围/成本的都停下来问你 | 我自决 + 列开放问题 |

**调研项目不是选项，是默认行为**（见第 1 段）：默认由我选主流代表去调研；**若你的指令里点名了某个开源项目，就在默认调研之外，额外把那个也调研一遍**（追加，不替代）。

> 原则：**能用默认值又快又不返工的，就别问；会返工或改范围的，必须问，且每个问题都给推荐**。一次问全，别把同一决策拆成多轮。

### 第 1 段：开源调研（本技能的核心，见 `references/oss-research.md`）

**在写第一版之前做。调研是默认行为，不需要用户要求。**

- **默认调研**：由我选同类主流代表（覆盖不同技术路线）——这部分**总是做**。
- **追加用户点名的项目**：若用户指令里点名了某个开源项目（「参考 XX」「看看 XX 怎么做的」），就在默认调研**之外**把它也调研一遍（**追加，不替代**默认调研）。

分两级，能到第二级就到第二级：

1. **初筛读 README / docs / CHANGELOG**：识别技术栈、ID/短码生成方式、跳转语义、统计方案、安全做法，产出一张**「业界 vs 本方案」横向表**，标出「业界有什么更好做法 / 本方案该学什么」。
2. **`git clone --depth 1` 到临时目录读源码**（用完清理）：对会改变设计的**关键论断**逐条取证。README 会漏、源码不会——唯一键真实定义、点击去重、UV 哈希口径这些都在源码里。

**纪律**：不硬凑（Go/Rust 常缺生产级高星，如实写对标对象）；每条借鉴回指「写进文档哪节 / 哪个决策」；AGPL/GPL 只作架构参考、不抄代码。

详见 `references/oss-research.md`。

### 第 2 段：带着参照系写第一版（覆盖 tech-design 写作流程）

按 `tech-design` 的叙事链 9 问 → 取证 → 对账 → 量化 → 配图 → 撰写。**但把第 1 段的横向表当作输入**：

- 每个「业界更好做法」在写作时就决定：采纳（写进对应决策）还是不采纳（写理由），别留到最后补。
- 落盘后先跑一遍机械门禁 `check-design-doc.mjs`，清掉占位符、空壳章节、缺图、DDL 不一致等机械项。

### 第 3 段：按终局把取舍做到位

- **不可逆的结构决定**（唯一键、主键形态、分片键、状态机枚举、契约字段）即使当期用不上也按终局定死，并写清「不改的代价」。典型：唯一键要不要带 `domain_id`——当期单域名不必，但二期改索引要停机迁全表，终局现在就带。
- 业界成熟方案优先；本文拍脑袋的换成业界方案并注明出处。
- 每项都要「业界谁这么做 + 本文为什么采纳/不采纳」，不采纳也写理由（如 Shlink 的 GeoIP 离线批处理，本文因 5 分钟延迟选写入侧）。

### 第 4 段：独立评审 + 门禁闭环（见 `references/review-loop.md`）

1. 机械门禁 `check-design-doc.mjs --tier <档位> --strict`：error/warn 清零。
2. 图校验：Mermaid `check-mermaid.mjs`；结构类 SVG `audit-svg-topology.mjs` 端点贴合。
3. 独立上下文跑 1–2 个 lens（按场景选：数据 / 图与论证 / 安全 / 调用方），各回 `VERDICT` + top findings。
4. 收成单一 `VERDICT: approve | revise`；`revise` 改完**重跑门禁**（改文档会引入新机械问题）。

### 第 5 段：命名与收尾（见 `references/delivery.md`）

按命名规则定文件名、改名同步 wikilink、备份、给交付报告。**本技能不涉及任何 git 操作，也不涉及技能发布。**

## 红牌（出现这些念头就停下）

- 「先写，写完再看开源」——本技能明确反着来：调研前置，否则第一版就得大改。
- 「基调/档位/调研深度先按我想的来，用户应该没意见」——这几项答错要返工，第 0.5 段明确要求给选项问。
- 「README 看过了，够了」——关键论断没读源码就下结论，等于抄宣传稿。
- 「当期用不上，唯一键先单列吧」——不可逆结构迁就当期，二期停机迁表。
- 「业界这么干，我们也加上」——没写代价与不采纳场景的借鉴，不算取舍。
- 「随便找个目录存一下」——落点先探测环境、给选项让用户选（Obsidian 优先、路径写进选项），别乱塞也别擅自定。
- 「门禁 0 error 了，可以交付」——门禁只管机械项，像不像主流靠评审 lens。
- 「文件名无所谓」——`短链.md` 与 `短链-系统设计.md` 清晰度差一截，命名有规则。

## 记录与备份约定

- 过程文档（调研台账、评审记录）：落工作区 `.dsh/docs/notes/<日期>-<主题>-<类型>.md`，默认 gitignore、不入库。
- 备份：批量/结构改动前备份到 `.dsh/backups/<时间戳>-<标签>/` 并写 `manifest.json`（含 sha256）。
- **本技能不做任何 git 操作（不 add / 不 commit / 不 push / 不和分支、PR 打交道），也不做技能发布**；这些留给用户和其他技能。
