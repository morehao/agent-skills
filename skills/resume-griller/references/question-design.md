# 选题设计

题目从简历里长出来，不从题库里挑。这份文档管「问什么、问到多深、怎么追问」。

## 题池与取舍

一场面试能深聊的只有 5–8 题，但题池应该更大：**先出 10–14 道，再挑**。面试官现场按候选人的回答改道，靠的就是池子里有可替换的题。

| 档 | 用途 | 数量（60 分钟） |
|---|---|---|
| 必问 | 没问清就不能下结论的（核心项目、量化口径、事实矛盾） | 3–4 |
| 选问 | 按时间与兴趣挑着问的（技术广度、相邻领域） | 3–5 |
| 备用 | 二面、时间富余、想深挖或换角度时用 | 4–6 |

备用题也要写全题源、锚点、答案键——翻到就能用，不能只留个标题。预算只算必问 + 选问。

## 选题来源（按优先级）

| 来源 | 取什么 | 占题量 |
|---|---|---|
| 项目经历 | 一个项目 = 一个主题；取决策点最密的那一两个 | 主体（约 2/3） |
| 技能缺口 | 「技能」栏有、项目里无的技能；跨度过大的技术栈 | 1–2 题 |
| 协作与动机 | 跨团队推进、冲突处理、离职原因（仅在简历有对应痕迹时） | 0–1 题 |

项目选择看三件事：**与岗位的相关度**、**简历里描述的具体度**（有数字和职责的优先）、**可疑度**（时间线、口径、贡献度）。不要按简历顺序出题，按「这场面试最需要确认什么」排序。

## 好问题的五条判据

一道题同时满足越多条越好，少于三条就重写：

1. **有对象**：问的是一个具体决策、一次失败、一个数字的口径，不是「你怎么看 X」。
2. **有取舍**：候选人必须说出放弃了什么、代价是什么；只有一个正确答案的题问不出判断。
3. **要证据**：答案必须落到他做过的事、看过的数据、跑过的实验上。
4. **有边界**：存在「什么情况下这套做法不成立」，能继续追问失效条件。
5. **可追问三步**：至少能顺着往下问三层（事实 → 决策 → 反例）而不掉进细节。

## 深度阶梯

| 层 | 问什么 | 例 |
|---|---|---|
| L1 事实 | 复述做法 | 「这个服务怎么拆的？」 |
| L2 决策 | 为什么这么做 | 「为什么按业务域拆而不是按读写拆？」 |
| L3 取舍 | 放弃了什么、代价多少 | 「拆完跨域查询怎么解决的，多写了多少代码？」 |
| L4 评估 | 怎么证明有效、怎么证伪 | 「你怎么知道拆完确实变好了？指标掉下去你会怎么判断是拆错了？」 |
| L5 迁移 | 换条件还成不成立 | 「如果团队只有三个人、QPS 再降一个数量级，你还会拆吗？」 |

**默认从 L2 起步、L3 收口**；高级岗与架构相关主题要摸到 L4/L5；L1 只在简历描述与事实明显对不上时用来校准，不作为独立题。

## 题型与问法

| 题型 | 适用 | 问法骨架 |
|---|---|---|
| 决策复盘 | 有明确技术选型的项目 | 「当时在 A 和 B 之间，你按什么定的？现在回看会改吗？」 |
| 失败归因 | 简历写了「优化」「重构」「提升」但没写代价 | 「这次改造最不顺利的一段是什么？根因在你、在依赖、还是在需求？」 |
| 评估设计 | 有量化结果的项目 | 「这个提升是怎么测出来的？口径是什么、对照组是什么、噪声多大？」 |
| 边界与失效 | 用了框架/方案但没写限制 | 「这套方案在什么条件下会先崩？你怎么发现的？」 |
| 迁移推演 | 想考判断而非记忆 | 「把规模缩小十倍、或把一致性要求提高一档，你的方案哪一步先变？」 |
| 缺口核实 | 技能栏与项目不互证 | 「简历里写了 Kafka，但项目里没看到它出现在哪条链路上，能说一个你实际用它解决的问题吗？」 |
| 协作与边界 | 跨团队、带人、对外承诺 | 「这件事需要别的团队改，他们不配合时你怎么推进的？」 |

**不要出**：算法题、语言语法题、框架 API 默写、名词解释、脑筋急转弯。这些不是简历分析的产物，也测不出项目判断。

## 追问写法

每个追问写两样东西：**何时问**（触发条件）+ **想听到什么**（一句话）。没有触发条件的追问是废问。

```markdown
- 追问：
  - 若他只讲了「用了 Redis 缓存」：问「缓存和库的一致性怎么保证的？脏读窗口多大？」（想听：版本号或延迟双删的具体选择）
  - 若他说「没出过问题」：问「上一次缓存和库不一致是什么时候，怎么发现的？」（想听：监控口径，不是运气）
```

追问贴在所属问题下，不集中放到文末——面试时是按题走的，不是按清单走的。

## 按级别校准

| 候选人级别 | 主问落点 | 期望的答案深度 |
|---|---|---|
| 初级 / 1–3 年 | L2 | 能讲清自己那部分的做法与理由 |
| 中级 / 3–5 年 | L3 | 有取舍、有代价、有量化 |
| 高级 / 5 年以上 | L4 | 能设计验证、能说失效条件 |
| 架构 / 研究 | L5 | 能推演条件变化后的方案变化，能给出反例 |

级别判断依据是简历自述的年限、职责范围、项目规模；判断不了就用中级档，并在「注意事项」里写明。

## 简历薄弱时

- **项目只写了职责没写结果**：问「这件事上线后谁受益、怎么衡量」，把结果问出来；答不出是有效信号，不要替他补。
- **全是团队成果、看不出本人贡献**：「哪一部分是你亲手写的？哪一部分是你推动别人写的？」——这题几乎必出。
- **时间线重叠 / 短期跳槽**：不当作质疑，改成「两段并行时你怎么分配时间」；动机类问题只问一次。
- **技术栈与岗位差得远**：只考可迁移的判断（规模、一致性、成本、失败处理），不考对方没做过的领域知识。

## 坏问题清单

| 坏问题 | 为什么坏 | 改成 |
|---|---|---|
| 「讲讲你对分布式的理解」 | 无边界的背诵题 | 「你那个订单服务为什么最后选了最终一致？」 |
| 「Kafka 的 ISR 机制是什么」 | 查文档就会 | 「消息重复时你怎么保证幂等，重复从哪来的？」 |
| 「你最大的缺点是什么」 | 八股，拿不到证据 | 「上一次你的判断被数据推翻是什么事？」 |
| 「如果给你一千万 QPS 你怎么设计」 | 与简历无关的假设题 | 「你的系统涨到十倍，第一个撑不住的是哪」 |
| 「这个项目是不是你做的」 | 质问语气，易防御 | 「这个项目里哪一块是你独立负责的？」 |
| 「你觉得自己能打几分」 | 无信息量 | 直接按维度打分，面试后写 |

## 自检清单（交付前逐条过）

- [ ] 每题都有题源，且引用的是简历原文而不是转述
- [ ] 每题至少一个 L3 及以上的落点，没有纯 L1 题
- [ ] 追问都有触发条件，且贴在所属问题下
- [ ] 技能栏逐项有题号或 `覆盖豁免：<理由>`
- [ ] 题目时长合计 ≤ 面试时长，开场与收尾没有被挤掉
- [ ] 没有算法题、API 默写、名词解释
- [ ] 同一技能没有用两个角度重复出题
