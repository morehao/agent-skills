# 手册格式契约

`check-interview-doc.mjs` 校验的结构以本文为准：改骨架就同步改门禁与回归测试，三者不许各说一套。

## 输入契约

| 项 | 必填 | 说明 |
|---|---|---|
| 简历正文 | 是 | 粘贴文本、`.md`/`.txt`，或由 PDF/DOCX/图片抽取；读不出就请用户粘贴，不装依赖 |
| 面试时长 | 否 | 默认 60 分钟；写进元数据块 `minutes` |
| 候选人级别 | 建议 | 元数据 `level`：初级 / 中级 / 高级 / 架构；**决定 ★ 标 3 还是 4**，缺省时门禁跳过这项校验 |
| JD / 招聘方背景 | 否 | 有则写进「注意事项」，选题与情境题跟着它走 |
| 候选人姓名 | 是 | 缺失时用「候选人 A」，并在「注意事项」标注 |

抽取降级顺序：`pdftotext` → `python3` + `pdfplumber` → `office-docx` 技能 → 请用户粘贴。扫描件/图片按视觉读取，手册里标「按图片读取，可能有识别误差」。

## facts 表（内部工作产物）

不强制落进手册，但选题前必须先填；建议放在手册「面试前」的折叠块或单独草稿里。

| 项目 | 背景 | 本人角色 | 动作 | 结果 | 数字口径 | 疑点 | 原文 |
|---|---|---|---|---|---|---|---|
| 订单服务拆分 | 单体 2000 万行订单 | 主导（2 人） | 按域拆 4 个服务 | P99 800→200ms | 压测值，非线上 | 数字未标口径 | 「主导订单服务拆分，P99 下降 75%」 |

数字必须带分母、时间窗与口径（压测 / 线上 / 估算）；「参与 / 负责 / 主导」分开记；时间线重叠与技能栏缺口记成疑点。

## 手册骨架

元数据块必须在文件最前，字段 `key: value`，缺 `candidate` / `minutes` / `date` 判 error。元数据块之前允许一段 **YAML frontmatter**（Obsidian 的 tags/status），门禁会跳过它再找元数据块。

```markdown
<!-- resume-griller
candidate: 张三
role: 后端工程师
level: 中级
minutes: 60
date: 2026-11-19
resume: 张三-后端-2026.pdf
-->

# 面试手册：张三 · 后端工程师

## 面试前

- 画像：最强证据是订单中台拆分（有 P99 数字、有主导声明）；最需要确认的是「75%」的口径与本人实际承担的模块。
- 必须核实：① 主导还是参与（Q1）；② P99 是压测还是线上（Q3）；③ Kafka 在项目里的真实位置（Q2）。
- 时间表：开场 3′ · Q1 18′ · Q2 20′ · Q3 12′ · 收尾 7′（合计 60′）
- 短版：40 分钟只问 Q1、Q3（Q2 是加分项，时间富余再问）
- 简历优势：技术栈与岗位一致；有跨团队改造经历。
- 注意事项：未给 JD，按简历自述方向选题；数字均为简历口径，未核。

## 面试

### Q1 订单服务为什么按业务域拆

- 题源：「主导订单服务拆分，P99 下降 75%」— 项目经历 · 订单中台（2023.03–2023.09）
- 优先级：必问
- 考点：拆分边界的决策依据与代价
- 时长：18 分钟
- 追问：
  - 若只讲「按微服务规范」：问「当时还考虑过按读写拆吗，为什么否掉？」（想听：具体否掉理由）
  - 若讲不出代价：问「拆完多出来的跨域查询怎么解决的？」（想听：宽表或补偿的具体选择）
- 要听的点：
  - 4：给出否掉的另一种拆法与原因，并说清跨域查询的代价与失效条件
  - ★ 3：讲清拆分边界 + 一个量化结果，代价提到适配层或宽表
  - 2：只说「按规范拆」，问不出边界依据
  - 1：把团队方案说成个人设计，追问接口答不出
- 示范答案：
  - **结论**：先按业务域拆，不按读写拆——耦合在状态机，读路径只是慢
  - **代价**：跨域查询多一跳，用订单维度宽表加异步补偿对齐
  - **边界**：写入再涨一个数量级时宽表先撑不住，那时按用户分片
  - **口径**：压测峰值 2000 QPS，线上值待核〔待补充：线上真实峰值〕
- 危险信号：只讲收益不讲代价；数字口径说不清；把「参与」说成「主导」且举不出自己写的模块。

### Q2 Kafka 在你们链路里解决什么问题

- 题源：「熟悉 Kafka、RocketMQ」— 技能栏；项目描述未出现
- 优先级：选问（时间富余）
- 考点：技能是否真用过，用在哪条链路、怎么保证不丢不重
- 时长：20 分钟
- 追问：
  - 若说「做解耦」：问「解耦之后下游消费失败怎么处理，重试几次、死信去哪？」（想听：真实策略）
  - 若说不出重复来源：问「你见过重复消费吗，从哪来的？」（想听：重平衡或提交位点）
- 要听的点：
  - 4：说清 topic 划分与位点提交策略，能给出一次真实重复/丢失事故及修复
  - ★ 3：能定位到具体链路，说清至少一个可靠性机制（幂等表 / 事务消息）
  - 2：只报组件名与「解耦、削峰」两个词
  - 1：说不出这条链路的上下游是谁
- 示范答案：
  - **结论**：订单事务里写消息，独立任务投递，消费端幂等
  - **不丢**：本地消息表保证「已入库的必发出」，不依赖 MQ 默认配置
  - **重复**：幂等键用业务单号，不用消息 ID——重复来自位点回退
  - **代价**：延迟多一次轮询，约 200ms；只能做到最终一致〔假设：轮询间隔 500ms〕
- 危险信号：只说组件名；把「了解」说成「精通」；说不出失败后的兜底。

### Q3 P99 数字是怎么测出来的

- 题源：「P99 下降 75%」— 项目经历 · 订单中台
- 优先级：选问（时间富余）
- 考点：量化口径与验证设计，是否分得清压测与线上
- 时长：12 分钟
- 追问：
  - 若说是压测：问「压测模型怎么造的数据，和线上分布差多少？」（想听：差异与结论边界）
  - 若说是线上：问「哪个面板、哪个时间窗，改版前后的流量一样吗？」（想听：对照条件）
- 要听的点：
  - 4：区分压测与线上，给出时间窗、流量条件与噪声处理
  - ★ 3：说清口径（压测/线上）与大致时间窗，承认没做对照
  - 2：只说「监控上看的」，问不出口径
  - 1：数字与简历其他处矛盾且无法解释
- 示范答案：
  - **结论**：这是压测值，不是线上真实值——口径先说清
  - **对照**：改版前后各压 30 分钟，流量固定 800 QPS，取稳定段
  - **噪声**：主要来自 GC，看连续 10 分钟中位数而不是单点
  - **边界**：线上峰值没拿到，不能据此判断线上表现〔待补充：线上峰值与监控面板〕
- 危险信号：把压测说成线上；没有对照条件；被追问后改口。

## 面试后

- 评分维度：

| 维度 | 4 | 3 | 2 | 1 | 权重 |
|---|---|---|---|---|---|
| 技术深度 | 有独立判断与反例 | 做法 + 理由 + 证据 | 只能复述 | 概念错误 | 30% |
| 工程判断 | 取舍与演进清晰 | 讲清代价 | 只讲收益 | 无判断 | 25% |
| 证据与量化 | 口径与验证完整 | 有数字但口径模糊 | 数字对不上 | 无证据 | 20% |
| 协作与沟通 | 结构清晰、有推动 | 能讲清协作 | 泛泛而谈 | 情绪化 | 15% |
| 动机与匹配 | 动机具体、预期现实 | 基本合理 | 含糊 | 明显不匹配 | 10% |

- 判定（按顺序，先命中先生效）：任一维度 = 1 或存在未解释的事实矛盾 → 不通过；任一维度 = 2 → 待定；加权均分 ≥3.0 → 通过；其余 → 待定。
- 面评草稿：事实（回指题号）→ 判断（分维度 + 依据）→ 结论与建议（三段合计 ≤200 字）。
```

## 结构约束（门禁强制）

| 约束 | 严重度 |
|---|---|
| 元数据块存在，且 `candidate` / `minutes` / `date` 齐全、格式合法 | error |
| 四个 `##` 段落齐全（面试前 / 面试 / 覆盖核对 / 面试后） | error |
| 至少一道 `### Q<编号>`，编号不重复 | error |
| 每题有 `题源` 且含「」原文引用 | error |
| 每题有 `时长：N 分钟` | error |
| 每题有 `要听的点`，且 ★ 恰好一处、落在 `level` 对应档位（初级/中级 3，高级/架构 4） | error |
| 每题有优先级与时长：写在字段里，或写在标题的 `【必问 · 9′】` 里，二者取其一 | warn |
| 题目可以分布在 `## 面试` 与 `## 备用题` 两个段落 | — |
| 「面试前」有 `短版：` 行，其引用的题号必须存在 | warn / error |
| 题源允许 `「前段 ... 后段」` 省略写法，省略处不校验，每段都须在原文中 | — |
| 每题有 `示范答案` 且 ≥60 字 | error / 不足为 warn |
| **必问 + 选问**的时长合计 ≤ `minutes`（备用题不计），低于 60% 记 warn | error |
| 时间表里逐题分钟与题目 `时长` 一致、合计等于 `minutes`（只列计划题，备用题不进时间表） | error |
| 覆盖表按表头「落到哪一问 / 对应问题」定位目标列，允许多余列 | — |
| 覆盖表引用 `Q<n>` 必须存在；每行要么有题号要么有 `覆盖豁免：` | error / warn |
| 每题的 4/3/2/1 锚点不齐（须按行写 `- N：`，单行写比例不算） | warn |
| 代码围栏内的 `##` / `### Q` 不参与解析（不截断段落、不算题目） | — |
| 缺 `考点` / `危险信号` / `追问` / `时间表` / 维度表 / 判定 | warn（追问为 note） |
| `TODO` / `TBD` / `FIXME` / 裸「待补」 | error |
| `〔待补充：…〕` / `〔假设：…〕` | note，不阻断 |

规则码与严重度的**唯一清单**用 `--list-rules` 查，本文不抄全量枚举。

## 命名与落点

- 单人：`interview-<拼音或首字母>-<YYYY-MM-DD>.md`；多人：每人一份，另加 `interview-index-<YYYY-MM-DD>.md` 列名单与链接。**索引页不是手册**，不要对它跑门禁（缺元数据是预期内的）。
- 默认落在用户当前工作目录；用户指定目录时以用户为准。**候选人的简历、手册、JD 原文都不进仓库、不进 git**。
- 手册是 Markdown 纯文本，不依赖渲染服务；需要 PDF 由用户自行导出。

## 门禁用法

```bash
node skills/resume-griller/scripts/check-interview-doc.mjs <手册.md>...          # 0 = 无 error
node skills/resume-griller/scripts/check-interview-doc.mjs <手册.md> --strict   # warn 也阻断
node skills/resume-griller/scripts/check-interview-doc.mjs --list-rules         # 规则清单
node skills/resume-griller/scripts/verify-sources.mjs <手册.md> --resume <简历清洗稿.txt>  # 题源是否真在原文
```

退出码：`0` 通过（可含 warn/note，`--strict` 下仅 note）/ `1` 有 error / `2` 用法错误或文件读不到。

题源核验的退出码独立：`0` 全部定位到（含近似命中）/ `1` 有引文 `SRC-MISS` / `2` 缺 `--resume` 或文件读不到。近似命中（`SRC-NEAR`）不阻断，但要人工确认那一句是否真在原文——PDF 水印会造成插入噪声。
