# 答案键与评分

答案键不是标准答案，是**面试官在听什么**。同一道题允许不同路线，判断依据是「观点与证据的联系」，不是「像不像我脑子里那版」。

## 要听的点：四级锚点

每题写四条，从高到低，**★ 标在及格线那一档**：初级 / 中级岗标 3，高级 / 架构岗标 4。

| 档 | 语义 | 典型表现 |
|---|---|---|
| 4 | 有独立判断 | 说清取舍与代价，能给出反例或失效条件，能指出自己方案在哪失效 |
| 3 | 讲得清 | 做法 + 理由 + 一个具体证据（数字、事故、对比），没有明显漏洞 |
| 2 | 只会复述 | 讲得出流程，说不清为什么，数字对不上或只有团队成果 |
| 1 | 不成立 | 三类硬错：概念性错误、据为己有（把别人的工作说成自己的）、答非所问；不是「比 2 更差」，而是另一类 |

写锚点时避免「能说清 / 表达流畅」这类空话——要写**具体听到什么内容**：

```markdown
- 要听的点：
  - ★ 4：能说出「先按业务域拆、代价是跨域查询多一跳」，并给出当时否掉的另一种拆法及原因
  - 3：能说清拆分边界与一个量化结果（如 P99 从 800ms 降到 200ms），代价只提到「多写了适配层」
  - 2：只说「按微服务规范拆的」，问不出边界依据
  - 1：把团队架构方案说成自己设计，追问具体接口时答不出
```

## 示范答案：两层、四段、分点写

### 两层

- **简历可证的事实**（项目用了什么、他在哪段、结果是什么）：用「我们 / 我负责的这块」，必须能在简历里找到出处。
- **方案推演**（规模变了怎么选、对账怎么做）：用「我会」，涉及具体规模与口径先标 `〔假设：…〕`，候选人没给过的数字写 `〔待补充：…〕`。

示范答案不替候选人编造经历性事实——事故、评测集、压测数据、职责边界都算。

### 水位：资深高级研发工程师

示范答案按「能独立负责一条链路、带过人、做过故障复盘」的水位写，不是按「背过八股」的水位：

- 不只说怎么做，说**为什么这么做、代价是什么、什么条件下换方案**；
- 主动带运维与组织面：谁维护、怎么发现、怎么回滚、出事谁背；
- 数字带口径，不确定就标 `〔待补充〕`，不硬编；
- 不炫术语——能用一句话说清的，不用三句。

| 中级答法 | 资深答法 |
|---|---|
| 「用本地消息表保证不丢」 | 「消息表只保证已入库的必发出；崩溃窗口在写表前，所以 Lua 里要同写 pending」 |
| 「加索引优化查询」 | 「先看执行计划与回表行数；区分度低时加索引没用，改写更有效」 |
| 「用 Redis 缓存」 | 「先定能丢多少，再选同步策略；缓存是副本，DB 才是源」 |
| 「上 Redis 集群扛量」 | 「先算单机承载与瓶颈在哪，再决定分片；集群会带来一致性与运维成本」 |

### 四段（内容）

结论 → 依据 → 取舍 → 边界。缺哪段，4 档就拿不到。

### 分点（排版）

**一段 200 字没人读得下去。** 示范答案一律写成缩进列表，4–6 条，每条一行：

- 首条 `**结论**`：一句话给出主张；
- 中间 2–4 条：机制或步骤，每条一个 `**加粗引导词**`；
- 末条 `**核心原则**` 或 `**边界**`：一句话收口，说明什么条件下不成立。

约束：每条 ≤60 字；总数 120–220 字；不用表格、不用代码块（手机上难读）；分点不等于省掉条件，`〔待补充〕` 照旧。

```markdown
- 示范答案：
  - **结论**：语义上是「Redis 预扣 + 异步落单」，一致性靠对账，不追求强一致。
  - **扣减**：Lua 里同时写 pending 记录与扣库存，避免「扣了库存没记录」的窗口。
  - **投递**：扫描 pending 重投，失败按退避重试；消息至少一次，靠消费端幂等收敛。
  - **兜底**：DB 是库存最终权威，异常时按 pending 反向补扣。
  - **核心原则**：Redis 扛并发，Kafka 做异步，DB 保正确。
```

反例（不要这样写）：把上面五点连成一段 200 字的散文，面试官在现场只会跳读，条件全丢。

## 危险信号

听到就往回追，或直接在这一维扣分：

| 信号 | 追什么 |
|---|---|
| 全是「我们」，找不到「我」 | 「这一版里你提交的代码是哪部分？」 |
| 数字没有分母、没有口径 | 「这个提升是和什么比的？测了多久？」 |
| 只讲成功，问不出失败 | 「上线后第一次回滚是因为什么？」 |
| 责任全在外部（产品改需求、运维背锅） | 「如果重来一次，你会在哪一步做得不一样？」 |
| 技术名词密度高但一问就空 | 挑一个词问它在他项目里的具体位置与参数 |
| 对前司 / 前同事的评价带情绪 | 不追问细节，记录表达方式即可 |

## 评分维度

默认五个维度，权重按岗位调，总和 100%；招聘方给了维度就以招聘方为准。

| 维度 | 看什么 | 默认权重 |
|---|---|---|
| 技术深度 | 原理、边界、失效模式 | 30% |
| 工程判断 | 取舍、代价、演进路线 | 25% |
| 证据与量化 | 数字口径、验证方法、复盘 | 20% |
| 协作与沟通 | 表达结构、冲突处理、推动力 | 15% |
| 动机与匹配 | 为什么来、能待多久、期待是否现实 | 10% |

每个维度用同一套 4/3/2/1 语义（见上表），**打分必须附一句依据**，例如「工程判断 3：取舍讲清了，但没说清为什么否掉分片」。

## 判定规则

**按顺序判，先命中先生效**（并列条件会互相打架，所以优先级写死）：

1. 任一维度 = 1，或存在未解释的事实矛盾 → **不通过**
2. 任一维度 = 2 → **待定**（写明下一轮补验什么）
3. 加权均分 ≥ 3.0 → **通过**
4. 其余 → **待定**

事实一致性（时间线、职级、职责）单独记一条「事实风险」，**不折进「证据与量化」维度**——否则同一个问题被扣两次分。

规则可被招聘方覆盖，覆盖必须在手册「面试后」写明**改了什么、为什么**——不允许面试完临时改标准。

## 面评草稿

三段**合计**控制在 200 字内，禁止形容词堆砌；每条判断都要能回指题号：

```markdown
- 事实：Q2 能给出读多写少的判断与主从延迟的代价；Q4 的 QPS 数字与简历口径不一致，追问后承认是压测值。
- 判断：技术深度 3、工程判断 3、证据 2；强在取舍清晰，弱在指标口径与验证方法。
- 结论与建议：待定。下一轮补验「压测方法」与「线上真实峰值」，若仍说不清口径则按 2 计。
```

每条判断都要能回指题号，回指不到的内容不要写进面评——那是印象，不是证据。
