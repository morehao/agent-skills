# 答案正确性

这份文档管一件事：**示范答案在技术上是对的**。它不是「标准答案」——同一道题允许不同路线；但凡是断言某个机制怎么工作的地方，不允许错。

顺序：先核对事实，再谈像不像一段好回答。**宁可少写一条机制，不要写一条错的。**

## 三层校验

写完每段示范答案，过三遍，任何一遍不过就改：

| 层 | 问什么 | 不过的表现 |
|---|---|---|
| 技术事实 | 这个机制真的这样工作吗？我漏了什么前提？ | 把「配置到位才成立」说成默认保证；把补偿说成回滚 |
| 简历事实 | 这句话里的经历、数字、职责，简历或对话里有吗？ | 替他编事故、编评测集、编规模 |
| 题答对应 | 答案回答的是我出的那道题吗？ | 问取舍，答流程；问口径，答优化 |

## 高频错误对照

左边是面试里很常见、但站不住的说法，右边是可辩护的版本。写答案键时逐条扫一遍。

| 常见说法 | 为什么站不住 | 可辩护的说法 |
|---|---|---|
| Redis Lua 原子，所以库存不会超卖 | Lua 只保证单脚本内命令原子；Redis 与 DB 之间没有事务；主从切换可能丢写 | 预占 + 扣减流水 + DB 余量兜底 + 对账；超卖靠最终校验而不是「原子」 |
| Kafka 保证消息不丢 | 取决于 `acks=all`、`min.insync.replicas`、生产者幂等/事务、消费端提交位点；默认配置会丢 | 说清这套链路用了哪些配置，端到端语义是什么，哪一段仍可能丢 |
| MQ 削峰就是限流 | 削峰是缓冲，队列无上限时只是把故障推迟；限流是入口的拒绝/排队 | 入口限流 + 有界队列 + 消费能力监控，三者一起说 |
| MQTT QoS 2 等于端到端 exactly once | 只在客户端与服务端都完整实现会话时成立；业务层仍可能重复 | 协议层语义 + 业务幂等键，两层都要 |
| WebSocket 是可靠的 | TCP 之上不假，但连接会半开、会断；重连后状态要重建 | 心跳 + 超时摘连接 + 重连全量同步 + 消息序号 |
| TCC 是强一致 | TCC 是最终一致 + 补偿；还有空回滚、悬挂、幂等三个坑 | Try 预占、Confirm/Cancel 幂等，明确不一致窗口 |
| Saga 会回滚 | Saga 只做补偿，不保证隔离，中间态对外可见 | 说清补偿动作与可见的中间状态，必要时加语义锁 |
| Seata AT 万能 | AT 依赖全局锁与回滚日志，热点行会放大冲突 | 说清适用规模，热点场景换 TCC/消息表 |
| 唯一索引防重就够了 | 只防同键并发插入；回滚后重试、软删、分库后的全局唯一都要另处理 | 唯一键 + 幂等状态机 + 对账三层 |
| 缓存双写天然一致 | 写库删缓存也会失败；强一致与高可用不可兼得 | 先写库再删缓存 + 重试/延迟双删或订阅 binlog，接受收敛时间 |
| Redlock 是安全的分布式锁 | 有时钟漂移与进程停顿争议，边界内可能双持锁 | 单点仲裁或 fencing token；非强一致场景用它要说明风险 |
| ES 深分页用 from + size | 成本随 from 线性增长，深翻会打爆协调节点 | `search_after`（有序翻页）或 `scroll`（离线导出） |
| ES 写完立刻能查到 | 默认 1s refresh，是近实时 | 需要读己之写时显式 refresh，或接受延迟并说明 |
| 分库分表后 join 照常 | 跨库 join 不支持，聚合要上移 | 冗余表、广播表、应用层聚合，说清选哪种 |
| GOGC 调低能降内存 | GOGC 影响回收频率，不直接降峰值 | 看对象生命周期与 pprof，GOGC 只是权衡 CPU/内存 |
| goroutine 泄漏重启就好 | 重启掩盖问题，泄漏点还在 | pprof goroutine 看栈，定位阻塞的 channel/锁/未取消的 context |
| 加了 Redis 计数就是限流 | 固定窗口有临界突刺；计数不等于限流 | 滑动窗口/令牌桶，阈值来自压测，超限有排队或降级 |
| RAG 接了向量库就不幻觉 | 检索质量、知识时效、生成约束三处都会漏 | 评测集 + 拒答策略 + 知识同步延迟的兜底话术 |
| 多模态生成的标题可以直接上架 | 合规与类目校验不能省 | 敏感词/类目校验 + 人工兜底 + 失败回退模板 |
| P99 200ms 就是接口快 | 没说口径：网关到返回？含不含异步？压测还是线上？样本量多少？ | 先问口径，再谈优化；数字带分母与时间窗 |

## 措辞纪律

- **绝对化词只在事实层面成立时用**：`一定`、`绝不`、`保证`、`100%`、`永远不会`。拿不准就写条件：「在 acks=all 且副本同步的前提下……」。
- **每个机制断言带条件**：什么配置、什么规模、什么失败模型下成立。
- **不确定的机制标 `〔待核实：<查什么>〕`**，不要用「一般来说」蒙过去。
- **数字只有两个来源**：简历原文，或显式 `〔假设：…〕`；不允许「大概」「差不多」。
- **区分「我做过」与「我知道」**：示范答案里属于候选人的事实，只能用简历有的；推演用「如果是我」。

## 复核清单（写完逐条打勾）

- [ ] 每条机制断言都能说出成立条件，没有把「配置到位才成立」写成默认保证
- [ ] 没有把补偿（Saga/TCC/消息表）说成回滚或强一致
- [ ] 没有替候选人编事故、评测集、压测数据、团队规模
- [ ] 数字要么出自简历，要么标了 `〔假设〕`/`〔待补充〕`
- [ ] 答案回答的是题目问的那件事（取舍 vs 流程、口径 vs 优化）
- [ ] 绝对化词都删了或补了条件
- [ ] 拿不准的地方标了 `〔待核实〕`，没有硬编一个「听起来对」的机制

有子 agent 时，把写好的答案键交给**独立上下文**复核一遍，只让它回「哪条断言不成立、条件是什么」，不回改写建议——避免它顺着原文把错误合理化。
