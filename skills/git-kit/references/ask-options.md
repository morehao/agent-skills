# 决策点：一律给选项（`release` / `tag` / `pr-merge` 共用）

**凡需要用户决定的事，必须用宿主的选项式提问给出候选，不能只打印一段现状、等用户用自然语言回。**

反面模式（本文件要解决的问题）：打印预检结果 + 计划卡 + 「要不要发新版本？」，然后停下来等一句「对，发 0.1.6」。用户被迫同时做三件事——判断该选什么、想清楚怎么表述、再等下一轮。而选项式提问把「有哪些选择、各自代价」直接摆在眼前，点一下就结束。

## 规则

1. **决策落在选项上，汇报落在正文里**：计划卡、回执、预检结果照常打印（那是信息）；但**决策本身必须是一次带选项的提问**，不能是开放式追问（「是否继续？」「要发版吗？」不算）。
2. **优先用宿主机制**：dsh 用 `ask_user_question`（**一次调用可含多题**，每题带 `header`、`options`，可选 `multi_select`）；其他宿主用其等价的提问/选择能力。宿主没有该能力时，退化为编号列表，并明确写「回复编号即可」——不要退化成「请说明你的选择」。
3. **一次问全**：同一阶段内能并进一次调用的决策合并提出，不要一个个打断。例如发版确认一次问三题：是否按此打 tag / 写不写 CHANGELOG / GitHub Release 谁创建。
4. **选项写法**：
   - 推荐项**放第一位**并标 `（推荐）`；
   - 每个选项一句话说明**后果或代价**，不是只重复标题；
   - 永远保留 `自定义 / 其他` 兜底项（用户可能想要候选之外的值）；
   - 选项文本要**短**——长内容（计划卡、注记正文全文）放在提问之前的正文里，不塞进选项。
5. **不替用户选**：用户取消或没选，就停在当前状态，报告「已做 / 未做 / 下一条命令」；不要因为「看起来该发版」就自行选推荐项往下走。
6. **不可逆操作单独一题**：删 tag、重打 tag、force push 这类，题面必须写明不可逆后果，推荐项是「停止」。

## 标准选项形状

| 场景 | 选项（推荐项在前） |
|---|---|
| 确认执行 | `按此执行（推荐）` / `取消` / `改参数（自定义）` |
| 二选一副作用 | `不做（推荐，零副作用）` / `做（写明代价）` |
| 版本取值 | `patch` / `minor` / `major` / `自定义` |
| 失败后处置 | `只报告（推荐）` / `重跑` / `下个版本` |
| 不可逆操作 | `停止（推荐）` / `授权执行（写明不可逆后果）` |
